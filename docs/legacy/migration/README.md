## 跨功能链路不能拆丢

1. **Todo ↔ Today**：同一事项的集合视图与日视图；不能创建两份任务副本。
2. **Journey → Inbox**：开始体验另外创建待办，旧库没有正式外键。匹配仅能视为待核对推断，不能只按相同标题自动去重合并。
3. **业务对象 → 文档**：草稿、感想、摘录、回顾答案、手记都通过 ID 引用 `d_tiptap`；看板也在其中但结构不同。
4. **再次体验 → 共享材料**：复制的 Watch payload 可能仍指向同一感想 / 摘录。
5. **业务 payload ↔ 标签词库**：记录上的字符串是实际关联，词库只提供选项；保留 group、前缀和地点层级。
6. **正文 → 媒体**：当前正文和历史、头像和封面都可能引用同一文件。
7. **Journal 正文 → 搜索与统计**：`raw_text / word_count` 是派生数据，导入或恢复后应重建或校验。

## 导入数据核对

| 检查对象         | 必须保留 / 解释                                                | 不能直接假定                                 |
| ---------------- | -------------------------------------------------------------- | -------------------------------------------- |
| 用户             | 邮箱与旧 creator ID 映射、昵称、头像、语言                     | 旧数字 ID 就是 Palace owner                  |
| 集合与 Todo      | ID、归属、顺序、难度、链接、执行次数、归档和计划语义           | Inbox 是普通集合；Archive 名称等于归档状态   |
| 时间             | 原时间值、部署时区、业务时间含义                               | `created_at` 永远不可变；旧周号等于 ISO 周号 |
| 文档             | 当前 JSON、可用历史、版本值、所属对象和共享引用                | 每条正文都只有一个所有者对象；全是富文本     |
| Journey          | 作品年份与体验日期、评分倍率、轮次、累计进度与 checkpoint      | 相同作品名表示重复记录；-1 表示倒退进度      |
| Echoes           | 类型、周期、题号和[题目内容](../dashboard/echoes/questions.md) | 问题文本保存在数据库；周期记录必然唯一       |
| Journal          | 正文、日期、收藏、标签、地点、回顾次数                         | 默认 PUBLIC 就有匿名阅读能力                 |
| 附件             | UUID 到对象 key 的映射与实际文件                               | 签名 URL 永久有效；删元信息必然删文件        |
| 软删除与孤立记录 | 分类列出、明确导入政策                                         | 所有未被当前列表引用的正文都是垃圾           |
| 连接配置         | 服务类型、账号、加密凭据处理办法                               | 旧密文可直接用于新服务                       |

## 融合时需要另定的产品边界

这些是从旧实现发现的待决策事项，不作为本次新增功能要求：

- Todo 的长期事项、每日执行和归档在 Palace 中如何表达；是否补执行历史与循环计划。
- Journey 开始时生成的提醒要继续独立，还是显式关联作品体验；重复体验的感想是否共享。
- Echoes 的周与十年边界、历史补写限制、重复周期数据如何处理。
- Quick Note、cheatsheet、Blog、Journal 是否保留独立类型；统一入口后怎样保留各自操作和元信息。
- Blog / Entry 的公开状态是否发展为真正的分享权限与公开阅读；图片分享如何保留。
- 多端并发、放弃修改、历史恢复和删除回收如何使用 Palace 自身一致性规则。

## 已知旧版限制

旧版存在日期哨兵、多用途时间列、先正文后元信息的非事务创建、业务删除不清理附件、强制保存绕过版本检查、历史仅保留 7 天等事实。这些必须在导入解释中处理，但不要求新系统重复同样的技术设计。

目前证据覆盖 9 张截图和该发布版的页面 / handler / model。尚未检查线上数据数量、孤立 / 重复行、历史时区、外部服务可用性和附件完整性；正式导入前应对数据副本执行上述核对。
