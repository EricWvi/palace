# 决策记录（ADR）

`decisions` 用于承载 ADR。ADR 必须放在对应领域的叶子节点文件夹下，例如：
`specs/decisions/desktop/core/effect/`。

每个叶子节点文件夹中的 ADR 按连续决策记录维护：

- 第一个决策是根决策，文件名使用 `0-短句名称.md`。
- 后续 ADR 的文件名使用 `YYYYMMDD-短句名称.md`，日期部分表示该决策的年份和日期。
- 每一个后续 ADR 都必须基于前一个 ADR 进行改动，并在内容中说明继承或修改的决策依据。
- 短句名称应简洁、能够概括决策主题，并使用小写字母与短横线连接。

## ADR 生命周期

ADR 的 frontmatter `status` 表示决策所处阶段。决策从提案到落地时，按下面的顺序维护；状态变化时
同步更新 ADR 正文。ADR 状态变为 `approved` 后，才开始维护其对应的核心测试用例。

### proposed

`proposed` 用于记录尚在评审的方案。此阶段应详细说明问题、风险、决策依据、替代方案、约束、不变量
和预期行为，使 reviewer 能够在没有实现代码的情况下纠偏。可以包含少量帮助说明语义的代码片段或
数据示例，但它们只用于解释决策，不构成实现契约。此阶段不要编写或维护核心测试用例；核心测试用例
应在 ADR 评审通过、状态变为 `approved` 后，依据最终同意的决策补充。

### approved

完成评审后，先根据反馈纠正决策内容，再将 frontmatter 标记为 `approved`，并依据最终同意的方案补充
受影响的核心测试用例。标记前应确保决策依据、边界条件和不变量已经反映最终同意的方案；不能仅通过
修改状态字段代替纠偏。

### implemented

代码实现完成并验证后，将 ADR 标记为 `implemented`，并根据最终实现重新同步 ADR。此时精简决策表述，
保留稳定的领域规则、约束和必要的决策依据，删除代码片段、临时方案、未采用的实现细节和已经失效的
推测。ADR 应描述最终系统承诺，而不是实现过程或历史草稿；若最终实现偏离 approved 决策，应先在正文
中明确记录实际采用的决策及偏离原因，再标记为 `implemented`。

## ADR 写作风格

ADR 应让 reviewer 在没有实现代码的情况下，沿着“问题 → 约束 → 决策 → 后果 → 验收”的链路完成
判断。优先写稳定的系统承诺和选择依据，不写会议记录或实现流水账。

### 先给结论，再交代边界

- 标题直接写出核心选择及其替代关系，正文开头用一段话说明最终方案、关键行为变化和影响面。
- 紧接着说明当前 `status` 的含义、涉及的模块、明确的兼容性边界，以及本 ADR 不承担的迁移
  义务。不要让 reviewer 读完整篇后才知道决策到底是什么。
- 使用领域术语、代码符号和路径时保持原样；解释性正文使用中文，示例、标识符和协议字段使用代码
  格式。必要时用一个最小输入/输出示例固定语义。

### 显式继承前序决策

后续 ADR 应在“继承与修改”一节中列出此前决策汇总的关键约定，并用表格逐项标记“继承，不变”或“修改”。
只描述本 ADR 真正改变的边界；不把之前所有 ADR 重新复制一遍。修改项必须说明新的规则，避免只写“调整”
而不写调整后的系统行为。

### 用编号决策组织主体

将互相独立、可以分别评审的选择写成 `D1`、`D2` 等小节。每项决策遵循以下顺序：

1. 先写规则和对外可观察的行为。
2. 再写为什么这样选，包括约束、不变量、失败模式和必要的代价。
3. 对容易误解的边界给出反例、表格或短代码块；表格用于精确对比，代码块只用于固定语义，不作为
   实现契约。
4. 把跨决策的约束集中到“不变量”一节，使用编号，确保每条都能在评审或测试中单独判断。

解释设计时优先回答“为什么”，尤其要说明数据来源、身份边界、持久化影响、错误处理和可变输入如何
影响系统承诺。对于有损规范化、定长标识、特殊保留值、来源归属等规则，必须同时说明可读性、唯一性、
稳定性和文件系统/协议约束之间的取舍。

### 正面比较替代方案

使用“为什么不是这些替代方案”一节，以表格列出真正考虑过的方案及否决理由。理由应落到本 ADR 的
约束或不变量上，例如唯一性、跨平台稳定性、可迁移性、可观测性、错误可解释性或升级风险；不要只写
“复杂”或“不可扩展”。若某个替代方案在特定维度更优，也应明确承认其优势及最终取舍。

### 收束到风险、未决项和落地

- 对会破坏历史状态、身份匹配、目录布局、事务顺序或外部副作用的规则，单独说明“为什么不能直接
  改写”，并给出安全的迁移或重建路径。
- “本决策未解决的问题”只记录明确留在后续 ADR 的边界，并说明为什么超出当前范围；不要把未完成的
  思考伪装成当前决策。
- “不变量”应是简短、肯定、可验证的系统承诺，不写实现步骤或模糊愿望。
- “落地顺序”按可独立验收的阶段拆分；每一步说明范围、完成条件，以及这样拆分如何降低评审或实现
  风险。最后明确哪些行为保持不变，哪些行为从该阶段开始改变。

整篇 ADR 保持论证密度：用短段落承载因果关系，用项目符号列举平行后果，用表格承载精确映射或取舍。
避免空泛的背景铺陈、重复结论和未经验证的实现细节；在 `proposed` 阶段保留能帮助评审的推测与示例，
进入 `implemented` 后删除已失效的推测、临时代码和未采用方案的实现细节。

# 核心测试用例

`test-cases` 是 reviewer 的风险导航图，用于记录需要长期关注的系统承诺及其直接测试证据。按业务
行为和风险组织核心用例，不按 crate、测试文件、单元测试或集成测试分类，也不登记所有测试函数、
表驱动输入或属性测试样本。

## 目录镜像

- `decisions` 与 `test-cases` 的领域目录必须完全镜像；移除各自根目录前缀后，相对路径必须一致。
  例如 `specs/decisions/desktop/core/effect/` 对应
  `specs/test-cases/desktop/core/effect/`。
- 创建或移动 ADR 领域目录时，同步创建或移动对应的 test-case 目录。test-case 文档只放在拥有对应
  decisions 目录的领域路径下。

## 稳定引用

- 供代码注释引用的核心用例标题必须使用英文，并作为文档中的二级标题。文件路径与该标题生成的
  Markdown anchor 共同构成稳定引用，例如
  `specs/test-cases/desktop/core/effect/convergence.md#replaying-a-converged-generation-must-have-no-side-effects`。
- 文档标题、风险、前置状态、验证义务等非引用标题使用中文；仅核心用例标题为稳定代码引用保留
  英文。
- 重命名或移动已有核心用例前，先更新代码中的全部引用和本目录内的索引链接。

## 用例内容与证据

- 满足以下任一条件的行为应成为核心用例：改变状态或转换、改变副作用或事务顺序、涉及 ownership、
  重试、取消、超时、并发、幂等、协调、恢复、安全、兼容性，或跨 crate、进程、transport、持久化
  层流转。
- 每个核心用例至少描述风险、前置状态、触发、必须成立、禁止结果、验证义务与证据、决策依据。
- 先把系统承诺拆成可独立判断的验证义务，再为每项义务列少量代表性证据。只有测试失败会直接说明
  该验证义务不成立时，才把测试列为证据。
- 使用 `Covered`、`Partial`、`Missing` 标记证据状态：完整义务有直接证据才是 `Covered`；只证明
  部分路径或较低层规则时是 `Partial`；没有直接证据时是 `Missing`。如实保留缺口，不用间接依赖
  测试填补证据表。
- ADR、状态机、持久化模型或外部副作用发生变化时，必须同步检查对应核心用例、验证义务和证据状态。
  新增、删除、重命名或弱化代表性测试时，也必须同步更新证据表。

# Markdown 路径变更

移动、删除或改名 `specs/` 下任意 Markdown 文件时，必须在同一次变更中维护两个仓库的路径一致性：

1. 从代码仓库根目录全局搜索旧路径、文件名和相关 Markdown anchor，更新代码注释、源码内嵌文档、
   测试引用及其他仓库文档中的全部引用。
2. 使用 `git -C specs` 在独立的 `specs` 仓库内全局搜索同一组引用，更新 ADR、核心测试用例、索引
   和交叉链接；同时检查 `decisions` 与 `test-cases` 的镜像目录是否仍然一致。
3. 搜索结果必须逐项判定：保留的历史说明要明确不构成当前路径引用，其他旧路径不得残留；新路径和
   需要维护的 anchor 必须存在。

完成条件是代码仓库与 `specs` 仓库都没有指向已移动、删除或改名文件的活动引用，且所有受影响的镜像
目录、索引和稳定引用已经同步。
