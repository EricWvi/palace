# `pal article upload` 从文章目录读取 `article.json`、Markdown 与本地媒体，一次请求导入 Palace

新增 `pal article upload <path-to-dir>`：从目录内的 `article.json` 读取元数据，从唯一的 Markdown 文件读取正文，将正文中 `assets/<文件名>` 的行内图片引用转换成 `media:<文件名>`，连同引用到的文件一次提交给现有 `POST /api/articles`。成功时输出服务端返回的文章 JSON；同一 Owner 下重复上传相同原文网址，返回已有文章，不更新正文或元数据。命令只读取本地文件，不修改源目录。

当前为 `implemented`，命令已实现并通过本地与真实依赖验证；核心测试用例见[文章上传](../../test-cases/cli/article-upload.md)。本决策基于 [pal CLI 根决策](0-pal-cli-uploads-and-deletes-media-with-env-token.md)，承接[文章导入决策](../web/stars/20261020-articles-imported-with-media.md)的 HTTP 协议。影响范围是 `apps/pal` 与 CLI 使用文档；服务端、数据库、Web 和 OpenAPI 契约不变。不提供批量目录上传、抓取网页、HTML 转换或历史数据迁移。

## 问题与约束

- Eric 指定的参考目录 `/home/eric/projects/reading-list/2026/07/3` 中有一个 `getting-started-with-loops.md` 和 `assets/` 下四个 JPEG 文件。正文以 `![alt](assets/09dbace0173e57a4.jpg)` 等形式引用图片，没有 frontmatter；文章标题在首行一级标题中，作者出现在末尾文字中，但原文网址和发布日期没有结构化来源。
- 经本次讨论确认，元数据放在目录新增的 `article.json` 中，不要求修改 Markdown。参考目录说明文件布局，不意味着 `2026/07/3` 是发布日期，也不能从文章中出现的其他链接猜测原文网址。
- 现有文章接口要求 `title`、`content`、`url`、`date`，作者可选。正文与媒体应在一次请求中提交，文章、Moment 和媒体记录由服务端同一事务写入；不能先逐张执行 `pal s3 upload`。
- 原文网址在 Owner 内按字节比较并唯一，决定重复导入身份；文章正文导入后不可编辑。元数据猜错或媒体漏传的代价高于一次明确的本地校验失败。
- 服务端只识别行内图片语法中的 `media:` 引用，引用名必须为 1–128 个 `[A-Za-z0-9._-]` 字符；每个引用必须有文件，每个提交的文件必须被引用。

## D1：一条命令对应一个文章目录，元数据唯一来源是 `article.json`

```text
3/
├── article.json
├── getting-started-with-loops.md
└── assets/
    ├── 09dbace0173e57a4.jpg
    ├── 284c7ab10a927e19.jpg
    ├── 6e807e1d39157cca.jpg
    └── a1d6a3adf5d8cdb8.jpg
```

`article.json` 是 UTF-8 JSON 对象，字段与导入 API 对齐，不包含正文或媒体清单：

| 字段 | 规则 |
| --- | --- |
| `title` | 必填字符串，去除首尾空白后非空，最多 1024 UTF-8 字节；保留原始值 |
| `url` | 必填字符串，绝对 `http`/`https` 原文网址，最多 2048 字节，无首尾空白；不规范化、不去 query、不补尾斜杠 |
| `date` | 必填字符串，`YYYY-MM-DD` 或带偏移的 RFC 3339 时间；原样传递，日期的时区解释由服务端决定 |
| `author` | 可选字符串或 `null`，最多 256 UTF-8 字节；缺失、`null`、纯空白按 API 表示无作者 |

拒绝重复键和未知字段，避免把 `data`、`source_url` 等误拼字段静默忽略。`title` 不从一级标题回退提取，`author` 不从正文末尾猜测，`date` 不从目录、文件时间或 Git 历史推断。JSON 不接受注释或尾逗号。

目录顶层必须恰好有一个扩展名为 `.md` 的普通文件，作为整篇正文；不递归寻找正文，不固定 Markdown 文件名。没有或有多个时失败，并指出候选文件。不增加 `content`、`markdown` 或 `path` 元数据字段，避免同时维护两份正文选择规则。其他不参与上传的文件忽略，未引用的 `assets` 文件也不上传；无本地媒体的文章无需 `assets/`。

Markdown 必须是非空 UTF-8 文本，不解析或剥离 frontmatter。其内容整体作为正文，只有 D2 中的媒体地址可以改变；一级标题、作者署名、换行和其他文字保留。源文件在任何结果下都不写回。

**选择依据**：旁置 JSON 保留现有阅读和编辑习惯，字段直接对应 API，也适合抓取工作流生成。唯一 Markdown 自动发现使文件改名不必同步元数据；要求显式填写标题等字段，代价是准备目录时多写一份元数据，收益是没有隐式推断和优先级冲突。

## D2：只转换正文中明确的本地行内图片引用，媒体清单从正文派生

用 Markdown 解析结果识别嵌入，不能对正文做正则全局替换。与服务端使用相同的 Markdown 扩展语义，只改写行内图片的地址区间，不重新渲染整篇 Markdown。

| 输入 | 行为 |
| --- | --- |
| `![封面](assets/09dbace0173e57a4.jpg)` | 改成 `![封面](media:09dbace0173e57a4.jpg)`，附上对应文件 |
| `![](./assets/demo.mp4)` | 改成 `![](media:demo.mp4)`；视频沿用 API 的图片语法，由媒体类型决定播放器 |
| 多处图片引用同一个 `assets/<文件名>` | 所有对应地址都改写，文件只提交一次 |
| 行内代码、代码块中的 `![](assets/a.jpg)` | 原样保留，不读取文件 |
| 普通链接 `[下载](assets/a.jpg)` | 原样保留，不作为附件上传 |
| 图片的 `https://`、`http://`、`//` 或 `data:` 地址 | 原样保留，不联网抓取；阅读页仍按现有规则显示占位 |
| 引用式本地图片 `![alt][ref]`，定义指向 `assets/a.jpg` | 本地拒绝，提示改成行内图片语法 |
| 图片地址为 `media:...` 或 `/api/media/...` | 本地拒绝；此命令只从目录组装文件，不接受手写占位符或既有媒体身份 |

支持的本地媒体路径仅为 `assets/<文件名>` 或 `./assets/<文件名>`，文件名直接作为 multipart 的 `filename` 和 `media:` 引用名，必须符合服务端的字符与长度限制。首版不支持 `assets` 的子目录、中文或含空格的媒体文件名、百分号编码、query、fragment、绝对路径、`file:` URL、反斜杠或 `..` 路径段；其他本地图片地址在发送前失败，提示支持的布局。未知地址 scheme 也拒绝，避免本地媒体被当作外链静默遗漏。

只读被正文引用的普通文件。为避免符号链接把上传范围扩大到目录以外，所选 Markdown、`article.json`、`assets` 目录和引用的媒体文件均不得是符号链接；用户传入的目录路径可先解析为实际根目录。构造文件路径使用 `Path` / `PathBuf`，不把 Markdown URL 直接当作任意文件系统路径。未被引用的文件不因存在而导致拒绝，也不会被打开。

**选择依据**：参考目录已使用扁平 `assets` 和合规的哈希文件名，直接保留名字便于诊断，也没有截断、转义或不同路径合并后的命名碰撞。限制输入布局比引入自动重命名、递归资源发现或改写共享引用定义更容易解释；将来扩展布局需要另行决定映射规则。

## D3：先完成本地校验，再用一个 multipart 请求提交

执行顺序为：

1. 校验现有 `PAL_URL`、`PAL_TOKEN` 配置；发现正文和 `article.json`，解析字段与 Markdown 引用。
2. 校验 D1、D2 的全部本地规则，确认引用文件可打开且为普通文件；转换后的正文也须非空且不超过 API 的 4 MiB 限制。检查完成前不发出网络请求。
3. 向 `POST /api/articles` 发送一次 multipart。首个 part 是 `article`，类型为 `application/json`，字段为 `{ title, content, url, author?, date }`；后续每个独立的引用文件一个 `file` part，按文件名排序发送。
4. 文件名使用 D2 中的引用名，`Content-Type` 沿用媒体命令按扩展名推断的规则，未知类型为 `application/octet-stream`。正文和元数据在内存中组装，媒体内容以文件流发送。
5. 仅 `201`（新建）或 `200`（返回已有文章）视为成功，确认响应为合法 JSON 后，一次输出服务端文章响应及结尾换行。

本地校验只检查 API 的稳定字段约束，不猜测部署配置。单媒体大小与整个请求的上限由服务端决定，`413` 按原有错误格式报告。只含日期的 `date` 不在 CLI 按本机时区转换，服务端仍按 `PALACE_TIMEZONE` 解释。

不为“已经存在的网址”跳过本地目录校验，也不先发 GET 探测；即使服务端可能返回已有文章，命令仍要求输入目录完整。上传过程中文件被修改或删除属于本次读取失败风险，CLI 不提供跨文件快照；运行期间应保持目录稳定。错误在网络发送之后发生时，不能承诺服务端没有提交。

**选择依据**：一次请求保留文章接口的事务边界和媒体归属；先校验可避免上传几张图片后才发现另一个引用不存在。服务端仍是最终校验和并发收敛的权威，不在 CLI 复制事务、数据库或存储逻辑。

## D4：重复上传是“返回已有文章”，失败不自动重试

同一 Owner、完全相同 `url` 的重复或并发上传由 API 收敛为同一篇文章。`200` 与 `201` 都退出 0，stdout 为服务端实际返回的完整文章 JSON；不能用本地输入拼出成功响应，因为已有文章可能与本次输入不同。

命令不自动重试，沿用 CLI 的显式调用习惯。断线、响应读失败、成功状态下 JSON 不可解析，或用户中断时，文章可能已经保存；诊断应说明“可使用相同原文网址重新运行，已有文章不会被覆盖”，不能沿用媒体命令“重试产生第二个媒体”的警告。重跑前改变 `url`、在 Web 中修改已有文章的 `url` 或更换 Owner，都会改变幂等匹配范围。

| 情形 | 退出码与输出 |
| --- | --- |
| 缺少目录参数、未知参数或子命令 | 2，命令行解析器写用法提示 |
| 配置、目录、JSON、Markdown、引用或文件读取不合规则 | 1，stderr 指出文件路径、字段或引用及原因；stdout 为空 |
| 网络或响应解析失败 | 1，stderr 说明原因和提交结果可能不确定；stdout 为空 |
| 非 `200` / `201`，包括重定向 | 1，stderr 沿用 HTTP 状态码与 API 错误字段；stdout 为空 |
| 新建或命中已有文章，且响应 JSON 合法 | 0，stdout 输出文章 JSON 及换行 |

复用既有认证错误提示、禁止重定向、10 秒连接建立超时与无整体请求超时策略。所有诊断不包含 token，进度与诊断不混入 stdout。失败时不自行删除服务端文章或媒体，清理由导入接口负责。

## 不变量

1. 一次命令只选择一篇正文，所有元数据来自该目录的 `article.json`。
2. 所有可预先发现的本地输入错误都在发送请求前报告。
3. 转换只改变本地行内图片的地址；源目录始终只读，代码与普通链接不因相同字符串而被改写。
4. 每个提交文件都被转换后的正文引用，每个生成的 `media:` 引用都有且只有一个提交文件。
5. 一次调用最多发送一次 `POST /api/articles`，不调用 `POST /api/media`，不直接访问数据库或对象存储。
6. 相同 Owner 和原文网址的重复上传不更新已有文章，也不产生第二篇文章；该承诺由服务端兑现。
7. stdout 只在确认成功后输出服务端结果，任何失败都返回非零退出码。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 本次取舍 |
| --- | --- | --- |
| Markdown frontmatter 存元数据 | 元数据与正文同一文件，移动方便 | Eric 选择旁置 `article.json`；不改动现有 Markdown，也不引入 frontmatter 剥离规则 |
| 命令参数或交互输入元数据 | 可以直接上传现有无元数据目录 | 上传材料无法随目录完整保存；脚本或重跑可能换了原文网址，破坏稳定身份 |
| 从 H1、末尾署名、目录日期猜元数据 | 少写配置 | 示例缺少原文网址，目录末级可能是编号；猜测会把不可靠信息永久保存，见 D1 |
| 将整个 `assets/` 全部上传 | 不需要解析哪些图片被引用 | API 拒绝未引用文件；也会把目录里的备用资源误存入文章 |
| 全文字符串替换 `assets/` | 实现短，适配示例直观 | 会改坏代码示例、普通链接和图片标题，违反不变量 3 |
| 先逐张调用媒体上传，再创建文章 | 复用 `pal s3 upload`，每张可以单独重试 | 破坏现有文章导入协议的事务与归属边界，中断会留下独立媒体 |
| 为任意文件名生成新的引用名，支持任意嵌套目录 | 用户无需整理目录 | 需要新增命名稳定性、碰撞和编码规则；参考布局已满足扁平文件名约束，首版收益不足 |

## 风险与为什么不能直接改写

- **元数据准备**：参考目录需要补齐 `article.json` 才能上传，CLI 不修改 reading-list 仓库或自动填值。真实原文网址、发布日期必须由内容维护者确认。
- **正文不可原地修复**：上传后修正本地 Markdown，再次上传相同网址仍返回旧正文。误导入时应明确删除旧文章及媒体、确认删除成功后再导入；这会产生新文章身份和导入时间，不能把重跑描述成更新。
- **媒体规则有意收窄**：引用式图片、HTML 媒体标签、普通附件链接、远程媒体下载与任意嵌套资源目录不属于本次转换能力。原始 HTML 按现有 Markdown 渲染规则处理，不据此收集附件；远程图片仍会显示占位，不能承诺整篇文章的所有外部资源已离线化。
- **源文件可变**：打开文件不能保证其他进程不修改其内容；本次不引入锁、临时完整副本或内容快照。发送中的失败按 D4 报告，服务端保持原有对象清理与事务保证。
- **网址是可变身份**：CLI 不规范化 `url`；编辑已有文章网址后，再用旧网址上传会创建新文章。这继承现有 API 行为，不能在 CLI 单方面改成按文件名、目录或内容哈希去重。

## 本决策未解决的问题

批量遍历 reading-list、读取抓取项目内部索引、自动补齐元数据、上传前预览、独立 `check` 命令、更新已上传正文、远程资源下载、HTML 转 Markdown，以及支持更宽松的媒体路径，都留待具体需求；它们分别涉及额外输入源、更新语义或资源映射规则，不影响本次单目录上传。

## 落地与验收
