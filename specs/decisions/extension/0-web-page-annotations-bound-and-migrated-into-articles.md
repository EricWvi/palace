# 浏览器插件在原网页上标注，标注按网页地址存进 Palace；网页由用户绑定到已导入的文章后，标注在文章页重新定位并迁移，原网页转为只读显示

> 历史决策：D7 中「插件打开网页时，按地址拉取这个网页的状态和原网页标注」已被[标注默认关闭，按标签页开启](20261021-annotating-off-until-turned-on-per-tab.md)修改：插件只在读者开启了标注的标签页里工作，Palace 自己的页面不能开启。

新增一个 Chromium 浏览器插件。读者在任意网页上选中文字，可以留下与 Palace 相同的高亮、划线、波浪线和批注。这些**原网页标注**用 Access Token 直接存进 Palace 服务端，按网页地址归组，每次保存时顺带记下标签页标题，供插件的列表页浏览。文章被抓取项目导入 Palace 后，读者在插件里把这个网页**绑定**到一篇文章：插件给出候选文章，同一域名、路径相近的排在最前，最终由读者选定。绑定后打开 Palace 文章页，前端在渲染后的正文里按引文和上下文重新定位每一处原网页标注。定位成功的，在一个事务里新建为文章标注，同时删除原网页标注；定位失败的留在文章页上，由读者手动重标或丢弃。绑定之后，原网页不能再标注，插件改为只读显示这篇文章当前的标注。插件不在本地保存数据，每次操作直接写服务端，多台电脑之间以最后写入的为准。

当前为 `implemented`，核心测试用例见[网页标注](../../test-cases/extension/web-annotations.md)。本决策是插件领域的根决策。它沿用[摘星标注决策](../web/stars/20261021-annotations-on-articles-and-messages.md)的标注组成、样式与文章锚点坐标系，沿用[文章导入决策](../web/stars/20261020-articles-imported-with-media.md)的文章模型，认证使用 [Access Token 决策](../server/owner/20261018-owner-access-tokens-for-cli-and-services.md)。涉及新增的 `apps/palace-extension`，`palace-db` 的新表与迁移，`palace-domain` 的校验与排序规则，`palace-backend` 的新接口、OpenAPI 和文章列表排序，以及 `apps/palace-web` 文章页的迁移流程与未定位标注的展示。实现与本决策评审稿的差异集中记录在[实现中的调整](#实现中的调整)。对话页、笔记、Firefox 与 Safari、离线标注、自动匹配文章都不在范围内。

## 问题与约束

- 文章是在原网页上第一次读到的。最初的高亮和想法产生在原网页上，而决定把文章导入 Palace，往往发生在读完之后。如果导入后只能在 Palace 里重新标一遍，第一次阅读时留下的东西就丢了。
- Palace 标注的锚点是渲染后文字中的 `[start, end)` 加 `quote`（标注决策 D3）。这个坐标系只在 Palace 前端渲染 `MarkdownContent` 时存在。原网页是另一套文字：有导航、评论和站点模板；块与块之间的空白不同；从 HTML 转成 Markdown 时，个别文字也可能改变。原网页上的位置不能直接换算成 Palace 坐标，两边共有的只有引文本身。
- 服务端只有文章的 Markdown 源码，不知道渲染后的文字，因此无法在服务端算出 Palace 坐标。
- 抓取项目存进 `article.url` 的是原样网址，与读者浏览器地址栏里的地址未必一致，例如可能多带跟踪参数，或者经过跳转。同一篇文章也可能发在多个网址上。只按网址自动匹配会漏掉一部分文章，也可能配错。
- Palace 只有 Eric 一个用户，但会在多台电脑上使用插件。同一处标注不会被两台电脑同时修改。
- Access Token 是 Owner 级凭证，Bearer 请求不做 Origin 校验（Access Token 决策 D3），插件不需要浏览器 Session。

## D1：范围与组成

- 插件是 Manifest V3 的 Chromium 扩展，放在 `apps/palace-extension`，与 `palace-web` 一样用 TypeScript 和 Vite 构建，颜色取自 `design/tokens.css`。定位函数（D5、D6）与 API 类型直接取自 `palace-web`，插件与文章页按同一套规则找引文。
- 插件有三个部分：
  - 在网页上运行的内容脚本，负责选区小条、绘制标注和批注浮层；
  - 后台 service worker，负责持有 token 并调用 Palace API；
  - 一个插件页，列出所有标注过的网页，并提供设置。
- 只处理网页正文中的文字。跨 iframe 的选区、`input`/`textarea` 中的文字、PDF 查看器都不在范围内。

## D2：原网页标注的组成

一个**网页**由地址标识，保存时一并记下标签页标题。一处**原网页标注**属于一个网页：

| 部分 | 规则 |
| --- | --- |
| `quote` | 被选中的文字，去掉两端空白后非空，UTF-8 不超过 16 KiB；取法与 Palace 相同：把选区内的文本节点首尾相接 |
| `prefix` / `suffix` | 页面文字中紧挨在引文前、后的各至多 32 个 UTF-16 码元，可以为空（引文位于页面开头或结尾时） |
| `position` | 引文起点在整个页面文字中的比例，取值 `[0, 1]` |
| 样式与批注 | 与标注决策 D2 相同，至少有一个 |

- 网页地址取 `location.href` 去掉 `#` 及其后的部分，不做其他规范化。规则与 `article.url` 相同：绝对 `http`/`https` 地址，不超过 2048 字节。服务端拒绝带 `#` 的地址而不是替客户端去掉，忘了去掉的客户端不会为同一个地址建出第二个网页。
- 标签页标题在每次新建或修改标注、以及绑定时更新为当前标题。为空时用地址代替；超过 1024 字节（与文章标题的上限相同）时在字符边界截断而不是拒绝：标题由站点决定，读者无从修改。
- 原网页上的显示与 Palace 一致：四种高亮、划线、波浪线和批注样式。

**为什么原网页标注不存位置坐标，而存前后文**：原网页的文字下标只在那一刻的 DOM 里有意义。站点改版、广告位变化，甚至同一页面换一种语言加载，都会平移所有下标，而这些下标本来也无法换算成 Palace 坐标。引文加前后文是 W3C Web Annotation 的 TextQuoteSelector，Hypothesis 等工具就用它在不同版本的文档之间重新定位标注。`position` 存比例而不是下标，因为原网页和 Palace 正文的文字总长相差很大，比例在两边都还能大致对应。

## D3：网页的绑定

网页有两种状态：

| 状态 | 原网页上 | 原网页标注 |
| --- | --- | --- |
| 未绑定 | 显示原网页标注，可以新建、修改、删除 | 全部有效 |
| 已绑定到文章 A | 只读显示文章 A 当前的标注，见 D6 | 只剩迁移时没能定位的几处，只能在 Palace 文章页丢弃，见 D5 |

- **绑定入口**：插件弹窗中的「收进 Palace」，打开候选文章列表（D4）。读者选定后完成绑定，插件随即在新标签页打开这篇文章的 Palace 页面，迁移由此开始（D5）。
- 网页没有标注时也可以绑定。这时插件会新建这个网页的记录，之后在原网页上只读显示这篇文章的标注。
- 已绑定的网页可以改绑到另一篇文章。改绑只改变剩余的原网页标注之后迁往哪里，以及原网页上显示哪篇文章的标注；已经迁移的标注仍属于原来的文章。不提供解除绑定：绑定一旦建立，原网页就不再接受新标注，Palace 文章才是唯一可以修改的地方。
- 多个网页可以绑定到同一篇文章，例如同一篇文章的转载或改版后的新地址。
- 删除文章时，绑定到它的网页及其剩余的原网页标注一起删除。这与「标注随标注对象删除」一致：文章上已经迁移的标注也会被删除，只保留剩余的那几处没有意义。
- 未绑定的网页上最后一处标注被删除时，网页记录在同一事务中删除，插件列表页里不会留下空网页。

**为什么由读者选择文章，而不是按网址自动匹配**：`article.url` 是抓取时的原样地址，与读者浏览时的地址可能只差一个跟踪参数、一次跳转或一个末尾斜杠，但按字节比较就对不上。自动匹配需要一套网址规范化规则，而这套规则无论定得多宽，都会遇到转载、改版换地址这类它处理不了的情况，配错时标注还会悄悄迁进错误的文章。由读者确认只多一次点击，结果确定，而且同时解决了一篇文章对应多个网址的问题。

**为什么绑定后原网页只读**：如果两边都能修改，同一处标注就有两份可以分别修改的副本，需要设计双向同步和冲突处理。只读让 Palace 文章成为唯一可以修改的地方。

## D4：候选文章排序

`GET /api/articles` 增加可选参数 `near=<url>`。带 `near` 时，忽略默认排序，按以下顺序排列：

1. 主机名与 `near` 相同的排在前面。比较前去掉开头的 `www.`，并按小写比较。
2. 同一主机名内，路径按 `/` 切段后，开头相同的段越多越靠前。
3. 其余按导入时间倒序。

- 可以与 `q` 同时使用：先按 `q` 过滤，再按上述规则排序。`total` 和响应形状与摘星根决策 D5 相同，列表项另带原文 `url`，供候选列表区分同名文章。游标编码 `(接近程度, 导入时间, id)`，与按发布日期排序的游标形状不同，不能混用。
- 主机名与路径段按浏览器同样的 URL 解析规则取得，所以接近程度在服务端的 Rust 代码里计算：一次读出符合 `q` 的全部文章的地址与导入时间，排序后只加载当前页的行。一个人的文章数量有限，这一步的代价可以接受；SQL 里用正则拆 URL 会与浏览器的解析出现偏差。
- 插件的候选列表默认带 `near` 请求第一页，搜索框输入时加上 `q`。

**为什么在服务端排序**：列表是分页的，插件只拿得到其中一页，无法对全部文章排序。

## D5：迁移在 Palace 文章页上完成，定位成功的原网页标注与新建的文章标注在一个事务中交换

**定位**：打开文章页时，前端请求 `GET /api/articles/{id}/web-annotations`，得到所有绑定到这篇文章的网页上剩余的原网页标注。如果有，就在 `MarkdownContent` 渲染出的标注文字上逐条定位：

1. **规范化**：引文、前后文和标注文字都删去全部空白字符，并记下删除后每个位置对应的原始下标。删去全部空白而不只是合并空白，是因为 Palace 的标注文字把块与块直接相接，原网页的 DOM 文字则在块之间夹着换行和缩进。
2. **候选**：在规范化后的标注文字中，找出规范化引文的全部完全匹配。
3. **打分**：每个候选按两项打分：它前面的文字与 `prefix` 末尾的公共长度，加上它后面的文字与 `suffix` 开头的公共长度；分数相同时，取起点比例离 `position` 最近的一处。
4. **结果**：如果有候选，取得分最高的一处，换算回原始下标：`start` 是第一个字符的位置，`end` 是最后一个字符之后的位置，`quote` 取标注文字中 `[start, end)` 那一段。没有候选时，这处标注定位失败。不做模糊匹配。

`quote` 取自 Palace 文字而不是原网页，所以新标注满足标注决策 D3 的长度约束。它首尾都是非空白字符，内部空白与 Palace 的显示一致。

**提交**：`POST /api/articles/{id}/web-annotations/migrate`，请求体是 `{ items: [{ web_annotation_id, start, end, quote }] }`，包含所有定位成功的原网页标注。服务端在**一个事务**中：

1. 删除 `items` 中列出的、属于绑定到这篇文章的网页的原网页标注，并取回被删除的行。
2. 只对第 1 步真正删除的行，按标注决策的校验规则新建文章标注。样式与批注取自被删除的行，锚点取自请求；`created_at` 取原网页标注的创建时间。
3. 返回新建的标注。

- 请求中的某一项已经不存在（例如另一个标签页刚迁移过），就跳过这一项，不报错。同一处原网页标注只会变成一处文章标注。
- 任一新标注没有通过校验时，整个事务回滚，返回 400，原网页标注保持原样。
- 原网页标注不属于这篇文章，或者不属于当前 Owner，都按不存在处理，跳过。

**未定位的标注**：文章页 meta 行在「N 处标注」后面显示「M 处原网页标注没对上」。点开后列出每一处的引文、样式和批注，各带一个「丢弃」，调用 `DELETE /api/web-annotations/{id}`。读者可以对照引文，在正文里重新选中文字标注。这些标注不会自动重试定位；文章正文不会变化，换一次也只会得到同样的结果。

**为什么在前端而不是服务端定位**：Palace 坐标系由 `MarkdownContent` 的渲染结果定义，包括开头标题的提升、表格空白的处理、跳过的复制按钮和图片占位（标注决策 D3）。服务端要算出同样的坐标，就得复刻这一整套规则，两边一旦不一致，标注就会悄悄错位。在文章页上定位，用的正是画标注的那份文字，并且只做一次。

**为什么定位成功后删除原网页标注，而不是留作只读记录**：留下的记录需要另设一个只读状态，还需要回收；而原网页上的只读显示会改用文章当前的标注（D6），这份记录不会再被读取。在迁移事务里删除，原网页标注就只有一种状态：有效、可以迁移。

**为什么先删除、再按删除结果新建**：两个标签页可能同时迁移同一批标注。以「这次事务删掉了哪些行」为准，后到的事务删不到任何行，也就不会新建任何标注，两边最终收敛到同一个结果，不需要额外的锁或幂等键。

## D6：已绑定网页的只读显示

- 打开已绑定的网页时，插件请求 `GET /api/articles/{id}/annotations`，按 D5 的规范化方法在页面文字中查找每处标注的 `quote`。引文出现多次时，取起点比例最接近 `start / 文章 Markdown 正文长度` 的一处；找不到就不画。
- 标注用 CSS Custom Highlight API 绘制，不修改网页的 DOM。悬停有批注的标注时，在 shadow DOM 中显示批注，内容只读。
- 选中文字时不再出现标注小条。插件图标上的标记显示「已收进 Palace」，弹窗里有打开文章的链接。

**为什么显示文章当前的标注，而不是迁移前的快照**：迁移后，读者会在 Palace 里修改样式、补写批注、新增标注。显示快照会让原网页与 Palace 逐渐不一致，读者也分不清哪一边是最新的。

**代价**：文章标注只有 `quote` 和 Palace 坐标，没有前后文。同一句话在原网页上出现多次时，只能按比例估计是哪一处，偶尔会画错位置。这只影响只读显示，不影响任何数据。

**为什么用 Custom Highlight API**：它在不改动网页 DOM 的前提下给任意文字范围加样式，支持背景色和下划线、波浪线，不会破坏站点脚本对 DOM 的假设，也不受站点 CSS 影响。Palace 回响页的搜索高亮已经在使用它。

## D7：同步：插件不在本地保存数据，每次操作直接写服务端

- 新建、修改、删除都直接调用接口。修改时整体替换 `style` 和 `note`，服务端按请求到达的先后处理，后到的生效。删除直接删除行，不保留删除标记。
- 插件打开网页时，按地址拉取这个网页的状态和原网页标注；打开列表页时拉取全部网页。
- 连不上 Palace 时，选区小条不出现，插件图标显示「未连接」，不排队、不缓存。

**为什么不支持离线**：离线标注需要本地存储、版本号、删除标记和合并规则，札记的同步就是为此专门设计的。插件的使用场景是在线阅读网页，网页本身就需要联网。只有一个用户，也不会出现并发修改，按服务端到达顺序处理已经足够。

## D8：认证与请求路径

- 插件页的设置里填写 Palace 地址和 Access Token，保存在 `chrome.storage.local`。不用 `chrome.storage.sync`：token 不应经由浏览器厂商的同步服务传播；每台电脑各自生成一个带备注的 token，在密钥管理里可以分别删除。
- 所有 API 请求由后台 service worker 发出，带 `credentials: "omit"`，浏览器里登录 Palace 的会话 cookie 不会代替 token。manifest 的 `host_permissions` 声明 `<all_urls>`，请求不受 CORS 限制，服务端不需要为插件开放 CORS。内容脚本不持有 token，只通过消息请求 service worker 代为调用，且只能读写所在网页的原网页标注；列出网页、搜索候选、绑定和设置只接受插件自己的页面。
- 请求返回 401 时，插件提示 token 无效，并停止在页面上显示小条。

**为什么内容脚本不直接请求**：内容脚本运行在任意网页里，与页面共享 DOM；把 token 留在 service worker 中，网页的脚本就无法读到它。

## D9：存储与接口

新表 `web_page`：

| 列 | 说明 |
| --- | --- |
| `id`、`owner_id` | UUIDv7；`(owner_id, url)` 唯一 |
| `url`、`title` | D2 的规则 |
| `article_id` | 可空；空表示未绑定，非空以 `(owner_id, article_id)` 复合外键引用文章，`ON DELETE CASCADE` 删除网页 |
| `created_at`、`updated_at` | 数据库时钟，毫秒精度 |

新表 `web_annotation`：`id`、`owner_id`，以 `(owner_id, page_id)` 复合外键引用 `web_page`（`ON DELETE CASCADE`），以及 `quote`、`prefix`、`suffix`、`position`、`style`、`note`、`created_at`、`updated_at`。检查约束与 `annotation` 相同：`style` 与 `note` 至少一个非空；此外 `position` 在 `[0, 1]` 之间。

| 方法与路径 | 作用 |
| --- | --- |
| `GET /api/web-pages` | 全部网页：`{ items: [{ id, url, title, article_id, annotation_count, updated_at }] }`，按 `updated_at` 倒序 |
| `GET /api/web-pages/lookup?url=` | `{ page, annotations }`：一个网页及其原网页标注；没有记录时返回 404 |
| `POST /api/web-pages/annotations` | 请求体 `{ url, title, quote, prefix, suffix, position, style, note }`，网页不存在时一并创建；网页已绑定时返回 409 |
| `PUT /api/web-annotations/{id}` | 请求体 `{ title, style, note }`，替换 `style` 与 `note` 并记下标签页标题；所属网页已绑定时返回 409 |
| `DELETE /api/web-annotations/{id}` | 删除；未绑定网页上的最后一处被删除时，网页一起删除 |
| `PUT /api/web-pages/binding` | 请求体 `{ url, title, article_id }`，绑定或改绑，网页不存在时一并创建 |
| `GET /api/articles?near=` | 见 D4 |
| `GET /api/articles/{id}/web-annotations` | 绑定到这篇文章的所有网页上剩余的原网页标注 |
| `POST /api/articles/{id}/web-annotations/migrate` | 见 D5；响应 `{ items }` 是新建的文章标注 |

- 跨 Owner 的网页、原网页标注、文章都与不存在一样返回 404。网页已绑定时的 409 带错误码 `web_page_bound`，插件据此转为只读显示。
- 未绑定网页至少有一处原网页标注（不变量 8）由提交时检查的约束触发器兜底；写入方仍在删除最后一处标注的同一事务中删除网页。对同一网页的新建、修改、删除和绑定都先锁住网页行，彼此串行。
- `GET /api/web-pages` 不分页：网页是读者亲手标注过的，数量有限，与标注列表不分页的理由相同。
- 网页与原网页标注不进入同步域，不分配 `serverVersion`。
- 领域层用枚举表达网页状态（`Unbound`、`Bound(ArticleId)`），数据库用可空外键表达同样的两种状态。

## 不变量

1. 网页与原网页标注只在所属 Owner 的认证上下文中可见、可改；跨 Owner 与不存在都返回 404。
2. 同一 Owner 下，一个网址至多对应一个网页；一个网页至多绑定一篇文章，且两者属于同一 Owner。
3. 已绑定网页上不会新增原网页标注，其上的原网页标注也不会被修改，只能被迁移或删除。
4. 一处原网页标注至多迁移一次：迁移事务中，新建文章标注与删除原网页标注一起提交或一起回滚，同时迁移同一处时只有一个事务新建标注。
5. 迁移产生的文章标注满足标注决策 D3：`quote` 等于正文标注文字中 `[start, end)` 那一段。
6. 定位失败的原网页标注保持不变，直到读者丢弃，或者网页改绑后迁移成功。
7. 删除文章时，绑定到它的网页和剩余的原网页标注在同一事务中删除。
8. 未绑定的网页至少有一处原网页标注。
9. Access Token 只存在于插件的 service worker 与本机存储中，不进入网页上下文。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| 按网址自动把原网页标注挂到同网址的文章 | 无需操作 | 原样网址与浏览地址常常对不上，也处理不了一篇文章对应多个网址；配错时标注会悄悄进入错误的文章，见 D3 |
| 服务端在导入或绑定时，用 Markdown 纯文本定位 | 不打开文章也能完成迁移 | 服务端要复刻 `MarkdownContent` 的坐标规则，任何偏差都会悄悄错位，见 D5 |
| 把 Palace 标注改成前后文选择器，迁移时直接复制数据 | 迁移最简单，原网页只读显示也更准 | 要改动已经实现的锚点模型，每次渲染都要做查找，同一句话多次出现时标注可能漂到别处；标注决策已经否决过这种做法 |
| 迁移后保留原网页标注作为只读快照，定期或在服务启动时回收 | 原网页显示不依赖文章 | 快照与 Palace 逐渐不一致，见 D6；回收时机取决于服务重启频率，回收失败还会影响启动 |
| 绑定后原网页仍可标注，再迁入文章 | 原网页上的体验不中断 | 同一篇文章有两个都能修改的地方，需要双向同步，见 D3 |
| 插件本地存储，以 LWW 合并多台电脑的数据 | 支持离线 | 需要版本号、删除标记和合并规则，对单人在线阅读收益很小，见 D7 |
| 修改原网页 DOM，用 `<mark>` 包裹标注文字 | 兼容更老的浏览器 | 与站点脚本争夺 DOM，会被站点 CSS 影响，还可能破坏页面行为，见 D6 |
| token 存在 `chrome.storage.sync`，多台电脑自动共享 | 只需配置一次 | token 经由浏览器厂商同步；无法按电脑分别删除，见 D8 |

## 风险与为什么不能直接改写

- **定位失败率**：HTML 转 Markdown 时，如果改写了文字（引号样式、连字符、脚注编号、被丢弃的图注），涉及这些文字的引文就无法完全匹配，会留给读者手动处理。先不做模糊匹配，因为模糊匹配可能悄悄标到相似但错误的句子上；等实际的失败比例出来，再决定是否加入字符归一化（例如统一引号）。
- **迁移不可撤销**：迁移删除原网页标注。如果绑定到了错误的文章，引文对不上的会留下来，碰巧对上的已经进入错误的文章，只能在那篇文章里手动删除。绑定前的候选列表需要显示标题、作者和网址，帮助读者选对。
- **Palace 渲染规则变化**：与标注决策的风险相同。迁移完成后，标注就是普通的文章标注，渲染规则变化时按标注决策的方式处理。
- **站点文字中的空白**：规范化删去全部空白，英文中「foo bar」和「foobar」会被视为相同。由于引文通常较长，又有前后文打分，误判的概率很低。

## 本决策未解决的问题

- **对话页**：对话从 ChatGPT 等站点导入，原页面的结构与消息坐标都不同，另行决定。
- **Firefox 与 Safari**：Manifest V3 的差异与 Highlight API 的支持情况需要单独评估。
- **模糊匹配与字符归一化**：等有了实际的定位失败数据再决定。
- **在 Palace 里浏览未绑定的网页标注**：目前只在插件页里列出。

## 实现中的调整

以下几处与评审稿不同，正文已按实现改写：

- **D2、D9：修改标注时也带标签页标题。** D2 要求修改标注时更新标题，评审稿 D9 的 `PUT` 请求体却只有 `style` 与 `note`，所以请求体加上 `title`。
- **D4：接近程度在 Rust 中计算。** 理由见 D4；列表项增加 `url` 字段，摘星列表不使用它。
- **D8：`host_permissions` 声明 `<all_urls>` 而不是 Palace 地址。** Palace 地址由读者在设置里填写，安装时写不进 manifest；内容脚本本来就要在所有网页上运行，安装时的权限提示相同。
- **D9：迁移只用一条语句。** 「删除并取回、按删除结果新建」写成一条带数据修改 CTE 的语句，原子性由语句本身保证，不需要显式事务。
