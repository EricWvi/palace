# 插件的标注默认关闭，由读者在弹窗里为单个标签页开启；Palace 自己的页面不能开启

插件不再在每个打开的网页上自动工作。默认情况下，插件既不出现选区小条，也不显示未绑定网页的原网页标注或已绑定网页的只读标注，也不向 Palace 发出任何请求。读者在插件弹窗里点「在这个标签页开启标注」后，这个标签页才开始显示原网页标注或只读标注，并接受新标注；之后在这个标签页里换网页、刷新都保持开启，直到读者在弹窗里「关闭标注」，或者关掉标签页、退出浏览器。Palace 自己的页面任何时候都不能开启。

当前为 `implemented`，核心测试用例见[网页标注](../../test-cases/extension/web-annotations.md#annotating-must-stay-off-until-turned-on-for-the-tab)。本决策基于[浏览器插件在原网页上标注](0-web-page-annotations-bound-and-migrated-into-articles.md)，只改变插件在什么时候工作，不改变标注、绑定、迁移、服务端接口和存储。涉及 `apps/palace-extension` 的内容脚本、service worker 与弹窗。

## 问题与约束

- 按根决策 D7，内容脚本在每个 http/https 网页加载后都按地址查询一次 Palace。读者浏览的绝大多数网页从来不会标注，这些请求却把完整的浏览记录送进了 Palace 的请求日志，浏览器启动、恢复大量标签页时还会同时发出一批请求。
- 原网页标注是少数网页上的少数时刻：读者读到一篇值得留下想法的文章时，才需要插件。
- 插件在 Palace 自己的文章页上也会运行。那里 Palace 有自己的标注小条，插件的小条会叠在上面，插件还会把 Palace 页面当作普通网页去查询原网页标注。
- 工具栏图标的亮暗切换依赖每个网页里的脚本报告 `prefers-color-scheme`，这一点要保留。

## 继承与修改

| 前序约定 | 本决定 |
| --- | --- |
| 根决策 D1：插件由内容脚本、service worker 和插件页组成 | 继承；内容脚本仍随 manifest 注入每个网页，但默认不做任何事，见 D1 |
| 根决策 D3、D6：未绑定网页显示原网页标注并可标注，已绑定网页只读显示文章标注 | 继承，不变；只在开启了标注的标签页里生效，见 D1 |
| 根决策 D7：插件打开网页时，按地址拉取这个网页的状态和原网页标注 | 修改：只在开启了标注的标签页里拉取，关闭时什么都不请求，见 D1 |
| 根决策 D8：内容脚本只能读写所在网页的原网页标注 | 继承，不变；开关的状态由 service worker 回答，见 D2 |
| 根决策 D9：服务端接口与存储 | 继承，不变 |

## D1：标注默认关闭，按标签页开启

- 标注是**标签页**的开关，有「开」和「关」两种状态，默认是关。
- **关**的标签页里，内容脚本不查询 Palace，不出现选区小条，不绘制任何标注，不往网页 DOM 里加节点。它只报告浏览器的亮暗外观，并在加载时向 service worker 询问自己所在的标签页是否开启。
- 读者在插件弹窗里点「在这个标签页开启标注」后，这个标签页立即按根决策 D3、D6 工作：查询网页状态，显示原网页标注或只读标注，未绑定时接受新标注。弹窗随即显示这个网页的状态，以及「收进 Palace」或「改绑到另一篇」。
- 开启后，这个标签页里换网页、刷新、前进后退都保持开启。新开的标签页，即使是从这个标签页里打开的，也从关开始。
- 读者在弹窗里点「关闭标注」，或者关掉标签页、退出浏览器，标签页回到关：已画的标注立即消失，小条与批注收起，工具栏图标上的标记清除。
- 关的标签页打开弹窗时，弹窗只显示开启的按钮，不向 Palace 发请求。
- 插件加载之前就已经打开的标签页里没有内容脚本，开启后弹窗提示刷新网页。

**为什么按标签页，而不是按网页或按站点**：读一篇文章时常常要在同一个标签页里翻页、跳到参考链接再回来，按网页开启就得一页页重新打开。按站点开启会让这个站点上的每个网页都重新开始自动查询，回到本决策要解决的问题。标签页的范围与「我现在要在这里读、在这里标」的意图一致，关掉标签页时自然结束。

**为什么开启状态放在 `chrome.storage.session`**：service worker 随时可能被浏览器挂起，内存里的状态会丢失；`chrome.storage.session` 在 service worker 重启后仍在，退出浏览器时清空，标签页编号也只在一次浏览器会话内有效。它默认只对插件自己的页面开放，所以内容脚本通过 service worker 询问自己的标签页，网页里的脚本读不到其他标签页的开关。

## D2：Palace 自己的页面不能开启

- 网页与插件设置中的 Palace 地址同源（协议、主机名、端口都相同）时，弹窗显示「这是 Palace 本身，请用 Palace 自己的标注。」，不提供开启按钮。
- 已开启的标签页导航到 Palace 页面时，service worker 对这个网页回答「关」，内容脚本保持不动；离开 Palace 回到其他网页后，标签页按原来的开启状态继续工作。
- 判断在 service worker 回答开关时进行，用的是发出询问的网页地址，所以弹窗和内容脚本使用同一条规则。

**为什么按同源判断**：Palace 地址是读者在设置里填写的唯一来源。同一主机名的其他端口、子域名可能是别的服务，不应被排除；反过来，只比较主机名会把同一台机器上的其他站点一起屏蔽。

## 不变量

1. 没有开启标注的标签页里，插件不向 Palace 发出任何请求，不绘制任何标注，不向网页 DOM 添加节点。
2. 标注的开启状态只属于一个标签页，在这个标签页内跨导航与刷新保持，关闭标签页或退出浏览器后消失。
3. Palace 自己的页面上，插件的标注始终处于关闭状态。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| 去掉 manifest 里的内容脚本，开启时用 `chrome.scripting.executeScript` 注入 | 关的网页里完全没有插件代码 | 需要新增 `scripting` 权限；每次导航后都要由 service worker 监听标签页更新、重新注入；工具栏图标的亮暗报告没有了运行的地方 |
| service worker 缓存「有标注或已绑定的地址」，只对命中的网页查询 | 打开有标注的网页时自动显示 | 仍要先拉取全部地址；多台电脑之间有同步延迟；读者的浏览记录仍会与这份列表逐一比对 |
| 选中文字、要标注时才查询 | 无需开关 | 打开网页时看不到已有标注；已绑定网页的只读显示无从触发 |
| 按站点开启，记住开启过的站点 | 常读的站点只需开启一次 | 这个站点上的每个网页又回到自动查询；开启状态要长期保存，还需要另一个管理界面 |
