# 卡片菜单统一更新 Conversation 标题与来源

会话收藏页的卡片菜单增加“编辑会话”操作，通过预填当前值的对话框更新 Conversation 标题和来源。来源编辑用于纠正导入时选错的来源网站，并原子更新该 Conversation 的全部 Path；标题和来源以外的消息树、Session ID、发生时间及 Palace 内部 ID 均保持不变。

当前为 `approved`，Web 端交互、来源身份变更、冲突处理和更新后的可见性已经确认，尚未实现。现有服务端只支持标题更新，本决策将其替换为统一的 Conversation 可编辑元数据更新，不保留仅更新标题的兼容接口。本决策需要调整持久化约束，但不迁移已有数据，也不扩展消息树同步协议；对应核心测试用例已记录验证义务，证据随实现补齐。

## 术语边界

界面沿用导入表单中的“消息来源”文案，但领域模型中的规范概念是 Conversation 的“来源”。单条 Message 不新增来源字段；一个 Conversation 及其全部 Path 始终属于同一个来源网站。

## 继承与修改

| 前序决策约定 | 本次决定 |
| --- | --- |
| Conversation 是主页面的一张卡片，标题属于可编辑显示信息 | 继承；卡片菜单提供标题编辑入口 |
| 一个 Conversation 的全部 Path 属于同一来源 | 继承；来源纠错必须覆盖全部 Path，不能逐条修改 |
| `(owner_id, source, session_id)` 唯一定位一个 Path | 修改：来源纠错会改变外部来源身份，但保留 Palace Path ID 和 Session ID；新组合仍须唯一 |
| Path 更新不改变 Path 身份 | 修改：普通追加更新仍不改变身份，用户显式纠正来源是唯一例外 |
| 原始链接由 Conversation 来源与 Path Session ID 生成 | 继承；来源更新后全部 Path 的链接立即按新模板生成 |
| 卡片按所有 Path 中最大的 `occurred_at` 排序 | 继承；元数据编辑不改变发生时间或列表顺序 |
| 卡片菜单包含“分支管理”和“删除对话” | 修改；在两者之间增加“编辑会话” |

## D1：编辑会话是卡片菜单中的独立操作

用户在会话收藏页打开卡片菜单后，可以选择“编辑会话”。该操作打开对话框，不把输入控件嵌入整张可导航卡片，也不复用分支管理弹窗。这样可以保持卡片主体继续承担打开详情的职责，并避免键盘输入、保存按钮与卡片导航产生冲突。

菜单顺序为“分支管理”“编辑会话”“删除对话”。编辑与删除是不同操作：编辑过程不展示删除警告，删除过程也不提供元数据修改能力。

本次只规定会话收藏页现有卡片菜单中的入口。详情页是否提供相同操作属于后续界面决策；无论入口位于何处，都必须调用同一个 Conversation 元数据更新能力。

## D2：对话框同时编辑标题与来源

对话框打开时，分别以当前 Conversation 标题和来源预填“会话标题”输入框与“消息来源”选择框。来源只能选择 `chatgpt`、`gemini` 或 `grok`，界面展示对应产品名称。用户可以只修改其中一项，也可以一次修改两项；保存时始终提交两项完整值，使一次操作只有一个成功或失败结果。

用户取消或关闭对话框时不发送更新请求。每次重新打开都从当前服务端可见值开始，不能恢复上一次已取消或失败后又关闭的草稿。

标题沿用现有领域规则：去除首尾空白后非空，UTF-8 编码不超过 1024 字节。系统不静默改写用户输入；合法标题中的首尾空白按原值保存和显示。前端可以提前阻止纯空白输入，但服务端仍是标题与来源完整校验的最终边界。

## D3：来源纠错原子更新整棵 Conversation

来源是 Conversation 与全部 Path 的共同约束。将来源从 `chatgpt` 改为 `gemini` 时，服务端必须在同一事务中更新 Conversation 及其全部 Path 的 source；不能出现 Conversation 已更新而部分 Path 仍保留旧来源的中间或最终状态。

更新前必须用每条现有 Path 的 Session ID 检查目标来源身份。若 Owner Scope 内任一 `(new_source, session_id)` 已被其他 Conversation 的 Path 占用，整次标题与来源更新以冲突失败，不修改任何记录。属于当前 Conversation 的 Path 共同迁移，不与自身冲突。

来源更新保留 Conversation ID、Path ID、Session ID、消息父链、Path head、消息数和全部时间字段。所有原始链接在读取时使用新来源的受控模板与原 Session ID 重新生成。Palace 不访问来源网站验证链接是否存在；用户确认来源选择即是本次纠错依据。

既有 Import 是已发生操作的凭据，其输入摘要和结果不因来源纠错而改写。相同 idempotency key 的历史重试仍返回原结果，不能把 Conversation 来源改回旧值；纠错后的新导入和 Path 更新则按当前来源身份执行匹配。

## D4：统一替换可编辑元数据接口

服务端提供 `PUT /api/conversations/{id}`，请求体为 `{ "title": string, "source": "chatgpt" | "gemini" | "grok" }`，原子替换 Conversation 的全部可编辑元数据，并返回更新后的 `{ "id", "title", "source" }`。现有 `PUT /api/conversations/{id}/title` 被移除，Web 端调用方同步迁移，不增加兼容转发层。

服务端按当前 Owner Scope 与 Conversation ID 定位记录。不存在或不属于当前 Owner 的 Conversation 均不得被更新，也不能通过成功、冲突或错误响应泄露其他 Owner 的标题、来源或 Session ID。请求体不能借此修改 Owner、Path ID、Session ID、消息父链或导入记录。

多个客户端提交时，每个成功请求原子替换标题与来源，后提交并成功提交事务的请求成为当前值；本次不引入字段合并、编辑锁或版本比较。跨端结构同步仍未开放，因此元数据更新只承诺当前服务端记录及其 Web 投影的一致性。

## D5：保存结果必须在全部元数据投影中一致可见

保存期间禁用重复提交。服务端成功后关闭对话框，并使会话列表、搜索使用的标题与来源文本、来源图标、卡片菜单的无障碍名称、已缓存的 Conversation 详情以及各 Path 的原始链接观察到新值。实现可以直接更新缓存或使相关查询失效，但不能要求用户刷新页面，也不能让列表、详情和链接长期使用不同元数据。

元数据更新不刷新 Path 的 `updated_at` 或 `occurred_at`，不改变默认 Path，也不移动卡片顺序。若新标题或来源不再匹配当前搜索条件，该卡片应按现有搜索规则从过滤结果中消失。

请求失败时保留对话框和用户已输入的标题、来源，展示可理解的校验或 Session 冲突错误并允许重试。失败不得先行修改其他投影；如果采用乐观更新，必须在失败时完整恢复旧标题、旧来源及旧链接。

## 为什么不是其他方案

| 替代方案 | 优势 | 本次取舍 |
| --- | --- | --- |
| 点击卡片字段后原位编辑 | 操作步骤更少 | 字段位于可导航卡片内部，输入、提交和卡片跳转的交互边界容易冲突，键盘与触屏行为也更难保持一致 |
| 在分支管理中编辑来源 | 可以直接看到每条 Path | 来源属于整棵 Conversation，不是单条 Path 的可选属性；逐 Path 修改会产生一棵树包含多个来源的非法状态 |
| 标题与来源使用两个接口分别保存 | 单个请求体更小 | 同一次编辑可能只成功一半，界面难以说明和恢复；统一替换可让校验、冲突和缓存刷新共享一个原子结果 |
| 重新导入以纠正来源 | 无需元数据更新能力 | 导入承担消息和 Path 写入，错误来源下的身份已经存在；重新导入会创建或匹配另一份记录，不能纠正原 Conversation |
| 删除后按正确来源重新导入 | 复用已有流程 | 会更换 Palace ID、丢失整棵树的 Path 组织和既有引用，而且要求用户重新提供所有历史内容 |
| 只修改 Conversation.source | 数据库写入较少 | Path 承担 `(source, session_id)` 外部身份并参与原始链接生成，只改 Conversation 会破坏共同来源不变量 |

## 不变量

1. 标题与来源编辑只作用于当前 Owner 的 Conversation。
2. 一个 Conversation 及其全部 Path 始终拥有相同来源。
3. Owner Scope 内 `(source, session_id)` 始终唯一；冲突时整次更新不产生任何修改。
4. 来源纠错保留 Conversation、Path 和 Message 的 Palace ID 以及所有 Session ID。
5. 元数据编辑不改变消息树、默认 Path、发生时间或卡片排序。
6. 保存成功后，当前 Web 会话中的标题、来源和原始链接投影最终来自同一份新元数据。
7. 保存失败时，服务端记录和已提交的界面状态保持旧值，用户输入可在对话框中重试。
8. 纯空白或超过 1024 UTF-8 字节的标题以及规范枚举外的来源不能写入。

## 风险与持久化约束

当前数据库通过 Conversation 与 Path 上重复保存的 source 以及复合外键保证共同来源，直接先更新任一侧都会暂时违反约束。落地时必须调整约束，使一次事务能够级联或延迟校验整棵 Conversation 的来源更新；不能通过删除并重建 Path 绕过约束，因为那会更换身份并影响 Import 引用。

来源是 Path 外部身份的一部分，纠错后旧 `(source, session_id)` 被释放，未来导入可以再次使用它；新组合则立即参与唯一性检查。这个变化是用户显式纠错的结果，不能由标题编辑、普通追加导入或模板配置变化隐式触发。

## 本决策未解决的问题

- 详情页、移动端及其他内容视图是否提供元数据编辑入口：这些界面尚未形成统一 action 布局。
- 标题或来源修改历史、撤销与审计：当前产品只保存最新值，没有提出历史追踪需求。
- 单个 Conversation 包含不同来源 Path：现有模型明确禁止，若未来要合并跨站对话树，需要单独重定义来源归属和链接语义。
- 元数据跨端同步与并发冲突提示：Conversation/Message/Path 的结构同步协议尚未开放，不能只为两个字段提前定义局部协议。

## 落地顺序

1. 调整数据库约束与服务端领域操作，使标题及整棵 Conversation 来源能够在一个事务内更新；以冲突测试证明不会产生部分更新、跨 Owner 修改或重复来源身份。
2. 用统一元数据接口替换仅标题接口，并验证合法来源、标题边界、历史 Import 凭据和更新后的原始链接。
3. 在卡片菜单加入“编辑会话”及预填对话框，完成取消、客户端空白校验、提交中状态、冲突说明和错误重试。
4. 在成功后统一列表与详情缓存；验收无需刷新即可看到新标题、来源和原始链接，搜索结果和菜单无障碍名称随之更新。
5. 按对应核心测试用例补齐证据：组件交互测试覆盖对话框状态和失败重试，真实 PostgreSQL 测试覆盖事务与唯一性，浏览器测试覆盖菜单入口、持久化结果及刷新后的元数据。

整个落地过程不改变现有消息正文、树结构、Session ID、Path 管理、删除行为和卡片排序。
