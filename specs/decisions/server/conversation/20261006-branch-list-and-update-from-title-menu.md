# 分支管理改为分支列表，标题菜单直接提供“更新分支”

阅读页标题菜单依次为“更新分支”“管理分支”“编辑对话”“删除对话”。“更新分支”直接打开当前 Path 的追加更新对话框，与分支管理里某一行的“更新”是同一个表单；原“分支管理”更名为“管理分支”，弹窗不再画只投影 user 节点的对话树，改为每条 Path 一行的列表，每行显示标题、Session ID 与消息数，并提供“更新”“删除”。前端随之移除 React Flow 与 Dagre 依赖，服务端接口不变。

当前为 `implemented`，核心测试用例见[对话阅读页](../../../test-cases/server/conversation/reading-page.md)与[Conversation 树与 Session Path](../../../test-cases/server/conversation/message-tree.md)。继承[标题从 Conversation 移到 Path](20261005-title-belongs-to-path.md)的全部决策；修改[对话在摘星阅读页阅读与管理](20261004-reading-page-owns-conversation-actions.md) D3 的菜单项、[Conversation 承载树，Path 承载来源 Session](20260919-conversation-tree-and-session-paths.md) D3 的树状管理，以及[从时刻页日期菜单导入对话](../import/20261004-import-from-day-menu-and-open-reading-page.md)不变量 1 中“更新只能从分支管理发起”的入口限制。

## 继承与修改

| 前序约定 | 本决定 |
| --- | --- |
| 标题菜单依次为“编辑对话”“分支管理”“删除对话”（阅读页决策 D3） | 修改：依次为“更新分支”“管理分支”“编辑对话”“删除对话”，见 D1 |
| 分支管理弹窗隐藏 assistant，user 节点连接最近的 user 祖先，Path 末端映射到最后一个 user 节点（树决策 D3） | 修改：改为 Path 列表，见 D2 |
| 同一末端的多个 Path 分别提供更新、删除；只有 assistant 的 Path 不被隐藏（树决策 D3） | 继承：列表本来就一行一条 Path，这两点无需特殊区域 |
| 分支与更新只能从阅读页的分支管理发起（导入入口决策不变量 1） | 修改：更新还可以从标题菜单发起，仍只在阅读页，见 D1 |
| 更新回填该 Path 的标题与 `occurred_at`，Session ID 不可修改；成功后切到本次 Path 并改返回日期 | 继承，不变；两个入口共用 |
| 只剩一个 Path 时不提供删除 Path，最后一个 Path 通过“删除对话”删除 | 继承，不变 |
| 删除 Path 的事务语义与删除后阅读页的落点（阅读页决策 D5） | 继承，不变 |

## D1：标题菜单直接更新正在阅读的 Path

菜单从常用到不可撤销排列：

| 菜单项 | 行为 |
| --- | --- |
| 更新分支 | 打开当前 Path 的追加更新对话框 |
| 管理分支 | 打开分支列表，见 D2 |
| 编辑对话 | 不变：标题只改当前 Path，来源改整个 Conversation |
| 删除对话 | 不变：确认后删除整个 Conversation |

追加更新是回到一段对话时最常做的事：来源网站上的对话又续写了几轮，需要把完整 JSON 重新导入。被续写的几乎总是正在阅读的那一支，原来要先打开分支管理、再在树上找到它所在的节点，多了一步还要认节点。菜单项直接作用于当前 Path，表单、校验、幂等与成功落点都与分支管理里的“更新”相同，不形成第二套行为。

“分支管理”改称“管理分支”，与“更新分支”“编辑对话”“删除对话”同为动宾结构。

## D2：管理分支是一张 Path 列表

弹窗每行对应一条 Path，顺序与阅读页的默认 Path 规则一致（`updated_at DESC, id DESC`），阅读页默认打开的那一支排在第一行。每行显示：

- Path 标题，单行省略；
- Session ID 与消息数，作为次要信息。新分支默认沿用发起时所读 Path 的标题，同名分支常见，Session ID 是区分它们的唯一稳定依据；
- “更新”与“删除”两个文字按钮。只剩一条 Path 时“删除”禁用，指针移到它上面时变为帮助光标并提示通过“删除对话”移除，提示不常驻。

列表上方一行左侧显示分支数，右侧是“新建分支”文字按钮。新建作用于整个列表，不属于任何一行；放在列表上方，分支多时也不必滚到底才找到它。弹窗不再有说明文字。

为什么放弃树：树的价值是展示分支从哪条消息分开，但这在阅读页已经由分叉句（“此处分为 K 支：…”）在原位表达，读者在正文里看到分叉才知道分支的意义。管理分支时要做的只是找到某一支并更新或删除它，而读者记住一支的方式是它的标题，不是它最后一条 user 消息的摘要。树图还带来画布拖动、缩放、节点悬停才显示操作等额外交互，以及 React Flow 与 Dagre 两个依赖，与 Web 端“少 UI、以文字为主”的原则相悖。

## 不变量

1. 标题菜单的四项及其顺序固定为“更新分支”“管理分支”“编辑对话”“删除对话”。
2. “更新分支”与分支列表里的“更新”打开同一个表单：回填该 Path 的标题与 `occurred_at`，Session ID 不可修改，成功后的落点相同。
3. 分支列表恰好列出 Conversation 的每条 Path 各一次，顺序与阅读页默认 Path 规则一致；每行的更新、删除只作用于该 Path。
4. 新建分支只能从分支列表发起，更新只能从阅读页（标题菜单或分支列表）发起。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| 保留树图，只在菜单加“更新分支” | 改动最小，仍能看到分支结构 | 结构已由正文里的分叉句表达；树图的交互和两个依赖只服务于找到一行，代价不成比例 |
| 列表按树的先序排列，并缩进表示层级 | 列表里仍有结构 | 缩进只能表达 user 节点间的父子关系，Path 结束在内部节点或多个 Path 同一末端时仍需特殊说明，又回到树的复杂度 |
| 列表行只显示标题 | 最简洁 | 新分支默认同名，只看标题无法区分要更新或删除的是哪一支 |
| “更新分支”在菜单里先选择要更新的 Path | 可以更新任意一支 | 那就是分支列表本身；菜单项的意义正是省掉选择 |

## 落地与验收

`ConversationMenu` 承载四项菜单与“更新分支”打开的 `ImportDialog`；`BranchManager` 渲染 Path 列表，原 `BranchGraph`、`layoutBranches` 与 `userTree` 投影删除，`@xyflow/react`、`@dagrejs/dagre` 从依赖中移除。

组件测试覆盖菜单顺序、从菜单更新当前 Path 后的请求与落点、列表的行集合与顺序及每行操作；Chromium 测试覆盖菜单顺序、列表顺序、窄屏不出现横向滚动，以及从列表更新一支后的请求与落点。
