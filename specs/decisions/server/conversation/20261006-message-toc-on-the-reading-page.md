# 阅读页右侧加消息目录，每条消息一行由服务端截取的开头

阅读页右边缘固定一列短横线，当前 Path 的每条消息对应一条。指针移到横线上或用键盘进入时，原位展开一个浮层，每条消息显示一行开头文字，超出部分以省略号截断，点击跳到该消息。这行文字由服务端生成：对话详情与 Path 接口的每条消息新增 `toc_line` 字段，取消息 Markdown 开头的一小段，用 pulldown-cmark 去掉标记后截短；它不落库，每次读取时生成。

当前为 `implemented`，核心测试用例见[对话阅读页](../../../test-cases/server/conversation/reading-page.md#the-message-toc-must-list-every-message-of-the-current-path-by-its-opening)。继承[对话在摘星阅读页阅读与管理](20261004-reading-page-owns-conversation-actions.md)的页首、正文与分叉规则，只在其旁边增加目录；纯文本化沿用[对话 Moment 卡片字段](../moment/20261004-conversation-moment-card-fields.md) D3 的摘录规则。视觉参照为 `design/2.1-moment-conversation.html`。

## 继承与修改

| 前序约定 | 本决定 |
| --- | --- |
| 阅读页始终展示一个真实 Path，切换分支只替换地址里的 `path` | 继承：目录只列当前 Path 的消息，随分支切换而变；跳转不改地址、不增历史记录 |
| 摘录去掉 Markdown、原始 HTML 与多余空白，按 Unicode 标量截断并以“…”收尾 | 继承：目录行用同一套纯文本化与截断规则，只是更短，见 D2 |
| 消息接口返回 `content` 等持久化字段 | 修改：每条消息另带派生字段 `toc_line`，见 D2 |

## D1：目录是右边缘的一列横线，指向时展开成逐条一行

- 横线自上而下对应当前 Path 的消息；user 消息的横线较长，assistant 较短，与正文中 user 消息带底色的区分一致。
- 正在读的消息的横线为实色。正在读的是顶部最后越过窗口上方三分之一处的那条；滚到底时是最后一条。
- 指针移到横线上，或键盘焦点进入目录，展开浮层。每条消息一行，单行省略；当前一条带底色，展开时浮层滚到它所在的位置。指针离开后稍作延迟再关闭，滑出边缘时不至于立即消失。
- 点击一行平滑滚到该消息（读者要求减少动效时直接跳），并把它标为当前，直到读者自己滚动（滚轮、触摸滑动或按键）。页面接近底部时，短消息到不了三分之一处，按滚动位置推算会标到下一条，固定标记避免读者点了一条却看到另一条亮起。
- 用指针点击不在行上留下焦点，否则焦点会让浮层在指针离开后仍然展开；用键盘按 Enter 跳转则焦点留在行上，浮层保持展开，便于继续选择。
- 窗口宽度不足 900px 时不显示：760px 的正文两侧放不下横线，窄屏上它会盖住正文。只有一条消息的 Path 也不显示，此时目录不提供正文之外的信息。

## D2：目录行由服务端从消息开头截取

消息接口（`GET /api/conversations/{id}` 与 `GET /api/conversations/{id}/paths/{path_id}`）的每条消息新增 `toc_line`：取 `content` 开头 256 字节（截点落在多字节字符中间时退到该字符之前），再按摘录的规则转成纯文本，最多保留 48 个字符，被截断时以“…”收尾。空消息的 `toc_line` 为空字符串，界面显示“（空消息）”。

为什么由服务端生成：Web 端阅读页虽然拿到了完整 `content`，但把 Markdown 变成一行纯文本的规则已经在服务端实现，并用于时间线摘录。两处各写一套，表格、代码、原始 HTML 的处理会逐渐分叉，同一条消息在卡片和目录里显示的开头不一样。字段跟着消息走，也让以后的其他客户端直接可用。

为什么先截一段再解析：目录每次读取都要为整个 Conversation 的每条消息生成一行，而一条回答可能有几十 KB；一行 48 个字符只需要开头。48 个汉字约 150 字节，256 字节为周围的标记留出余量。

截点不理会 Markdown 结构：落在链接或强调中间时，未闭合的部分（如 `[文字](https://…`）会以字面量出现在行尾。只有开头大部分是不可见内容（例如很长的链接地址）、可见文字不足 48 个时，这些字面量才会进入目录行，而且几乎总落在浮层的省略号之后。退回到截点前最后一个换行可以避免它，却会把常见的“好的！”加一段长正文的开头缩成“好的！”两个字，丢掉真正有信息量的那句话。

48 个字符足以填满浮层最宽的一行：浮层宽 260px，中文约 17 字，英文约 35 字，超出部分本来就被省略号截掉，完整的行在悬停时作为提示显示。

## 不变量

1. 目录恰好列出当前 Path 的每条消息各一次，顺序与正文一致；切换分支后随之更新。
2. 每条消息的 `toc_line` 与 `content` 同源派生，不单独存储；同一 `content` 总得到同一行。
3. `toc_line` 只由 `content` 开头 256 字节派生，不含原始 HTML，长度不超过 48 个 Unicode 标量（另加截断时的“…”）；闭合的 Markdown 标记不出现在其中。
4. 点击目录跳到对应消息，并标记这一条为当前，直到读者自行滚动；跳转不修改地址和历史记录。
5. 用指针点击后，指针离开目录时浮层关闭。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| 前端从 `content` 自行截取 | 不改接口 | 与时间线摘录形成两套纯文本规则，同一消息在两处显示不同；其他客户端还要再写一遍 |
| 解析整条消息再截短 | 截点永远不会落在标记中间 | 每次读取要解析整个 Conversation 的全部正文，长回答的成本只换来几十个字符 |
| 截点退回到最后一个换行 | 截点不落在行内标记中间 | 短开场加长段落的回答只剩开场两个字；它要避免的字面量本来就几乎总在省略号之后 |
| 只列 user 消息 | 目录更短，像章节标题 | 回答往往比问题更值得回找；ChatGPT 的目录也逐条列出，读者已经熟悉 |
| 当前项始终按滚动位置推算 | 规则单一 | 接近底部的短消息到不了推算线，点了一条却亮起另一条 |
| 窄屏改成底部抽屉 | 手机上也能跳转 | 需要另一套入口与手势；手机上滚动本身足够快，目前不值得 |

## 落地与验收

`palace_domain::toc_line` 与 `excerpt` 共用纯文本化和截断；消息 DTO 在转换时填入 `toc_line`，OpenAPI 与前端类型随之重新生成。`MessageToc` 渲染横线与浮层，阅读页给每条消息加锚点 `message-<id>`。

单元测试覆盖目录行的纯文本化、截断和只解析开头；组件测试覆盖目录行来自 `toc_line`、随分支切换、跳转后的固定与解除以及点击不留焦点；Chromium 测试覆盖滚动时标记移动、接近底部跳转后标记不偏移、指针离开后浮层关闭，以及窄屏不显示。
