# 从用户提交开始原子导入一条线性对话路径

Palace 的系统边界从用户提交标题、来源网站、`session_id` 和对话历史开始；从 ChatGPT、Gemini 或 Grok 页面提取和导出数据不属于 Palace。文本框与 JSON 文件共用同一解析、校验与事务流程，一次成功导入记录一条 Path，失败不留下 Conversation、Message 或导入状态的部分结果。

当前为 `implemented`，服务端契约已实现并验证；核心测试用例分别记录直接证据及仍属于展示端、设备交互或导出的后续验证边界。本文件是所属领域的根决策，没有前序 ADR。第一版建立新导入契约，不承担既有生产数据、浏览器自动化或来源网站导出格式的兼容义务。

## 范围与依赖

拥有 `conversation_import` 表及导入应用流程，写入[来源会话与消息树](../conversation/0-source-session-and-message-tree.md)拥有的 Conversation、Message，并遵守[Owner 与数据隔离](../owner/0-authelia-identity-and-owner-scoped-records.md)。未来客户端重试与服务端分发遵循[客户端时间戳 LWW 与全局序列同步](../sync/0-client-timestamp-lww-and-global-seq.md)。浏览器工作流、扩展和 Web Chat DOM 适配位于系统边界之外。

## 问题与约束

用户可以粘贴 JSON 文本或上传 JSON 文件，两种入口不能产生不同的兼容性和错误语义。来源导出对象可能包含 `turnId`、`turnNumber` 等额外字段，也可能只包含 `role`、`content`；第一版只承诺一个跨来源最小格式。

JSON 数组只能表达一条线性消息序列，不能直接携带完整分叉树。重复导入同一来源会话时可以识别共享的完全相同前缀，但在没有来源消息 ID 的情况下，无法区分同一父节点下内容完全相同的两次独立生成。

## D1：粘贴与文件上传使用同一输入契约

一次请求包含用户填写的非空 `title`、规范 `source`、非空 `session_id`，以及由文本框内容或上传文件提供的一份 JSON。文件上传只改变字节获取方式；读取为文本后进入同一解析器，不能另设宽松字段、默认角色或内容转换。

对话历史采用按提交顺序排列的线性消息数组，每个元素只读取 role 与 content。

顶层必须是非空数组。每个元素必须是对象，`role` 必须严格为 `user` 或 `assistant`，`content` 必须是字符串；额外字段忽略且不持久化。空字符串仍是字符串，不由解析器擅自删除；是否提示无可见内容属于交互策略。

解析器不要求角色交替，不自动补 assistant，不合并连续同角色消息，也不按空白、标点或 Markdown 结构拆分消息。`content` 原样保存，不 trim、不统一换行、不渲染后回写。

## D2：导出与来源页面读取位于系统边界之外

Palace 不安装或运行 ChatGPT、Gemini、Grok 的网页抓取逻辑，不承诺来源 DOM、复制按钮、滚动加载、分支选择和附件导出行为。用户或外部工具负责在提交前取得符合契约的 JSON；Palace 从接收请求开始负责大小限制、解析、校验、持久化和结果返回。

来源网站模板链接只用于用户主动跳转，不用于服务端抓取、核验或补齐导入内容。原始网页无法访问、内容后来变化或外部导出遗漏，不使已经成功提交的 Palace 数据自动变化。

## D3：一次导入完整成功或完整失败

标题、来源身份、导入记录和全部消息在一个数据库事务中处理。任何字段或消息不合法时回滚整次请求，返回可定位到字段或数组下标的错误；不能跳过坏消息后宣称导入成功，也不能先创建空 Conversation 再等待用户修复。

同一 Owner Scope、同一 `(source, session_id)` 的导入必须串行处理；首次创建 Conversation 还需由数据库唯一约束兜底，并在并发冲突后按已有 Conversation 重新执行前缀匹配。不能让两个事务都基于同一旧树创建内容相同的兄弟节点。

`conversation_import` 至少记录稳定 `id`、`conversation_id`、输入摘要、路径头 `head_message_id`、消息数和导入时间。原始上传文件和完整原始 JSON 第一版不作为另一份权威正文长期保存；Message 内容才是持久化后的对话权威。

上传大小、消息数量、单条内容长度和 JSON 嵌套深度必须在读取或解析阶段受限。具体数值属于可调实现配置，但超限必须在任何业务写入前失败。Markdown 是不可信文本；存储保持原文，展示时必须经过安全渲染，不能直接作为 HTML 执行。

## D4：重复导入按最长完全相同前缀形成路径

同一 Owner Scope 的 `(source, session_id)` 已存在时，从根部按数组顺序比较 `role` 与原始 `content`：

1. 当前父节点下存在完全相同的子消息时复用该 Message。
2. 首次不同时，从最后一个共享节点开始创建剩余消息链。
3. 整条路径已经存在时不重复创建 Message，仍可记录本次成功 Import 并指向同一 head。

例如先后导入 `A-B-C` 与 `A-B-D`，结果为共享 A、B 的树，而不是两份完整正文。匹配可以使用内容摘要筛选候选，但最终必须比较完整 `role` 与原始 `content`；不得 trim、规范化 Markdown 或只靠摘要判等。

当前输入无法观察“同一父节点下两个角色和内容都完全相同、但来源上是两次不同生成”的区别。第一版将其视为同一逻辑 Message，这是有损但确定的导入规则。若产品需要保留这种不可观察差异，必须扩展输入契约提供稳定来源消息 ID 或显式节点 ID，不能继续声称只靠 `role/content` 可无损还原。

## D5：导入响应区分解析、校验与持久化结果

响应至少返回 Conversation 身份、本次路径 head、实际创建与复用的消息数量。JSON 语法错误、字段错误、限制超出、来源身份冲突和持久化失败是不同错误类别；不能只返回“导入失败”让用户逐条猜测。

客户端超时后可使用请求幂等键安全重试；同一幂等键与相同请求返回已提交结果，与不同请求复用则返回错误。输入摘要用于发现完全重复内容和审计，不代替请求幂等键，也不跨不同来源会话合并消息。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 本次取舍 |
| --- | --- | --- |
| Palace 直接抓取三家 Web Chat | 用户步骤少 | DOM、登录、导出与反自动化不稳定，明确位于当前系统边界之外 |
| 文件上传和文本框使用不同解析器 | 可分别优化体验 | 相同 JSON 可能得到不同结果，错误和兼容范围不可解释 |
| 忽略单条坏消息并继续 | 可导入更多内容 | 消息路径出现不可见缺口，用户无法判断知识是否完整 |
| 持久化所有来源额外字段 | 将来可能有用 | 三家字段不一致且语义不受 Palace 控制，扩大第一版契约和迁移成本 |
| 对 Markdown 做规范化后匹配 | 更容易合并视觉相同内容 | 会把原始数据不同的消息误认为同一节点，且改变用户提交内容 |
| 每次上传新建一份 Conversation | 实现最简单 | 同一来源会话无法共享前缀，重复导入制造不可解释副本 |

## 不变量

1. Palace 的责任从用户提交开始，不负责 Web Chat 页面提取和导出。
2. 文本框与 JSON 文件经过同一解析、校验和持久化流程。
3. 第一版只读取 role 与 content，忽略且不持久化额外字段。
4. 一次导入要么完整提交，要么不留下任何业务写入。
5. content 按用户提交的原始字符串保存，不因导入而规范化 Markdown。
6. 一次 Import 只表达一条 Path；分叉来自多条路径共享完全相同前缀。
7. 不同来源会话之间不因内容相同而合并 Message。

## 风险与为什么不能直接改写

仅保留 `role/content` 会丢失来源消息 ID、时间、模型、附件和工具调用；这是第一版明确的信息边界，后续无法从 Palace 数据中反推。若未来需要这些信息，应扩展版本化输入格式并从新导入获取，不能用猜测填充既有 Message。

最长相同前缀合并依赖原始内容精确相等。上线后改变 trim、换行或 Markdown 规范化规则会让相同输入形成不同树，或把既有不同节点合并；需要调整时必须新增格式/匹配版本并明确重建路径。已经被引用的消息父子关系不能为追求更高去重率而直接改写。

## 本决策未解决的问题

- 真正包含多个分支、稳定来源消息 ID 或附件的导入格式：需要独立版本和兼容规则。
- 导入预览、错误修复 UI、进度展示与批量任务：第一版事务契约不规定交互实现。
- 删除后重新导入与用户主动拆分/合并 Conversation：待产品行为明确后另定。再次导入保持已有标题，标题变化通过显式元数据编辑完成。
- 容量限制已由可配置解析边界和 HTTP 读取上限落实。病毒扫描和长期文件保存不属于当前纯 JSON 输入契约。

## 落地与验收

文本与文件共用字节解析边界；事务导入、精确前缀复用、请求幂等、容量限制和结构化错误均已落地。真实 PostgreSQL 测试验证并发收敛、既有树及新 Conversation 的失败回滚；HTTP 测试验证入口一致、原文保存和不访问来源页面。安全 Markdown 展示仍由未来展示端负责。

运行 `task test` 验证默认单元测试与 lint；`task test:integration`、`task test:contract` 显式运行默认忽略的容器测试。具体职责、接口、容量和部署配置见[运行文档](../../../../docs/README.md)，验证证据见对应领域核心测试用例。
