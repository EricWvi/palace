# 更新分支可以“仅上传新增消息”：增量接在当前 Path 末端之后，不再要求完整历史

> 历史决策：D5 中开关的位置与文字已由[更新分支可以在对话框里直接追加消息](20261027-write-delta-messages-in-update-dialog.md)修改：“对话文件”标签换成分段切换“对话文件 / 追加消息”，开关改名“增量导入”。

“更新分支”对话框增加一个开关“仅上传新增消息”，默认关闭。关闭时行为不变：上传的 JSON 必须是该 Path 的完整历史加上新消息。打开后，JSON 只包含要追加的新消息，服务端把它们依次接在当前 Path 的末端消息之后，不再拿 JSON 与已有历史比对。来源网站有时会改写已经导出过的历史消息（重新生成、编辑、截断、格式变化），完整历史无法再与 Palace 中的 Path 构成前缀，用户现在只能放弃更新或另建对话；打开开关后，用户删掉 JSON 里的历史部分，只交新增的几轮。下文把这种更新称为“增量更新”，与现有说法“追加更新”（上传完整 JSON、只允许在末尾追加）区分。

当前为 `implemented`，核心测试用例见[增量更新](../../../test-cases/server/import/delta-update.md)。涉及导入领域模型 `ImportTarget::Update`、`import_path` 的更新事务、`PUT /api/conversations/{id}/paths/{path_id}` 的请求体、OpenAPI 契约，以及 Web 端 `ImportDialog` 的更新模式。新建对话与新建分支不受影响。按“不保留兼容层”原则，更新请求直接增加必填的模式字段，不为旧客户端保留缺省值。

## 继承与修改

继承[创建会话、创建分支和追加更新使用明确的导入目标](20260919-explicit-branch-and-append-imports.md)和[分支管理改为分支列表](../conversation/20261006-branch-list-and-update-from-title-menu.md)，只修改更新操作的输入形态。

| 前序约定 | 本决定 |
| --- | --- |
| 更新只接受完整 JSON，新输入必须以该 Path 全部历史节点为前缀；不得修改、截短、重排历史 | 修改：增加“增量”输入模式，见 D1、D2；完整模式保持原规则 |
| 已被其他 Path 创建的相同后缀可以复用 | 继承：增量从末端开始同样复用末端下内容相同的子消息，见 D2 |
| 并发更新在数据库内串行检查最新末端，过期历史不能覆盖已经追加的内容 | 继承；完整模式靠历史前缀发现过期，增量模式改为显式携带基准末端，见 D3 |
| 幂等摘要包含操作类型、目标身份、原始历史与发生时间 | 修改：摘要还包含输入模式与基准末端，见 D4 |
| 更新回填该 Path 的标题与 `occurred_at`，Session ID 不可修改；成功后切到本次 Path 并改返回日期 | 继承，不变 |
| “更新分支”与分支列表里的“更新”打开同一个表单 | 继承：两个入口都出现“仅上传新增消息”开关，见 D5 |
| 一次导入完整成功或完整失败；原文保存，不规范化 content | 继承，不变 |
| 根决策 D1：解析器只读 role/content，不要求角色交替 | 继承：增量 JSON 使用同一解析器和限制，见 D2 |

## D1：更新请求显式声明历史形态

更新请求的 `history` 之外增加必填字段 `history_mode`，取值：

| 取值 | `history` 的含义 | 对应界面 |
| --- | --- | --- |
| `full` | 从根开始的完整历史，可在末尾追加新消息 | 开关关闭（默认） |
| `delta` | 只包含要接在当前末端之后的新消息 | 开关打开 |

为什么用枚举而不是布尔：两种形态对 `history` 的解释完全不同，调用方读到 `"history_mode": "delta"` 能直接知道这份 JSON 是什么；布尔 `append: true` 与现有“追加更新”的说法撞名，反而说不清完整模式也是在追加。`delta` 模式还要求携带 `base_head_message_id`（D3），`full` 模式禁止携带它；领域模型用带数据的枚举表达，而不是“一个模式字段加一个可选 ID”，使“增量却没有基准末端”无法构造。

为什么不让服务端自动判断：可以先尝试前缀匹配、失败再当作增量，但这会把“用户误传了一份历史被改过的完整 JSON”静默变成“把整段旧对话再接一遍”。是否丢弃来源的历史改动只能由用户声明。

## D2：增量从当前末端开始，沿用逐条复用与原子性

`delta` 模式下，服务端以 Path 当前末端为父节点，按数组顺序处理每条消息：父节点下已有 `role` 与原始 `content` 完全相同的子消息时复用，否则创建；下一条以这条为父节点。这与完整模式越过旧末端之后的处理相同，只是起点从根换成末端。

- 增量至少一条消息；根决策要求顶层是非空数组，空数组照常作为字段错误拒绝。
- 不检查增量第一条与末端消息的角色关系，例如末端是 user、增量也以 user 开头时照常写入，与根决策“不要求角色交替”一致。
- Path 的已有消息、父子关系和其他 Path 一律不变；只有本 Path 的末端前移。
- Path 的消息数变为原消息数加增量长度（完整模式下仍等于 JSON 长度），两种模式结束后都等于从根到新末端的消息数。
- 容量限制作用于本次提交的 JSON。增量模式下 Path 总长可以超过单次导入的消息数上限；上限保护的是解析和单次事务，不是 Path 长度。
- 标题与 `occurred_at` 的处理、Moment 移到新日期、成功落点都与完整模式相同。

复用规则必须保留：增量的开头可能正好是另一条 Path 已经从同一末端续写出的内容，若一律新建，同一父节点下会出现两个角色和内容都相同的兄弟，违反根决策 D4“同一父节点下相同内容视为同一逻辑 Message”。

## D3：增量携带基准末端，末端已变化时拒绝

`delta` 请求必须携带 `base_head_message_id`，即用户打开对话框时看到的 Path 末端。服务端在串行化 Path 修改的锁内读取最新末端，与它不同时拒绝整次请求，返回 409 `path_head_moved`，界面提示刷新后重试，不写入任何消息、标题、时间或回执。

为什么需要：完整模式的 JSON 自带全部历史，过期请求无法覆盖已经追加的内容，前缀检查天然防住了并发和重复提交。增量 JSON 没有锚点，同一段增量用两个幂等键提交两次（例如两个标签页、或刷新后重交），或两个对话框基于同一旧末端各自追加，若直接接在“最新末端”后，就会得到重复的尾巴或交错的两段对话，而且无法从数据上识别。基准末端把“我要接在哪里”变成请求的一部分。

| 场景 | 结果 |
| --- | --- |
| 打开对话框后无人修改该 Path | 接在末端后 |
| 打开后另一窗口已经追加（完整或增量） | 冲突，提示刷新；不写入 |
| 同一请求网络重试（同幂等键、同正文） | 返回已提交结果（D4） |
| 同一增量换新幂等键再交一次 | 第一次已移动末端，第二次冲突 |

Web 端从当前阅读页已经加载的 Path 数据取末端 ID，不额外请求。

## D4：幂等摘要覆盖模式与基准末端

摘要输入加入 `history_mode` 与 `base_head_message_id`（随 `ImportTarget::Update` 一起序列化）。同一幂等键下，完全相同的 JSON 以完整模式和增量模式提交是两个不同请求，后者重用键时返回冲突，而不是返回前者的结果。两种模式下同一份 JSON 的写入结果完全不同，不能互相充当重试。

## D5：对话框的开关与说明

更新模式的对话框在“对话文件”标签行的右端增加开关，文字为“仅上传新增消息”，每次打开对话框都处于关闭状态，不记住上次的选择。

文字按布局取舍：开关与七个字在 390px 宽的手机上仍与“对话文件”和帮助按钮同处一行，不拥挤，因此用直接说明操作的“仅上传新增消息”，不用更短但需要理解的“增量导入”。若以后标签行加入其他控件而变挤，再改为“增量导入”。不用“追加导入”：现有决策中的“追加更新”指上传完整 JSON 的更新，二者会混淆。

- 关闭：说明文字保持“上传完整 JSON，只能在原有消息之后追加。”
- 打开：说明文字改为“只上传新增消息，会接在当前第 N 条消息之后。”（N 为当前 Path 消息数）。
- 完整模式因历史不是前缀而失败时，错误提示补充“来源历史有变化时，可打开‘仅上传新增消息’，只上传新增部分”，让用户在出错处发现这个开关。
- 切换开关视为修改表单：清掉上一次失败的错误，并按新的请求重新生成幂等键（沿用现有“指纹变化即换键”的逻辑，指纹加入模式）。

为什么默认关闭且不记忆：完整模式会验证上传内容与 Palace 中的历史一致，是更安全的默认；增量更新放弃了这项验证，应当是用户每次有意识的选择。若记住打开状态，下次上传完整 JSON 时会把整段历史重复接在末尾，且 D3 不能防止这种误用。

新建分支不提供该开关：分支必须共享从根到 assistant 的前缀才能定位分叉点，没有完整历史就无从决定接在树的哪里。

## 后果：Palace 中的 Path 不再保证等于来源当前历史

增量更新之后，这条 Path 的前段是 Palace 早先导入的版本，后段是来源的新消息；来源网站上对前段的修改不会进入 Palace。这是用户主动选择的结果，也与根决策 D2 一致：来源内容后来变化不使已经提交的数据自动变化。代价是此后这条 Path 的完整 JSON 往往无法再以完整模式更新，用户会持续使用增量更新；需要与来源对齐时，应以新的 Session ID 新建分支或新建对话，Palace 不提供改写历史节点的操作。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| 完整模式失败后自动回退为增量或“最长公共前缀后接上” | 用户无需选择 | 会把历史被改写的完整 JSON 静默拼成重复或错位的对话；违背“用户声明意图”（D1） |
| 允许完整模式改写历史节点（就地替换旧消息） | Path 始终与来源一致 | 消息被其他 Path 共享，改写会同时改变别的分支；根决策明确已引用的父子关系不能改写 |
| 历史不一致时自动在分叉点建新分支 | 新旧两版都保留 | 需要新 Session ID 才能成为 Path；用户要的是更新这一支，不是多出一支 |
| 增量直接接在最新末端，不带基准末端 | 请求更简单 | 重复提交和并发追加产生无法识别的重复尾巴（D3） |
| 用布尔字段 `append` | 改动最小 | 与“追加更新”撞名，且让“增量却无基准末端”可以构造（D1） |
| 记住开关状态 | 常用者少点一次 | 下次上传完整 JSON 时把整段历史重复追加，基准末端检查拦不住（D5） |

## 不变量

1. 更新请求必须声明 `full` 或 `delta`；服务端不根据内容猜测模式。
2. `full` 模式的规则与本 ADR 之前完全相同。
3. `delta` 模式不修改、不比对、不截短 Path 已有的任何消息，只在末端之后增加或复用消息。
4. `delta` 请求的基准末端与锁内读到的最新末端不同时，整次请求失败且无任何写入。
5. 两种模式下，同一父节点下都不会因导入出现角色与内容完全相同的两个兄弟消息。
6. 成功后 Path 的消息数等于从根到新末端的消息数。
7. 同一幂等键不能在两种模式之间复用。
8. “仅上传新增消息”开关只出现在更新模式，每次打开对话框都默认关闭。

## 本决策未解决的问题

- **把来源的历史改动带进 Palace**：例如按来源新版本重建一条 Path 并替换旧 Path。涉及 Moment 身份、共享消息与删除语义，超出“只追加”的范围。
- **在界面上预览增量会接在哪条消息之后**：D5 只给出位置序号；是否显示末端消息摘要待使用后再定。

## 落地与验收

领域层用 `UpdateHistory::{Full, Delta { base_head_message_id }}` 表达更新形态，随 `ImportTarget::Update` 进入幂等摘要；HTTP 请求体保持扁平的 `history_mode` 与可选 `base_head_message_id`，在进入领域前拒绝不匹配的组合。`import_path` 在全局写锁内读取最新末端：增量与基准不符时返回 `DbError::StaleHead`（HTTP 409 `path_head_moved`），否则从末端开始逐条复用或创建，消息数累加原值。完整模式前缀失败的错误消息附带开关提示。Web 端开关为原生 `role="switch"` 按钮，状态由 `ImportDialog` 持有并在每次打开时复位，打开时请求携带当前 Path 的 `head_message_id`。

真实 PostgreSQL 测试覆盖增量写入、末端复用、角色不交替、过期基准无写入、并发增量只成功一个与幂等跨模式冲突；HTTP 测试覆盖字段组合与 409 类别；组件测试覆盖开关默认关闭、请求体、说明文字、冲突提示与换键；Chromium 测试覆盖 390px 宽度下的布局与从分支列表提交的请求和落点。
