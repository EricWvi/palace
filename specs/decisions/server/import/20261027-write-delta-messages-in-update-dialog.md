# 更新分支可以在对话框里直接追加消息：写下的消息拼成增量 JSON，开关改名“增量导入”

“更新分支”对话框的内容一行改为分段切换“对话文件 / 追加消息”。“对话文件”保持原样：选择 JSON 文件，右端开关决定完整或增量。“追加消息”不再要求准备文件：用户在表单里逐条添加消息，每条任选角色，下方文本框直接粘贴 Markdown；提交时前端把这些消息拼成与文件格式相同的 JSON 字符串，以增量模式接在当前 Path 末端之后。由于分段切换挤占了标签行，原开关“仅上传新增消息”按前序 D5 预留的方案改名为“增量导入”。

当前为 `implemented`，核心测试用例见[增量更新](../../../test-cases/server/import/delta-update.md#written-messages-must-append-as-a-delta-and-reset-on-reopening)。只涉及 Web 端 `ImportDialog` 的更新模式、新组件 `MessageDrafts`，以及完整模式前缀失败时错误提示中的开关名。HTTP 请求体、OpenAPI 契约、导入领域模型与数据库事务都不变。新建对话与新建分支不受影响。

## 继承与修改

继承[更新分支可以“仅上传新增消息”](20261010-delta-append-to-current-path.md)。

| 前序约定 | 本决定 |
| --- | --- |
| 更新请求必须声明 `full` 或 `delta`，增量携带 `base_head_message_id`，过期基准整体拒绝 | 继承，不变：写下的消息走同一请求，见 D1 |
| 增量从末端开始逐条复用或创建，不要求角色交替，至少一条 | 继承，不变 |
| 幂等摘要包含模式与基准末端；表单指纹变化即换键 | 继承：指纹改为包含更新方式与拼出的 JSON，见 D1 |
| D5：开关在“对话文件”标签行右端，文字“仅上传新增消息”；行变挤时改为“增量导入” | 修改：标签换成分段切换，开关改名“增量导入”，只在“对话文件”下出现，见 D2 |
| D5：每次打开对话框开关都关闭，不记忆 | 继承并扩展：每次打开都回到“对话文件”且开关关闭，见 D2 |
| 完整模式前缀失败的提示指向开关 | 继承：提示中的开关名改为“增量导入” |

## D1：写下的消息拼成与文件相同的 JSON 字符串，固定为增量

“追加消息”下，前端把每条消息按 `{"role", "content"}` 依次组成数组，序列化为字符串放进 `history`，请求固定为 `history_mode: "delta"` 并携带当前末端。user 消息是文本框里的原文，不修剪、不转义。assistant 消息只做一项转换：把 ChatGPT 复制出的 Markdown 转义公式 `\\(…\\)`、`\\[…\\]` 改为 `$…$` 与 `$$` 块，规则与 Automa 导出工作流（`automa/chatgpt/export-conversation.md` 的“公式定界符”）相同，代码块与行内代码不动。

为什么在前端转换：阅读页只排版美元符号定界的公式，直接粘贴的 ChatGPT 回复与 Automa 导出的文件应当读起来一样；文件经过 Automa 时已经转换，所以“对话文件”不再处理。转换发生在发出请求之前，服务端仍按根决策原样保存收到的 `content`。旧的美元语法与单反斜杠的转义括号都不含这两种定界符，原样保留，因此对其他来源的回复没有副作用。

为什么发字符串而不新增结构化字段：更新请求的 `history` 已经是 JSON 字符串，服务端对文件与写下的消息一视同仁，解析、容量限制、复用规则与错误信息只有一套。新增 `messages: [...]` 字段会让同一语义有两种请求形态，还要同步扩展 OpenAPI、领域模型和幂等摘要，却不带来新的服务端能力。

为什么固定为增量：在表单里重写整条历史没有实际用途；用户写下的总是“接下来的几轮”。因此“追加消息”下不显示开关，也就不存在“写下的消息却按完整历史比对”这种状态。

- 至少一条消息；任一条内容为空（只含空白）时在提交前拒绝，提示“第 N 条消息还没有内容。”，不发请求。服务端接受空字符串，但表单里的空框几乎总是漏填。
- 角色任选，不要求交替；新加一行默认取上一行的另一个角色，只为省一次选择。角色显示为“你”与该对话来源名，与阅读页一致。
- 可以删除任意一行，只剩一行时不显示删除。
- 表单指纹包含更新方式与拼出的 JSON：切换方式或改动任意消息都清掉上次错误并换新幂等键；网络失败后原样重试复用同一键。

## D2：分段切换取代“对话文件”标签，开关改名“增量导入”

更新模式下，内容一行左侧是分段切换“对话文件 / 追加消息”；“对话文件”下其后是帮助标记与开关，开关文字改为“增量导入”；“追加消息”下帮助标记与开关都不显示，文件框换成消息列表。新建对话与新建分支仍是普通的“对话文件”标签。

改名依据前序 D5 的预留：分段切换、帮助标记与七个字的开关在 390px 宽的手机上会折行，行高超过一行；“增量导入”四个字后同一行放得下。对话框说明文字保留“只上传新增消息，会接在当前第 N 条消息之后。”，解释开关打开后的含义；“追加消息”下说明为“追加的消息会接在当前第 N 条消息之后。”

每次打开对话框都回到“对话文件”且开关关闭；从“追加消息”切回“对话文件”时开关也是关闭的。理由同前序 D5：完整模式是更安全的默认，增量必须是每次有意识的选择。写下但未提交的消息在同一次打开内切换时保留，关闭对话框即丢弃。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| 请求新增结构化 `messages` 字段 | 前端不必序列化 | 同一语义两种请求形态，服务端、OpenAPI 与幂等摘要都要扩展，却没有新能力（D1） |
| “追加消息”下也保留开关，允许写整条历史 | 形式上对称 | 没有用途，并引入“写下的消息按完整历史比对”的易错状态（D1） |
| 开关仍叫“仅上传新增消息”，把分段切换放到单独一行 | 不改已有文案 | 多占一行；前序 D5 已为变挤预留了改名方案 |
| 记住上次选择的方式 | 常用者少点一次 | 下次上传完整文件时可能以增量重复追加整段历史（继承前序 D5） |

## 不变量

1. “追加消息”提交的请求与上传同样消息（assistant 公式已按 D1 转换）的 JSON 文件并打开“增量导入”的请求完全相同（幂等键除外）。
2. “追加消息”下的请求总是 `delta` 并携带打开对话框时的末端。
3. 有空内容的消息时不发请求。
4. 每次打开更新对话框都处于“对话文件”且“增量导入”关闭；切回“对话文件”时开关关闭。
5. 分段切换与“追加消息”只出现在更新模式。

## 落地与验收

`ImportDialog` 以 `UpdateInput = "full" | "delta" | "messages"` 持有更新方式，每次打开复位为 `full`；`MessageDrafts` 渲染消息列表，`ImportForm` 在提交时拼出 JSON 字符串。组件测试覆盖切换后隐藏开关与文件、默认角色、删除、空内容拒绝、请求体与复位；Chromium 测试覆盖 390px 宽度下两种方式的布局。
