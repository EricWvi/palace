# Web 编辑和删除札记时直接写工作区文件并立即发布；commit 带上之前，索引保留网页的结果

Web 可以修改札记的标题、标签和正文，也可以删除札记。服务端改的是工作区里的札记文件：编辑时原子地重写文件，删除时删掉文件。它照旧不写 `.git`、不 commit。写完文件后，服务端在发布锁内更新索引并发布新版本，网页和移动端立刻看到结果。服务端同时记下这次网页写入，在对账时据此判断网页的结果是否还在：commit 已经带上它时，以 commit 为准；commit 还没带上、工作区仍是网页写下的样子时，保留网页的结果；工作区已经被改成别的样子时，回到 commit 的内容。保存要带上打开时的版本，版本过期、文件被移走或者不再是这张札记时返回 `409`。

当前为 `approved`，核心测试用例见[札记同步](../../../test-cases/server/jotting/jotting-sync.md)和[札记读取接口](../../../test-cases/web/echo/jotting-reading.md)。本决策基于[札记根决策](0-jottings-indexed-from-git-commits.md)，修改其“问题与约束”中“不做编辑器”、D2 的对账规则、不变量 2 和 7。涉及 `palace-db`（新表、对账输入、网页读取带版本）、`palace-jottings`（文件改写与删除、对账规则）、`palace-backend`（两个新接口）和 `docs/features/jottings/README.md`。界面另见[回响页的放大卡片编辑和删除札记](../../web/echo/20261101-edit-and-delete-a-zoomed-jotting-with-title-slips.md)。移动端仍然只能新建，同步协议不变：网页编辑在移动端看来就是一次普通的修改或删除。札记文件格式不变。

## 继承与修改

| 前序约定 | 本决定 |
| --- | --- |
| 问题与约束：文件是唯一权威，Palace 不做编辑器 | 修改：文件仍是唯一权威，网页编辑的结果写进文件；Palace 提供修改小处用的编辑，不承担整理和批量改写，那仍由 Agent 做 |
| D1：身份是 `id`，`created` 是业务时间 | 继承；网页编辑不能改 `id` 和 `created`，见 D1 |
| D1：未知的 frontmatter 字段原样保留在文件中 | 继承；网页改写文件时原样保留，见 D2 |
| D2：索引只对应 HEAD commit 的树，加上尚未入 commit 的上传札记 | 修改：还加上尚未入 commit 的网页写入，见 D4 |
| D4：上传札记写入 `inbox/<id>.md`，按 ID 幂等 | 继承；上传的重试判定只看首次上传的摘要，网页改过或删过不影响重试结果 |
| D4：服务端不 commit | 继承 |
| D5：只有客户端看得到的字段变化才发布新版本；版本在发布锁内分配 | 继承；网页写入走同一把锁、同一套发布规则 |
| 不变量 2：已发布状态是合格 commit 的树加上未入 commit 的上传 | 修改，见本文件不变量 1 |
| 不变量 7：服务端只写 `inbox/<id>.md` | 修改：还会改写或删除网页指定的那张札记的文件，见本文件不变量 4 |
| 回响页的读取接口：`pending` 表示文件在 `inbox/` 下 | 修改：网页改过、尚未入 commit 的札记也是 `pending`，见 D5 |

## D1：可以修改的字段与接口

- `PUT /api/jottings/{id}`，请求体 `{ version, title?, tags?, body }`：把札记改成给定的标题、标签和正文。`title` 省略或为空白时去掉标题；`tags` 的规则同上传。`id`、`created` 不变。成功返回 `200` 和 `{ version }`。
- `DELETE /api/jottings/{id}?version=<n>`：删除札记，成功返回 `204`。
- `version` 是网页读取时拿到的 `server_version`。回响页的读取接口（列表、回顾）因此给每张札记加上 `version`。
- 正文上限 1 MiB，与上传相同。规范化也与上传相同：去掉正文开头的空行。
- 内容与当前完全相同的编辑什么也不写，直接返回当前版本。

**为什么 `id` 和 `created` 不能改**：`id` 是身份，改了等于删一张、建一张。`created` 决定札记在墙上的位置和回顾的候选资格，网页上的小改动用不到它，留给 Agent 在文件里改。

## D2：文件先写、索引后写，保留文件的其他部分

保存在发布锁内按以下顺序进行：

1. 按 `id` 读取索引行。札记已删除，或者 `version` 与当前版本不同：返回 `409 jotting_changed`，不写任何东西。
2. 读取工作区中索引记录路径下的文件。文件不存在、解析失败，或者 `id` 不是这张札记：返回 `409 jotting_moved`，不写任何东西。
3. 编辑：只替换文件中 `title`、`tags` 两个字段和正文，frontmatter 的其他行原样保留，包括字段顺序、未知字段和注释；新增字段写在 `created` 之后。以临时文件加 rename 原子写入。删除：删掉这个文件。
4. 更新索引行并发布，记录这次网页写入（D3）。

- **文件先写**：与上传相同，行存在就意味着文件已经写入。第 4 步失败时，文件里已是网页的内容，索引仍是旧的。这时既没有发布，也没有网页写入记录，所以下一次对账按 commit 处理；网页可以用同一个 `version` 重试，第 2 步能通过，结果相同。
- **只替换这几个部分**：Agent 在 commit 前会看 diff。整个文件按规范格式重新渲染会改动无关的行，Agent 就分不清哪些是网页的修改。
- **覆盖 Agent 未 commit 的改动是接受的**：第 2 步只检查文件还在、还是这张札记，不检查它是否等于 commit 里的版本。Agent 正在改的同一个文件被网页覆盖，Agent 未 commit 的改动会丢失；实际很少发生，换来的是网页保存不必关心 Agent 的工作区状态。
- **版本过期必须拒绝**：网页打开札记后，一次 commit 可能已经改了它。这时用旧稿保存，会把 Agent 已经 commit 的内容悄悄覆盖掉，而覆盖的是已经提交的工作，不是 Agent 正在改的草稿。

## D3：记录网页写入

新表 `jotting_web_write`，每张札记最多一行：

| 列 | 含义 |
| --- | --- |
| `jotting_id` | 札记 |
| `path` | 写入时文件的路径 |
| `base_oid` | 写入前这张札记在最近一次对账的 commit 中的 blob；上传后从未入 commit 的札记为空 |
| `written_oid` | 网页写下的文件的 blob；删除时为空 |
| `written_at` | 写入时间，毫秒精度 |

- 同一张札记连续编辑多次时，`base_oid` 保持第一次的值，`written_oid` 和 `path` 改为最后一次的。
- 没有入过 commit 的上传札记，`base_oid` 为空。它在对账中仍按上传规则处理（根决策 D4），这一行只用于 D5 的待整理状态，删除时随 tombstone 一起清掉。
- 这张表不改变 `jotting` 表的结构，也不改变 tombstone 的约束（tombstone 没有路径和 blob）。

## D4：对账时如何对待网页写入

对账时，对有网页写入记录、并且 `base_oid` 不为空的札记，按新树中这张札记的 blob 判断：

| 新树里这张札记 | 工作区中新树所在路径的文件 | 含义 | 处理 |
| --- | --- | --- | --- |
| blob = `written_oid` | — | 网页的修改已入 commit | 按 commit 处理，删除记录 |
| 不在树中，且这是一次删除 | — | 网页的删除已入 commit | 保持 tombstone，删除记录 |
| blob = `base_oid` | 仍是网页写下的样子：编辑时 blob = `written_oid`，删除时文件不存在 | 这次 commit 没带上它 | 保留网页的结果，不发布；路径变了时更新记录的路径 |
| blob = `base_oid` | 变成了别的样子 | 网页的结果已在工作区被撤销或改写，例如 `git restore`，或者 Agent 又改过但没 commit | 按 commit 处理（删除的札记因此复活），删除记录 |
| 其他 blob，或者不在树中而这是一次编辑 | — | 有人在 commit 里改过或删过它 | 按 commit 处理，删除记录 |

- 工作区按新树中的路径检查，而不是记录的路径：Agent 用 `git mv` 移动了网页改过的文件、但没有 `git add` 新内容时，新树里是旧 blob 在新路径，工作区的新路径上仍是网页的内容，网页的结果保留下来。
- 判断工作区文件时计算它的 Git blob OID，与 `written_oid` 比较，不解析内容。
- 检查只针对有记录的札记，一般是个位数，不扫描工作区。

**为什么要记下来，而不是只看工作区**：没有记录时，对账只能把工作区与 commit 的每一处差异都当作候选，那就是扫描工作区，根决策 D2 明确否决过。有了记录，对账只需要看网页写过的那几个文件。

**为什么以工作区为准判断是否撤销**：网页没有撤销按钮。要撤销网页的修改或删除，就在仓库里 `git restore` 这个文件，下一次对账自然回到 commit 的内容，不需要新的接口。

**已知边界**：撤销只在下一次对账时生效，而对账只在 HEAD 变化时进行。`git restore` 之后、下一次 commit 之前，网页和移动端仍然显示网页的结果。

## D5：待整理状态

回响页读取接口的 `pending` 改为：文件位于 `inbox/` 下，或者有网页写入记录且不是删除。网页改过、还没 commit 的札记因此带待整理圆点，提醒去 commit；commit 带上之后，记录被删除，圆点随之消失。

## D6：与回顾和同步的关系

- 编辑不改变回顾状态和完成次数。
- 删除写成 tombstone，回顾状态随之删除（回顾决策 D2 的 trigger）；今天卡片组里的这张卡片从读取结果中消失，完成它返回 `404`。按 D4 复活时，完成次数从当前最小值开始，与其他复活相同。
- 移动端经 `changes` 收到一次修改或删除，与 Agent 改动没有区别。对一张网页删掉的上传札记重试上传，仍按根决策 D4 第 3 步返回 `200` 和 tombstone 的版本，不会复活它。

## 不变量

1. 已发布的札记状态是某个合格 commit 的树，加上尚未入 commit 的上传，再加上工作区中仍然存在、尚未入 commit 的网页写入。
2. 版本过期、文件不在记录的路径、或者该路径的文件不是这张札记时，网页的保存和删除不改变任何文件和索引行。
3. 网页编辑后的文件，除 `title`、`tags` 和正文外，与编辑前逐字节相同。
4. 服务端从不写 `.git`；它只会写 `inbox/<id>.md`，以及改写或删除网页指定的那张札记在索引记录路径下的文件。
5. 一次网页写入在 commit 带上它、它被工作区撤销、或者 commit 改动了同一张札记之前，不会被对账悄悄改回旧内容。
6. 对账只读取有网页写入记录的工作区文件，不扫描工作区。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| 只写工作区，commit 之后才发布 | 不改不变量 2，对账规则不变 | 网页保存后看不到自己的修改，直到 Agent commit；网页与移动端各自显示不同内容。小改动在网页上做就是为了省掉这一步 |
| 服务端自己 commit 网页写入 | 文件与 Git 历史时刻一致，不需要 D3、D4 | 与 Agent 争用 index 和 HEAD，服务端需要 `.git` 写权限；根决策 D4 已因同样理由否决服务端 commit |
| 编辑只存数据库，作为覆盖层，不写文件 | 不碰工作区 | 数据库成了文件之外的第二份真相，Agent 和 `rg` 看不到网页的修改，违反“文件是唯一权威” |
| 不记录网页写入，对账时比较工作区与 commit | 少一张表 | 需要扫描工作区的全部札记，根决策 D2 已否决；工作区里 Agent 写了一半的文件也会被读到 |
| 保存时检查文件仍等于 commit 中的版本，有未 commit 的改动就拒绝 | Agent 的未 commit 改动不会被覆盖 | Agent 的工作区常有未 commit 的改动，网页保存会频繁失败；Eric 接受偶尔覆盖 |
| 删除改为移到回收目录或在 frontmatter 标记 | 可以在网页上撤销 | 已决定不做归档目录；commit 过的内容在 Git 历史中，`git restore` 已能撤销 |
| 整个文件按规范格式重新渲染 | 实现简单 | 改动无关的行，Agent 看 diff 时分不清网页改了什么；未知字段的格式和注释会丢 |

## 风险

- **网页写入长期不 commit**：网页结果一直保留，带待整理圆点，不会丢失，只是迟迟不进 Git 历史。Agent 的工作说明需要写明：工作区中由网页修改或删除的札记文件，原样 commit。
- **文件权限**：网页编辑会改写 Agent 创建的文件，服务端对整个札记目录（不只 `inbox/`）需要写权限，部署时与上传一样统一 UID 或设置组权限。
- **删除不可在网页上撤销**：从未入 commit 的内容（上传后、或网页编辑后未 commit）被删除后无法找回。界面用两步确认降低误删，见 Web 决策。

## 本决策未解决的问题

- **移动端编辑与删除**：需要离线修改与服务端修改的合并规则，移动端仍然只能新建。
- **修改 `created`、移动文件**：留给 Agent。

## 落地顺序

1. 迁移与对账：新增 `jotting_web_write`，对账按 D4 处理有记录的札记，`pending` 按 D5 计算，读取接口带 `version`。完成条件：对账规则的纯函数测试覆盖 D4 表的每一行，真实 Git 与 PostgreSQL 测试覆盖 `git mv` 与 `git restore`。此时还没有写入接口，行为不变。
2. 写入接口：`PUT` 与 `DELETE`，按 D2 写文件和索引。完成条件：真实 PostgreSQL 测试覆盖两种 `409`、未知字段逐字节保留、文件先写的失败恢复、与对账并发时的顺序。从这一步起网页可以编辑和删除。
3. 文档：`docs/features/jottings/README.md` 和札记仓库的 Agent 工作说明。
