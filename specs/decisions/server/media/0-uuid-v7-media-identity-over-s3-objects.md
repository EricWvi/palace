# 媒体文件存入 S3 兼容对象存储，Palace 以服务端生成的 UUID v7 作为稳定身份；首版只提供上传与删除

Palace 新增媒体文件（Media）能力：文件内容保存在 S3 兼容对象存储（MinIO 或任一 S3 实现），PostgreSQL 的 `media` 表保存归属与访问映射。每个媒体文件由 Palace 服务端在上传时生成的 UUID v7 标识，这个 ID 是对外唯一的引用方式；对象 key、bucket、endpoint 和签名 URL 都是服务端内部细节，客户端和业务正文不得持有。首版只开放两个接口：`POST /api/media` 上传单个文件并返回媒体 ID 与元信息，`DELETE /api/media/{id}` 删除媒体记录及其对象。读取、展示和引用管理留给后续决策。

当前为 `approved`，方案已通过评审，尚未实现；核心测试用例见[媒体文件存储](../../../test-cases/server/media/media-storage.md)。本文件是 `server/media` 的根决策，没有前序 ADR。表设计参考 dashboard 的 `d_media`（见[共享媒体与附件](../../../../docs/legacy/shared/media.md)），但不承诺兼容 dashboard 的接口、URL 形式或签名 URL 续签机制，也不承担旧 dashboard 媒体的导入；D2 只保证导入将来可以在不搬迁对象的前提下进行。涉及 `palace-db` 新迁移、`palace-backend` 的媒体接口、`palace-server` 的配置，以及一个新的对象存储 crate。

## 问题与约束

- [同步根决策](../sync/0-client-timestamp-lww-and-global-seq.md)把附件和二进制内容的传输、存储与回收列为未解决问题；笔记中的图片已经是 S3 链接，旧 dashboard 的头像、封面和正文图片视频也都在 MinIO 中。Palace 需要一个自己的媒体身份，后续的正文图片、旧数据导入和展示才有落点。
- dashboard 的做法是 `serial id` 加随机 UUID `link`，key 形如 `2025/01/<unix>_<文件名>`，并把 160 小时有效的签名 URL 存进表里、每天定时续签。它的问题是：key 混入原始文件名，带出 Unicode、长度和路径字符问题；签名 URL 落库造成“过期数据”需要后台任务维护；删除时先软删记录再删对象，批量中失败项被静默跳过。
- 正文（Markdown、富文本）一旦写入某个媒体引用就会长期保存、跨设备同步、被导出。被写进正文的必须是一个永不变化的标识，否则更换对象存储、bucket 或 key 布局就要改写全部正文。
- 依照 [Owner 根决策](../owner/0-authelia-identity-and-owner-scoped-records.md)，`media` 保存 Owner 数据，必须带 `owner_id NOT NULL`，并且只能在认证上下文给出的 Owner Scope 内读写。
- Palace 主要由 Eric 自用，媒体规模小（个人照片、截图、短视频）；可以接受单进程内存缓冲和串行逻辑，但不能接受“用户删除了文件、对象仍留在存储中而 Palace 报告成功”。

## D1：媒体 ID 是服务端生成的 UUID v7，是唯一对外身份

上传成功时，服务端为媒体文件生成 `Uuid::now_v7()` 作为 `media.id`，并在响应中返回。此后接口路径、正文引用、未来同步记录都只使用这个 ID。客户端不能指定 ID。

选择 UUID v7 而不是 dashboard 的 `serial + gen_random_uuid()`：

- 一个 ID 同时承担主键和对外身份，不再需要 `id`/`link` 两列及其映射；Palace 现有表（Owner、Session、同步记录）都使用 v7，保持一致。
- v7 按时间单调，B-tree 插入局部性好，按 ID 排序约等于按上传时间排序，列表和清理任务可以直接走主键。
- v7 的时间前缀会暴露上传时间。媒体只在 Owner Scope 内可访问，上传时间本身也会作为 `created_at` 展示，这一泄露可以接受。ID 难以猜测不构成授权，所有访问仍以 `(owner_id, id)` 定位。

由服务端而不是客户端生成 ID，是因为媒体在服务端完成对象写入之后才存在；让客户端预先选定 ID 会把“ID 已占用但对象未写入”“同一 ID 两次上传内容不同”变成需要处理的状态。代价是上传不幂等：响应丢失后重试会产生第二个媒体文件，见“风险”。

## D2：对象 key 是内部映射，与 ID 解耦存储

| 列 | 类型 | 规则 |
| --- | --- | --- |
| `id` | `uuid` | 主键，D1 生成 |
| `owner_id` | `uuid NOT NULL` | 引用 `owner(id)`；创建后不可修改，沿用 `reject_owner_change()` 触发器 |
| `object_key` | `text NOT NULL` | 对象在 bucket 中的 key；全局唯一 |
| `content_type` | `text NOT NULL` | 上传时确定的 MIME 类型，见 D3 |
| `byte_size` | `bigint NOT NULL` | 对象字节数，`CHECK (byte_size >= 0)` |
| `sha256` | `bytea NOT NULL` | 内容摘要，32 字节，用于完整性核对与导入去重判断，不用于自动合并 |
| `file_name` | `text NULL` | 客户端提供的原始文件名，只用于展示和下载，不进入 key |
| `created_at` | `timestamptz NOT NULL` | 毫秒精度，`date_trunc('milliseconds', now())` 写入并带同名 CHECK |

另有 `UNIQUE (owner_id, id)` 供将来 Owner-scoped 复合外键引用。

新上传的 key 由服务端按 `<owner_id>/<media_id>` 生成：不含文件名、扩展名或日期，因此不需要转义，长度固定，也不会冲突。前缀 `owner_id` 让按 Owner 枚举、导出和对账可以直接用对象存储的前缀列举完成。

key 仍然单独存一列，而不是每次由 ID 推导，是为了让旧 dashboard 对象将来以原 key（如 `2025/01/1736000000_IMG_0001.jpg`）登记为 Palace 媒体，无需复制对象；也让以后改变 key 布局时，新旧对象可以共存。bucket 和 endpoint 是部署配置，不入库：一个部署只有一个 bucket，迁移存储时整体复制 bucket，表不变。

与 `d_media` 相比，有意删去的列：

| `d_media` 列 | 处理 | 原因 |
| --- | --- | --- |
| `id serial` + `link uuid` | 合并为 `id uuid` | D1 |
| `creator_id integer` | 改为 `owner_id uuid` | Owner 根决策 |
| `presigned_url`、`last_presigned_time` | 不存 | 签名 URL 是短期派生值，落库只会制造过期数据和续签任务；需要时按 key 现签 |
| `updated_at`、`deleted_at` | 不存 | 媒体内容不可修改，替换文件就是上传新媒体；删除是硬删除，见 D5 |

## D3：上传接口一次接收一个文件

`POST /api/media` 接收 `multipart/form-data`，只有一个 `file` 字段。服务端：

1. 读取文件内容，超过上限（`PALACE_MEDIA_MAX_BYTES`，默认 50 MiB，对齐 dashboard 编辑器的单文件限制）时返回 413；空文件返回 400。
2. 计算 `sha256` 与字节数；`content_type` 取 multipart part 的 `Content-Type`，缺失或无法解析为 `type/subtype` 时记为 `application/octet-stream`。首版不按扩展名猜测，也不限制类型。
3. 生成 ID 和 key，以 `PutObject` 写入对象，同时把 `Content-Type` 写到对象元数据。
4. 对象写入成功后，在 Owner Scope 内插入 `media` 行，返回 `201`：

```json
{ "id": "0192f5c4-…", "contentType": "image/png", "byteSize": 48213, "fileName": "截图.png", "createdAt": 1760774400123 }
```

一次一个文件而不是 dashboard 的多文件 `photos` 字段：多文件上传要么整体原子（对象存储做不到），要么部分成功（违背 Owner 根决策 D4 “批量不静默部分成功”的精神，并要求客户端解析逐项结果）。单文件让每个请求的结果只有成功或失败，客户端并发发起多个请求即可。

先写对象、后写行：行存在就意味着对象已经写成功，因此不存在“有记录但无文件”的状态。如果插入行失败，服务端尽力删除刚写入的对象；这次删除也失败时只留下无人引用的对象，见“风险”。

首版把文件完整缓冲在内存中，原因是要在写入前得到长度和摘要，而且 50 MiB 上限下单用户内存可以接受。媒体接口按自身文件上限单独设置请求体上限，不与导入接口共享，避免调整一方时改变另一方的可接受范围。

## D4：对象存储通过 trait 注入，未配置时接口不可用

对象存储访问定义为一个 trait（写入、删除，后续加签名读取），生产实现基于 S3 协议，测试使用内存实现或真实 MinIO。连接参数来自环境变量：

| 变量 | 说明 |
| --- | --- |
| `PALACE_S3_ENDPOINT` | S3 endpoint URL，例如 `https://minio.example.com` |
| `PALACE_S3_REGION` | region，MinIO 可用 `us-east-1` |
| `PALACE_S3_BUCKET` | bucket 名，需预先创建 |
| `PALACE_S3_ACCESS_KEY_ID` | access key |
| `PALACE_S3_SECRET_ACCESS_KEY` | secret key，只在服务端使用 |
| `PALACE_S3_PATH_STYLE` | 是否使用 path-style 寻址；MinIO 通常需要 |

这组变量要么全部提供、要么全部不提供。全部不提供时服务正常启动，媒体接口返回 `503`，便于本地开发和不需要媒体的部署，这与笔记文件夹可选的做法一致；只提供一部分时启动失败，避免配置拼写错误被静默当成“未启用”。服务端以枚举表达“已配置 / 未配置”两种状态，不使用若干个 `Option` 字段。

S3 请求不得在持有同步全局锁（同步根决策 D4）的事务内执行；媒体表本身不进入同步域，不使用该锁。

## D5：删除先删对象、后删行，失败可重试收敛

`DELETE /api/media/{id}`：

1. 在 Owner Scope 内按 `(owner_id, id)` 查找；不存在（包括属于其他 Owner）返回 `404`。
2. 删除对象。S3 `DeleteObject` 对不存在的 key 也返回成功，因此重复删除无害。
3. 删除 `media` 行，返回 `204`。

任一步失败返回 `5xx`，行仍然存在，客户端重试会重新走完三步。这个顺序保证 Palace 只有在对象确实删除后才报告成功。

反过来先删行、后删对象（dashboard 的顺序）时，对象删除失败会留下一个 Palace 已无法通过任何接口找到的文件：用户以为照片已删除，文件仍在存储里，而且没有记录能驱动重试。本决策选择让中间状态停在“行还在、对象已没”，这个状态可以通过重试收敛；代价是在两步之间，读取接口（后续决策）可能遇到行存在而对象缺失，必须按 404 处理。

删除是硬删除，不保留墓碑。媒体首版不进入同步域，不需要向离线客户端传播删除；将来媒体进入同步时由后续 ADR 定义墓碑。删除也不检查正文是否仍引用该媒体，引用关系见“未解决的问题”。

首版不提供批量删除；多选删除由客户端逐个调用，失败项可单独重试。

## 不变量

1. 媒体文件的对外身份只有 `media.id`；对象 key、bucket、endpoint 和签名 URL 不出现在任何接口响应或业务正文中。
2. `media.id` 由服务端生成，创建后不变；更换对象存储或 key 布局不改变已有 ID。
3. 每一行 `media` 都对应一个已成功写入的对象。
4. 删除接口返回成功时，对应对象已从对象存储中删除。
5. 所有媒体读写都以 `(owner_id, id)` 定位；`owner_id` 只来自认证上下文且创建后不可修改。
6. 媒体内容不可修改；同一 ID 永远指向同一份字节，其 `sha256` 与对象内容一致。
7. S3 请求不在同步全局锁的事务内执行。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 本次取舍 |
| --- | --- | --- |
| 沿用 dashboard 的 `serial id` + 随机 UUID `link` | 与旧表结构一一对应，导入时少一次转换 | 两个身份需要维护映射；v4 无序，索引局部性差；Palace 其他表都是 v7 |
| 客户端生成 UUID v7 | 上传可按 ID 幂等重试，与同步记录“本地首次创建时生成 ID”一致 | 引入“ID 已占用但对象未写入”和“同 ID 不同内容”的状态；首版接受重试产生孤儿，等媒体进入同步时再评估 |
| 对象 key 直接使用 ID，不存 `object_key` 列 | 少一列，key 可推导 | 旧 dashboard 对象无法原地登记，只能复制；以后无法平滑改变 key 布局 |
| 按内容 sha256 寻址并去重 | 节省存储，重复上传天然幂等 | 删除需要引用计数，跨 Owner 去重会通过“上传是否秒成”泄露其他 Owner 是否有某个文件；个人规模下节省有限 |
| 存储签名 URL 并定时续签（dashboard） | 读取时少一次签名计算 | 签名 URL 是短期派生值，落库产生过期数据和后台任务；签名本身是本地 HMAC 计算，代价很低 |
| 客户端直传 S3（presigned PUT） | 大文件不经过 Palace，无内存压力 | 需要“预登记—确认”两阶段协议、未确认对象的清理和 bucket CORS 配置；首版文件小，不值得 |
| 文件存 PostgreSQL `bytea` 或本地磁盘 | 与元数据同事务，无外部依赖 | 数据库备份膨胀；本地磁盘与容器部署、现有 MinIO 资产不匹配 |
| 多文件一次上传 | 与 dashboard 接口一致，请求数少 | 只能部分成功，见 D3 |
| 删除时先删行再删对象（dashboard） | 行删除在事务内，失败率低 | 对象删除失败会留下无法追踪的文件且接口已报告成功，违反不变量 4 |

## 风险与为什么不能直接改写

- **孤儿对象**：D3 插入行失败且补偿删除也失败、上传响应丢失后客户端重试、进程在写对象和插入行之间崩溃，都会留下对象存储中有、`media` 表中没有的对象（或有行但没有任何正文引用）。它们只占空间，不会被任何接口返回。key 以 `owner_id` 为前缀，后续可以按前缀列举对象并与表对账清理；首版不实现清理任务。
- **内存缓冲**：上传整文件缓冲在内存。并发上传数乘以上限就是峰值内存；如果以后要支持大视频，应改为流式分片上传或客户端直传，而不是简单调大上限。
- **content type 由客户端声明**：首版不校验内容与类型是否一致。读取接口设计时必须决定是否以 `Content-Disposition: attachment` 或独立域名提供非图片类型，避免在 Palace 同源下渲染用户上传的 HTML/SVG。
- **ID 与 key 一旦写入正文和存储就不能改写**：已有媒体的 `id` 不能重新生成，`object_key` 不能在不移动对象的情况下修改。迁移对象存储时应整体复制 bucket 并保持 key 不变，然后切换配置；需要改变 key 布局时新对象使用新布局，旧行保持原 key，或者先复制对象、再在单条事务中更新 `object_key`、最后删除旧对象。
- **bucket 配置变更**：`PALACE_S3_BUCKET` 指向一个不含既有对象的 bucket 时，所有已登记媒体都会变成“行存在、对象缺失”。这是部署错误，不能通过删除这些行来“修复”。

## 本决策未解决的问题

- **读取与展示**：通过 ID 获取内容的接口（302 到现签 URL 还是由 Palace 代理）、签名有效期、缓存策略、非图片类型的安全展示。这是首版之后最先需要的决策。
- **引用关系与回收**：正文中如何书写媒体引用（例如 `palace-media:<id>`）、删除时是否检查引用、孤儿对象与未引用媒体的对账清理。
- **同步**：媒体元数据是否进入同步域、客户端缓存与离线可用性、删除墓碑。
- **旧 dashboard 媒体导入**：把 `d_media` 的 key 登记为 Palace 媒体、旧 URL 到新 ID 的映射、缺失对象和共享引用的处理，见[迁移核对](../../../../docs/legacy/migration/README.md)。
- **列表、配额和缩略图**：首版没有媒体列表接口，也不生成缩略图或限制 Owner 的总用量。

## 落地顺序

1. **存储抽象与配置**：新增对象存储 crate，定义 trait、S3 实现和内存实现；`palace-server` 解析 D4 的环境变量，三种配置状态（全部提供、全部缺失、部分提供）各有测试。完成条件：用本地 MinIO 镜像的集成测试验证写入、重复删除和删除不存在的 key。
2. **`media` 表**：新增迁移，包含 D2 的列、owner 不可变触发器和毫秒 CHECK。完成条件：真实 PostgreSQL 测试验证跨 Owner 读取不到、`owner_id` 不可修改。
3. **上传与删除接口**：按 D3、D5 实现并纳入 OpenAPI 合同。完成条件：HTTP 测试覆盖上传成功、超限、未配置返回 503、跨 Owner 删除返回 404、对象删除失败时行保留且重试成功；同步更新 `docs/server/环境变量.md`。

阶段 1、2 互不依赖，可以分别评审；阶段 3 之后客户端才能看到新接口。现有导入、时间线、同步和笔记行为全部不变。
