# 正文以 `/api/media/<id>` 引用媒体，读取时校验 Owner 后 302 到现签的短期 URL；被正文引用的媒体不能单独删除

Palace 新增 `GET /api/media/{id}`：在 Owner Scope 内找到媒体后，返回 `302` 跳转到对象存储的现签 GET URL，浏览器从对象存储直接取字节。业务正文中引用媒体的唯一写法是 Palace 应用地址 `/api/media/<id>`，签名 URL 永不进入正文或数据库。签名时间按小时对齐，同一小时内同一媒体的跳转目标不变，浏览器缓存因此有效。被业务记录引用的媒体不能通过 `DELETE /api/media/{id}` 单独删除，只能随引用它的记录一起删除。

当前为 `approved`，核心测试用例见[媒体读取](../../../test-cases/server/media/media-reading.md)。本决策基于[媒体根决策](0-uuid-v7-media-identity-over-s3-objects.md)，回答其“读取与展示”和“引用关系与回收”两个未解决问题中的读取与正文写法部分；第一个使用者是[文章](../../web/stars/20261020-articles-imported-with-media.md)。涉及 `palace-media` 的存储 trait 与 S3 实现、`palace-backend` 的媒体接口、`palace-server` 的配置与 `docs/server/环境变量.md`。孤儿对象的对账清理、缩略图、媒体列表、同步与旧 dashboard 媒体导入仍不在范围内。

## 继承与修改

| 前序约定（媒体根决策） | 本决策 |
| --- | --- |
| D1：`media.id` 是唯一对外身份，对象 key、bucket、endpoint、签名 URL 不出现在接口响应或正文中 | 修改：签名 URL 只作为 `302` 的 `Location` 出现，不进入任何响应体、正文或数据库；正文只写 `/api/media/<id>`，见 D1 |
| D2：bucket、endpoint 是部署配置，不入库 | 继承；新增可选的浏览器侧 endpoint，见 D3 |
| D4：六个 `PALACE_S3_*` 全有或全无；未配置时媒体接口返回 `503 media_storage_unavailable` | 继承；读取接口同样遵守，新增的 `PALACE_S3_PUBLIC_ENDPOINT` 不计入“全有或全无”，见 D3 |
| D4：存储 trait 只有写入和删除 | 修改：增加生成签名 GET URL 的操作，见 D2 |
| D5：删除不检查正文是否仍引用该媒体 | 修改：被业务记录引用的媒体拒绝单独删除，见 D4 |
| D5：读取接口可能遇到行存在而对象缺失，必须按 404 处理 | 继承；302 后由对象存储返回 404，见 D2 |
| 风险：读取时须决定非图片类型的安全展示 | 由本决策回答，见 D2 |

## D1：正文中的媒体引用写成 `/api/media/<id>`

- 正文（Markdown）里引用媒体，地址固定为 `/api/media/<id>`，`<id>` 是小写连字符形式的 UUID。前端 `MarkdownContent` 的 `load` 规则据此识别 Palace 媒体，其余地址按调用方规则处理。
- 写入正文的是应用地址而不是对象地址：更换 bucket、endpoint 或签名方式时不必改写任何正文，这正是根决策 D1 要求的“写进正文的必须是永不变化的标识”。

**为什么不用 `palace-media:<id>` 一类自定义 scheme**：自定义 scheme 需要每个渲染方先把它映射成可请求的地址；而 `/api/media/<id>` 本身就能被 `<img>`、`<video>` 直接请求，正文复制到 Palace 之外的地方也仍是一个可读的路径。代价是正文与 API 路径耦合：将来改动媒体接口路径时，旧路径必须继续可用，见“风险”。

## D2：读取接口校验 Owner 后 302 到现签 URL

`GET /api/media/{id}`：

| 情况 | 响应 |
| --- | --- |
| 当前 Owner 有这条媒体 | `302`，`Location` 为现签 GET URL，`Cache-Control: private, max-age=<到签名对齐窗口结束的秒数>` |
| 不存在或属于其他 Owner | `404` |
| 存储未配置 | `503 media_storage_unavailable` |
| `id` 不是 UUID | `400` |

- 接口和其他业务路由一样同时接受浏览器 Session 与 Access Token。浏览器以 `<img>`、`<video>` 请求时自动带同源 cookie，不需要前端拼接凭据。
- 签名 URL 带 `response-content-type`（取 `media.content_type`）与 `response-content-disposition`：`image/*`、`video/*`、`audio/*` 为 `inline`，其余类型为 `attachment`，文件名取 `file_name`（没有时用 ID）。
- 签名以“当前小时整点”为签名时间、有效期 2 小时，因此同一小时内同一媒体得到同一个 URL，任何时刻拿到的 URL 至少还有 1 小时有效。`302` 的缓存期截止到当前小时结束，浏览器在这段时间内既不重新请求跳转，也能命中对象字节的缓存。
- 读取接口不访问对象存储，签名是本地 HMAC 计算。行存在而对象缺失时（根决策 D5 的中间状态），浏览器跟随跳转后从对象存储得到 404，效果等同 404，Palace 不另做存在性检查。

**为什么是 302 而不是由 Palace 代理字节**：视频需要 Range 请求，代理就得完整转发 Range、`Content-Length` 与断点续传语义，并让每个视频字节都经过 Palace 进程；302 把这些交给对象存储。代价是对象存储的 endpoint 必须能被浏览器访问，见 D3。

**为什么非图片类型用 `attachment`**：`content_type` 由上传方声明，未经验证（根决策 D3）。对象存储与 Palace 不同源，即使以 `inline` 打开 HTML 也拿不到 Palace 的 cookie；但 `attachment` 让“点开一个媒体链接”只会下载，不会在任何源下执行上传方提供的页面。

**为什么签名时间按小时对齐**：每次请求都现签时，`X-Amz-Date` 每秒不同，同一张图每次打开文章都是新 URL，浏览器缓存全部失效。对齐后 URL 在一小时内稳定；2 小时有效期保证在窗口末尾拿到的 URL 也不会在页面加载过程中过期。

## D3：浏览器侧 endpoint

- 新增可选环境变量 `PALACE_S3_PUBLIC_ENDPOINT`（http 或 https URL）。配置时，签名 URL 使用它作为 endpoint；未配置时使用 `PALACE_S3_ENDPOINT`。写入与删除始终使用 `PALACE_S3_ENDPOINT`。
- 它不属于六个变量的“全有或全无”：容器内能直接访问的 endpoint 往往就是浏览器能访问的地址，多数部署不需要它。单独配置它而没有配置存储时，启动失败并指出变量名。

**为什么需要**：签名覆盖 Host，签好的 URL 不能事后替换主机名。服务端在容器网络里通过内部主机名（例如 `http://minio:9000`）访问 MinIO 时，用它签出的 URL 浏览器打不开，只能用浏览器能解析的地址签名。

## D4：被引用的媒体只能随引用方删除

- 业务记录以外键引用媒体（第一个是文章，见文章决策）。`DELETE /api/media/{id}` 在删除对象之前检查引用；被引用时返回 `409 media_in_use`，对象与行都不动。
- 引用方删除时，由引用方的删除流程按根决策 D5 的顺序先删对象、再在事务中删除引用与 `media` 行。
- 引用关系只在引用方创建时与媒体一起写入，此后不会新增（文章的媒体只来自导入请求本身）。因此“检查无引用 → 删除对象”之间不会有新的引用插进来，不需要加锁。

**为什么先检查而不是靠外键 `RESTRICT` 拦截**：根决策 D5 先删对象、后删行。只靠外键时，对象已经删掉，行删除才因外键失败，留下一篇图片永久缺失、却仍然引用该媒体的文章。

## 不变量

1. 正文与数据库中不出现签名 URL、对象 key、bucket 或 endpoint；媒体在正文中的唯一写法是 `/api/media/<id>`。
2. `GET /api/media/{id}` 只对该媒体所属 Owner 的认证上下文返回跳转；其他 Owner 与不存在的 ID 得到相同的 404。
3. 同一媒体在同一小时内的跳转目标相同；任何跳转目标在签发后至少 1 小时内有效。
4. 非 `image/*`、`video/*`、`audio/*` 的媒体通过签名 URL 打开时总是作为附件下载。
5. 被业务记录引用的媒体，其对象与行在引用方删除之前都不会被删除。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| Palace 代理对象字节 | 不暴露对象存储地址；不需要浏览器侧 endpoint | 视频 Range 请求与大文件都要经过 Palace 进程；实现与资源占用都更重 |
| 每次请求现签，不对齐时间 | 实现最简单 | 每次打开文章都是新 URL，浏览器缓存不起作用，视频与大图重复下载 |
| 读取时返回 JSON `{ url }`，由前端再请求 | 前端可以控制何时刷新 URL | `<img>`、`<video>` 不能直接使用正文地址；每个媒体多一次请求和一段前端逻辑 |
| `palace-media:<id>` 自定义 scheme | 正文与 API 路径解耦 | 所有渲染方都要做映射；正文离开 Palace 后不可读 |
| 允许单独删除被引用的媒体，正文显示占位 | 删除接口无需了解引用方 | 产生“引用了不存在媒体”的正文，与“引用方删除时媒体一起删除”的承诺矛盾 |

## 风险与为什么不能直接改写

- **正文与接口路径耦合**：`/api/media/<id>` 已写入正文后，这个路径必须永久可用。将来调整媒体接口时只能新增路径，旧路径保留为同一语义的读取入口，而不是改写所有正文。
- **公网可达的对象存储**：浏览器直接访问对象存储，bucket 必须允许签名 GET；不需要公开读或 CORS（`<img>`、`<video>` 不是 CORS 请求）。
- **签名 URL 泄露**：URL 在有效期内无需登录即可访问，最多 2 小时。它只出现在 `Location` 与浏览器历史/缓存里，不入库、不进正文，可以接受。

## 本决策未解决的问题

- **孤儿对象对账**：导入或上传中途失败留下的对象仍未清理，沿用根决策的风险说明。
- **未被引用的媒体**：`POST /api/media` 上传、尚未被任何记录引用的媒体如何回收，等第二个引用方出现时再定。
- **缩略图与转码**：读取返回原文件，不生成缩略图或转码视频。

## 落地顺序

1. 存储 trait 增加签名 GET；S3 实现按 D2 的对齐时间与响应头签名；配置增加 `PALACE_S3_PUBLIC_ENDPOINT`。完成条件：真实 MinIO 测试中签出的 URL 能取回字节，响应头符合 D2，同一小时两次签名结果相同。
2. `GET /api/media/{id}` 与 `DELETE` 的引用检查。引用检查要等文章的引用表存在才能被真实测试覆盖，因此与文章的导入一起落地。完成条件：真实 PostgreSQL + MinIO 覆盖跨 Owner 404、未配置 503、被引用 409。

上传与删除未被引用媒体的行为保持不变。
