# 对话 Moment 卡片展示来源、Path 消息数与开头两条消息的摘录

时间线上一张对话卡片对应一条 Path，展示该 Path 的标题、Conversation 的来源、该 Path 的消息数，以及该 Path 开头两条消息的纯文本摘录。时间线接口在按天查询 Moment 后，按 `kind` 批量读取这些字段；摘录由服务端截取，不在 `moment` 表中冗余保存。

当前为 `approved`，已通过评审，核心测试用例见[时刻身份与时间线](../../../test-cases/server/moment/moment-timeline.md)。继承[以 `moment` 表承载时刻身份与时间定位](0-moment-supertype-and-typed-details.md)的身份、时间定位与查询方式，具体化其落地顺序第 3 步“批量取对话卡片字段”；标题的归属见[标题从 Conversation 移到 Path](../conversation/20261005-title-belongs-to-path.md)。涉及 `crates/db` 的时间线查询、`palace-server` 的时间线接口与 OpenAPI 契约，以及 `apps/palace-web` 的对话卡片。卡片的打开方式见[Web 导航根决策](../../web/navigation/0-text-nav-day-routes-and-moment-opening.md) D4，视觉参照为 `docs/design/1-prototype.html` 中的对话卡片。

## 继承与修改

| 前序约定 | 本次决定 |
| --- | --- |
| `moment` 只持有身份、类型与时间位置，卡片字段不进入 `moment` | 继承，不变；卡片字段在查询时从详情派生 |
| 时间线按 `occurred_at, id` 排序，再按 `kind` 批量读取详情 | 继承，不变 |
| 同一 Conversation 的多张 Path 卡片共用标题，从 Conversation 派生 | 修改：标题属于 Path，每张卡片显示自己 Path 的标题；来源仍从 Conversation 派生 |
| 卡片上的消息数是整棵树的实际消息总数（Conversation 树与 Path 决策 D2） | 修改：时间线卡片对应 Path，消息数改为该 Path 的消息数，见 D2 |

## D1：卡片字段

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `id` | Moment | 等于 Path ID |
| `kind` | Moment | `conversation` |
| `occurred_at` | Moment | 时间线定位时间 |
| `conversation_id` | Path | 打开阅读页需要 |
| `title` | Path | |
| `source` | Conversation | 界面显示为产品名称 |
| `message_count` | Path | 从根到 Path 末端的消息数 |
| `excerpt` | Path | 开头至多两条消息，见 D3 |

卡片在界面上显示为 `[ 对话 ] 标题`，下一行 `来源 · N 条消息`，再下面是摘录。

## D2：消息数按 Path 计算

前序决策中“消息数是树的实际消息总数”是为会话收藏页的 Conversation 卡片定的，一张卡片代表整棵树。时间线上一张卡片代表一条 Path，同一 Conversation 的不同 Path 可能出现在不同日期；如果每张卡片都显示整棵树的总数，数字与点开后看到的内容对不上。改为 Path 的消息数后，卡片上的数字等于阅读页从这张卡片打开时元信息行显示的数字。

## D3：摘录是开头两条消息的纯文本前缀

- 摘录取 Path 从根开始的前两条消息，每条包含 `role` 和 `text`；Path 只有一条消息时只返回一条。
- `text` 是消息原始内容去掉 Markdown 标记后的纯文本，按 Unicode 标量截取前 120 个字符，被截断时末尾加 `…`；空白折叠为单个空格。
- 去除标记在服务端完成，使所有客户端看到一致的摘录，也避免为了显示几十个字下发整条长消息。
- 界面以“你：…”“来源名称：…”两行展示，每行超出宽度时省略。

选择开头而不是末尾两条消息，是因为开头最能说明这段对话在讨论什么；追加导入只延长 Path，不改变摘录，卡片不会因为续写而面目全非。

## 不变量

1. 卡片的 `message_count` 等于以该 Path 打开阅读页时显示的消息数。
2. 卡片的标题始终等于该 Path 的当前标题，来源始终等于所属 Conversation 的当前来源。
3. 摘录只来自该 Path 的消息，不包含其他 Path 独有的消息。
4. 卡片字段不在 `moment` 或其他表中冗余保存。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 本次取舍 |
| --- | --- | --- |
| 沿用整棵树的消息总数 | 与旧卡片一致 | 时间线卡片代表 Path，总数与打开后看到的内容不一致 |
| 摘录取最后两条消息 | 反映最近的进展 | 追加导入会不断改变卡片内容；结尾常是“谢谢”一类寒暄，不说明主题 |
| 返回完整消息由前端截取 | 服务端无需处理 Markdown | 长消息会让时间线接口的响应体不可控，各客户端的截取结果也可能不同 |
| 在详情表中保存摘录 | 查询更快 | 成为第二份副本，标题与消息变化后需要同步维护；目前的数据量不需要 |

## 本决策未解决的问题

- **由模型生成的摘要**：产品方向提到“简短摘要”，目前用开头两条消息代替，是否引入生成摘要另行决定。
- **Moment 时间的显示**：卡片暂不显示时间，留给 Web 导航根决策的后续决定。

## 落地顺序

1. **查询与契约**：时间线查询按 D1 读取对话卡片字段，OpenAPI 加入对应结构。完成条件：不变量 1、3 有数据库测试，包括同一 Conversation 多 Path 与 Path 在内部节点结束的情况。
2. **摘录处理**：按 D3 去除 Markdown 标记并截取。完成条件：中英文混排、超长消息、只有一条消息的 Path 都有单元测试。
3. **前端卡片**：按 D1 渲染。完成条件：组件测试覆盖摘录两行与一行的情况。

本决策不改变 `moment` 表结构、时间线排序和对话详情接口。
