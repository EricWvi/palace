# 先取当天 Moment 的有序轮廓渲染按类型的骨架，卡片数据到达后逐张由骨架过渡为卡片

新增 `GET /api/timeline/outline`，按与时间线接口相同的 `[start, end)` 区间返回当天 Moment 的轮廓：每项只有 `id` 与 `kind`，顺序与时间线接口的返回顺序一致。时刻页在没有当天缓存时同时发出轮廓与时间线两个请求：轮廓先到，就按每一项的 `kind` 渲染对应形状的骨架；时间线数据到达后，每个骨架在原位置上淡出占位块、淡入真实内容，并把高度平滑过渡到卡片的实际高度，而不是整列表从空白直接换成卡片。

当前为 `implemented`，核心测试用例见[时间线加载过渡](../../../test-cases/server/moment/timeline-loading.md)。本 ADR 继承[对话 Moment 卡片字段](20261004-conversation-moment-card-fields.md)的时间线接口与卡片字段，只新增一个只读接口和时刻页的加载呈现；涉及 `palace-db`、`palace-backend` 的时间线模块与 `apps/palace-web` 的 `TimelinePage`。时间线接口的请求与响应不变，不需要数据迁移。

## 问题与约束

- 时间线请求要在一个可重复读快照里读 Moment、批量读详情、沿 Path 回溯并用 Markdown 解析截取摘录，是时刻页最慢的请求。等待期间页面在日期标题下只有空白，数据一到整列表瞬间出现，页面高度从零跳到几屏。
- 用固定数量的骨架占位并不能解决问题：当天有 1 条时多出来的骨架会塌掉，有 8 条时列表又会突然变长，跳动只是换了个时机。占位要与最终列表一样长、每一项与最终卡片形状相近，才需要事先知道每一项的类型。
- 轮廓只需扫描 `(owner_id, occurred_at, id)` 索引上的 `moment` 行，不读详情，比时间线请求便宜得多。
- Web 端追求文艺、书卷、宁静的气质：加载状态应当安静，不用闪烁的扫光，也不用转圈。
- 骨架只是等待期间的过渡，不能拖慢真实内容出现，也不能改变时刻页已有的地址、焦点与定位约定（[Web 导航根决策](../../web/navigation/0-text-nav-day-routes-and-moment-opening.md) D2）。

## 继承与修改

| 前序约定 | 本决定 |
| --- | --- |
| `GET /api/timeline?start=&end=` 按调用方的本地日区间返回卡片，区间非空且不超过 48 小时 | 继承，不变 |
| 时间线按 `occurred_at, id` 排序，Moment 与卡片在同一快照中读取 | 继承，不变；轮廓接口使用同一排序，但不参与该快照，见 D1、D4 |
| 卡片字段与界面布局（`[ 对话 ] 标题`、来源与消息数、两行摘录） | 继承，不变；对话骨架模仿这一布局，见 D3 |
| 时间线请求未完成时页面在日期标题下留空 | 修改：轮廓到达后显示骨架，见 D2 |
| `moment` 参数在数据加载后把该 Moment 滚到视口中部 | 修改：有过渡时在过渡结束后滚动，见 D5 |

## D1：轮廓接口

响应是数组，每项为 `{ "id", "kind" }`。

- 参数与校验规则和 `GET /api/timeline` 完全相同：`start < end`，跨度不超过 48 小时，违反时返回同样的 400 字段错误。两个接口共用同一个区间类型，并经由同一个 `moment` 扫描完成校验、取区间和排序，避免某一天能取到轮廓却取不到卡片。
- 只读当前 Owner Scope 内的 `moment` 行，不读详情表。
- 按 `occurred_at, id` 排序，与时间线接口相同：在两次请求之间没有写入时，轮廓的第 *i* 项就是时间线的第 *i* 项。`kind` 与时间线项的 `kind` 使用同一个封闭枚举。
- 当天的 Moment 数量就是轮廓的长度，不另设计数字段。
- 响应与时间线接口一样带 `Cache-Control: no-store`。

轮廓带上 `id`，是为了让骨架与卡片按身份而不是按位置对应（见 D4）。`id` 在 `moment` 行上，返回它不增加查询成本；并发写入导致两次请求结果不同时，按 `id` 对应能让每个骨架准确变成它预示的那张卡片。

## D2：两个请求并行，骨架只在没有当天数据时出现

时刻页需要展示某一天、而缓存中没有这一天的时间线数据时，同时发出轮廓和时间线两个请求，不让时间线请求等待轮廓请求。

| 情形 | 页面呈现 |
| --- | --- |
| 缓存中已有当天时间线（包括后台重新验证中） | 直接显示卡片，不请求轮廓，不显示骨架 |
| 轮廓先到且不为空 | 按轮廓显示骨架，时间线到达后按 D4 过渡 |
| 轮廓先到且为空 | 立即显示“这一天还没有记录。”；时间线到达后若不为空，按 D4 的“轮廓中没有的卡片”处理 |
| 时间线先到（或轮廓请求失败） | 直接显示卡片，不显示骨架，也不做过渡 |
| 两者都未到 | 与现在一样在日期标题下留空 |

- 并行而不是串行：串行会让卡片出现的时间整整推迟一次往返，骨架反而成了拖慢内容的原因。
- 骨架不设最短显示时间。时间线紧跟轮廓到达时，骨架只停留一瞬，随即由过渡把它展开成卡片，观感是卡片在原位“长出来”；人为拖住骨架只会推迟真实内容。
- 用左右键快速翻日时，大多数日子还没有缓存，每一天都会走骨架。离开的那一天不做任何退出动画，新的一天从留空或骨架重新开始。
- 轮廓在 React Query 中按日期单独缓存，与时间线一样以日期为键；导入或删除对话后，时间线缓存失效时一并让轮廓失效。

## D3：骨架按类型呈现

- 每一种 `kind` 有且只有一种骨架形状，由 `DayMoments` 中以 `MomentKind` 为键的穷尽映射选择，新增 Moment 类型时必须同时给出它的骨架，否则类型检查失败。骨架只取决于 `kind`，不预示任何 Moment 的具体内容。
- 对话骨架占据与一张对话卡片相同的列表位置与下间距，内部是三组圆角色块：一条标题宽度的条、一条较短的元信息条，以及一块与摘录引用块同样底色和左边线的区域，内含两条文本条。初始高度取一张有两行摘录的对话卡片的典型高度。
- 色块用 `--bg-sunken` 一类已有的 token，不新增颜色。
- 动效是全体骨架同步、缓慢的透明度起伏（约 1.6 秒一个周期），不用从左到右的扫光：扫光在单栏长列表上显得急躁，也与页面安静的气质不符。
- 骨架整体对辅助技术隐藏，列表以 `aria-busy="true"` 标记加载中；数据到达后去掉 `aria-busy`，屏幕阅读器只读到真实卡片。

## D4：骨架按 `id` 过渡为卡片

时间线数据到达后，每个骨架过渡为与它 `id` 相同的卡片。过渡发生在同一个列表项上：列表项以 Moment `id` 为键，骨架与卡片之间不先卸载再挂载，内部内容替换后，列表项的高度从骨架高度过渡到卡片的实际高度，同时占位色块淡出、卡片内容淡入。

- 时长约 280 ms，缓出曲线；所有卡片同时开始，不做逐张错开的入场，以免列表变成一串连续的动画。
- 高度与位置过渡用 Web Animations API 从骨架最后一次布局的位置和高度插值到卡片的实际布局，不引入动画库；动画期间列表项裁切溢出内容，结束后不留任何内联样式或动画，卡片回到普通文档流。
- 过渡期间卡片已经是真实的链接，可以点击；动画不拦截交互。

两个请求不在同一个快照中，期间的导入、删除或追加导入（会改变 `occurred_at`）可能让轮廓与时间线不一致。列表最终的项与顺序只以时间线为准：

| 情形 | 处理 |
| --- | --- |
| 骨架的 `id` 在时间线中存在 | 原位过渡为该卡片；若顺序变化，列表项移动到时间线给出的位置 |
| 骨架的 `id` 不在时间线中 | 高度收拢到零并淡出后移除 |
| 卡片的 `id` 不在轮廓中 | 在时间线给出的位置上高度从零展开并淡入 |

收拢中的骨架停在它在轮廓中的位置，而不是被挪到列表末尾。时间线为空时直接显示“这一天还没有记录。”，不为收拢骨架推迟提示。

不一致只出现在并发写入的窄窗口里，最坏结果是一次多余的展开、收拢或移动，不会显示错误内容：卡片内容始终只来自时间线响应。

在系统设置 `prefers-reduced-motion: reduce`，或浏览器不支持 Web Animations API 时，骨架不做透明度起伏（前者），数据到达后直接替换为卡片，不做高度与透明度过渡。

## D5：失败与定位

- 轮廓请求失败：不显示错误，等同于“时间线先到”，由时间线请求决定页面。轮廓只是装饰性的预告，它的失败不能让一个本可以正常显示的日子报错。
- 时间线请求失败：骨架立即移除，显示现有的错误状态与重试；不对错误状态做过渡。
- `moment` 定位参数：如果这一天走了骨架过渡，等过渡结束、卡片高度稳定后再把目标滚到视口中部；否则在数据到达后立即滚动，与现在一样。过渡中途滚动会因为后续高度变化而停在错误位置。从阅读页返回时当天通常已有缓存，不会经过骨架。

## 不变量

1. 对任意合法区间，同一时刻、同一 Owner 下，轮廓接口返回的序列等于时间线接口各项的 `(id, kind)` 按原顺序组成的序列。
2. 轮廓接口与时间线接口对同一组参数给出相同的校验结论。
3. 每一种 Moment `kind` 恰好对应一种骨架形状。
4. 缓存中已有当天时间线时，时刻页不显示骨架，也不发出轮廓请求。
5. 一旦时间线数据到达，页面上不再有处于加载状态的骨架；不在时间线中的骨架只处于收拢动画中。
6. 页面上显示的卡片及其顺序只来自时间线响应；轮廓请求的成功、失败或与实际不符都不改变显示哪些卡片。
7. 轮廓请求失败不会让页面显示错误状态。
8. `prefers-reduced-motion: reduce` 下，加载与过渡都不产生动画。
9. 有 `moment` 定位参数时，滚动发生在卡片高度稳定之后。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| 固定数量（例如 3 个）骨架，不请求轮廓 | 不新增接口和请求 | 与实际条数不同时列表照样跳动，正是本 ADR 要消除的问题 |
| 只返回数量 `{ "count": n }` | 响应最小 | 骨架无法按类型呈现，有多种类型后形状与卡片相差很大；只能按位置对应，并发写入时骨架会变成别的卡片 |
| 轮廓只返回有序的 `kind`，不带 `id` | 响应更小 | 同样只能按位置对应；`id` 已在索引行上，带上它没有额外查询成本 |
| 时间线接口改为流式响应，先发轮廓再逐条发卡片 | 一个请求同时得到骨架与卡片 | 生成的 OpenAPI 客户端和 React Query 缓存都按整体 JSON 工作，流式响应要为一个加载动画重写这两层 |
| 把上次看到的当天轮廓记在浏览器本地存储 | 不需要新接口 | 首次访问某天时没有数据，最需要骨架的情形反而退化为空白；跨设备不一致 |
| 轮廓与时间线串行请求 | 骨架必定先于卡片出现 | 卡片出现时间推迟一次往返，骨架拖慢了真实内容 |
| View Transitions API 在骨架与卡片快照之间过渡 | 声明式，不需要手动测量 | 快照按图片缩放，骨架与卡片高宽比不同时文字会被拉伸；过渡期间整页快照覆盖在上面，卡片暂时不能点击 |
| 引入 Framer Motion 一类布局动画库 | 布局过渡开箱即用 | 为一处过渡引入数十 KB 依赖；高度过渡用浏览器原生的 Web Animations API 即可完成 |
| 只优化时间线查询的速度 | 从源头缩短等待 | 与本 ADR 不冲突；即使查询变快，网络往返仍然存在，空白到满屏的跳动依旧 |

## 本决策未解决的问题

- **翻日时的过渡**：本 ADR 只处理同一天内骨架到卡片的过渡，日期切换时整列表的退场与入场动画不在范围内。
- **原地展开型 Moment**：原地展开详情的高度过渡是否复用 D4 的实现，等第一个原地展开的类型出现时决定。

## 落地与验收

`palace-db` 的 `day_outline` 与 `timeline` 共用同一个 `moment` 扫描；`palace-backend` 提供 `GET /api/timeline/outline` 并进入 OpenAPI 契约。前端的轮廓查询键位于当天时间线键之下，导入、编辑与删除使时间线失效时一并失效；`DayMoments` 负责骨架、卡片与两者之间的过渡，`TimelinePage` 只负责并行请求和定位。时间线接口、卡片内容、地址与焦点行为保持不变。

真实 PostgreSQL 与 HTTP 测试证明不变量 1、2；组件测试覆盖 D2 的各个到达顺序与失败情形；真实 Chromium 测试覆盖按 `id` 原位过渡、轮廓不符时的收拢、展开与移动、过渡后不留内联样式、减少动态效果，以及过渡结束后才滚动定位。仍缺直接证据的部分见核心测试用例。
