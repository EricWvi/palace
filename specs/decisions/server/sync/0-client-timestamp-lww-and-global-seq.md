# 使用前端毫秒时间戳 LWW 与 PG 全局序列同步知识记录，冲突按整条记录覆盖

Palace 第一版由 Web client 生产知识记录，server 使用 PostgreSQL 保存；未来客户端使用 SQLite 消费并保存记录。本决策采用前端生成的毫秒级 `updatedAt` 做整条记录 LWW（Last Write Wins），以 PostgreSQL 全局 sequence 分配的 `serverVersion` 拉取增量。可写客户端先本地落库并标记待同步，每轮先上传再拉取；删除通过 `isDeleted` 传播，客户端收到删除直接执行，不比较时间戳。

当前为 `approved`，决策已经评审通过但尚未实现；对应核心测试用例用于跟踪实现证据。影响 Web client/server、未来客户端本地数据库及知识记录同步流程。本文件是 `server/sync` 的根决策，没有前序 ADR；第一版建立新协议，不承诺兼容其他同步协议或迁移既有产品数据。哪些记录开放客户端编辑及多记录结构变更留给后续决策。

## 问题与约束

Web client 负责知识记录的导入、修改与删除；服务端保存已接收的知识记录，向未来客户端提供增量。客户端需要在断网后继续使用已下载的记录，并在恢复连接后追上服务端变化。客户端的本地编辑也应先持久化，网络失败不能让修改只留在内存中。

不同设备可能离线修改同一条记录。第一版接受其中一个完整版本胜出，不维护编辑历史或合并不同字段；设备时钟决定胜负，服务端接收先后仅用于发现增量。Conversation 与 Message 的父子结构不能仅靠逐记录 LWW 推断，结构性编辑和级联删除需要后续协议明确事务边界。

## D1：Web 生产、客户端消费，记录身份独立于展示内容

| 概念 | 本决策中的含义 |
| --- | --- |
| 生产者 | Web client；产生修改，server 校验、持久化并分发 |
| 消费者 | 未来使用 SQLite 的客户端；第一阶段拉取知识记录并保存在本地 |
| 知识记录 | 具有稳定 `id` 的同步对象；Conversation 与 Message 是当前已知类型 |
| 待同步 | 本地修改尚未获得服务端明确处理结果的持久化状态 |
| 删除标记 | `isDeleted = true` 的记录，服务端保留以向离线客户端传播删除 |

`id` 在本地首次创建时生成，跨重试与设备保持稳定；修改标题、Markdown 内容或父子关系不通过创建同类型新 ID 偷换已有记录身份。服务端按[Owner 与数据隔离](../owner/0-authelia-identity-and-owner-scoped-records.md)在 Owner Scope 内判定冲突，客户端不得通过自报归属写入或拉取其他 Owner 的数据。知识记录 ID 的具体格式另行设计。

第一阶段客户端没有知识记录写入职责，其上传阶段为空。本地建立搜索索引、缓存渲染结果或改变存储路径均不产生业务修改，不改写 `updatedAt`。可写客户端的同步规则先用于 Web client，不据此开放所有客户端编辑。

## D2：业务版本由 `updatedAt` 决定，等值保留接收方已有版本

`updatedAt` 是产生业务修改的前端所记录的 Unix epoch 毫秒整数，服务端不替换为接收时间。新记录可直接接收；已有记录仅在传入时间戳严格更大时被整条覆盖。比较与写入必须原子完成，不能让并发上传基于过期读取分别覆盖。

| 接收情形 | 处理 |
| --- | --- |
| 本地或服务端不存在该 `id` | 接收传入记录；删除按 D5 处理 |
| 传入 `updatedAt` 大于已有值 | 接收完整业务记录，覆盖原业务字段 |
| 传入 `updatedAt` 小于已有值 | 保留已有业务记录 |
| 传入 `updatedAt` 等于已有值 | 保留已有业务记录，即使内容不同 |
| 客户端收到 `isDeleted = true` | 直接删除，优先于以上时间比较 |

整条覆盖包括该记录自身的业务字段，不对标题、内容等字段分别合并。`serverVersion`、待同步状态和本地派生索引属于同步或设备状态，不随业务记录整体复制；传入版本被忽略时，也可记录其处理结果或推进拉取游标。

例如 A、B 分别持有相同 `updatedAt`、不同标题的记录，交换后仍各自保留原值。协议不使用设备 ID 或 `serverVersion` 打破平局，因此不承诺所有副本最终内容一致。一次更新也可能覆盖另一设备对不同字段的修改，这是整条 LWW 的明确代价。

## D3：本地先落库，每轮先上传，再拉取

本地业务修改与待同步标记在同一事务持久化。上传发送持久化记录的快照；断网、超时和重启后仍能重试。同一客户端、同一同步范围只运行一轮同步，用户编辑可与网络请求并发。

服务端对每条上传返回明确结果：接收新版本、保留已有版本，或失败。保留已有版本是已处理的冲突结果，应返回服务端当前记录，使客户端即使已拉过其 `serverVersion` 也能按 D2/D5 处理；网络成功不能等同于记录写入成功。失败项继续待同步，已明确处理项可独立确认。一轮有限上传尝试结束后可以拉取，避免单个失败项长期阻塞消费。

上传确认在本地事务中重新核对 `updatedAt`，仅当当前记录仍是已发送的版本时清除待同步标记。为覆盖同毫秒内连续修改、时钟回拨及删除后重建，还必须核对持久化的本地修改代次；每次本地业务修改推进代次。代次只保护本地确认，不参与跨设备 LWW，也不打破时间戳平局。

例如上传快照时间为 `1000`，响应前用户改成 `1001`，旧响应不能清除新修改的待同步状态。同毫秒再次修改时，代次不同也不能清除。确认服务端已处理一个版本，只表示无需重传这个版本，不表示所有设备内容一致。

上传结果中的服务端当前记录按接收时的本地状态应用，不能无条件覆盖上传期间的新编辑。普通远端记录只有严格更新才覆盖本地并取代相应待同步修改；本地更新时保留待同步状态。删除例外见 D5。

## D4：`serverVersion` 使用 PG 全局 sequence，并保证提交可见顺序

所有进入本同步域的服务端有效记录变更，包括删除，使用同一个持久化 PG `bigint` sequence 分配 `serverVersion`。序列正向递增、不循环、`CACHE 1`；起始拉取游标为 `0`。只为实际接收的状态变化分配新版本；旧版本、等值上传和重复确认不制造业务变更。序列允许空洞，客户端不能等待缺失数字。跨 Web/客户端协议以十进制字符串无损传递版本，比较时按整数处理。

`serverVersion` 仅是增量发现顺序，不是冲突裁决依据。服务端写记录与记录版本在同一事务提交，响应只能报告已提交结果。

单独调用 `nextval()` 不足以安全推进游标：事务 A 取 `41` 尚未提交，事务 B 取 `42` 并提交，客户端拉到 `42` 后，晚提交的 `41` 将被永久跳过。这是基于 PG sequence 语义推导的失败场景；PG 明确规定取号不会因回滚而回收，并且大于一的缓存可能跨会话乱序。[Sequence 函数](https://www.postgresql.org/docs/current/functions-sequence.html)、[CREATE SEQUENCE](https://www.postgresql.org/docs/current/sql-createsequence.html)。

第一版所有同步写入必须先获取同一数据库事务级互斥锁，在锁内读取当前已提交状态、完成 LWW 判定、分配版本并写入，持锁到提交或回滚。禁止预先取号、绕过该入口写同步记录，或在锁内执行外部网络请求。事务级 advisory lock 可承载此规则，其生命周期由数据库事务管理。[PG 显式锁](https://www.postgresql.org/docs/current/explicit-locking.html)。此处选择全局串行发布，换取简单且不会漏记录的游标；吞吐瓶颈留待有数据后评估。

拉取按固定 Owner Scope 查询已提交的 `serverVersion > cursor`，按版本升序分页，返回记录的当前完整状态（含删除标记），不承诺交付每个中间版本。客户端只能将游标推进至这一页实际处理到的最后版本；空页保留原游标。禁止用 sequence 当前值或上传响应版本直接推进拉取游标。

每页记录应用、本地派生任务持久化和游标推进必须在本地同一事务完成。被 D2 忽略的记录也算已处理；事务失败整页重试。耗时派生任务无需在此事务中完成，但不能只推进游标而丢失任务。首次从 `0` 拉取现存记录与删除标记；Owner Scope 变化时须重新建立对应同步范围，不能直接复用旧游标。

## D5：服务端保留删除标记，客户端收到后直接删除

生产者本地删除先落为 `isDeleted = true` 的待同步记录，收到服务端处理结果前不能直接丢失删除意图。上传删除在服务端仍按 D2 的时间戳规则接收：较旧或等值删除不会覆盖已有记录；删除被接收后获得新 `serverVersion`，以删除标记长期保留。第一版不清理服务端删除标记。

客户端收到服务端删除标记时，不比较本地 `updatedAt`，直接删除本地业务记录和对应待同步修改，并取消该记录的派生任务。即便本地编辑更新、尚未上传，也以收到的删除为准；服务端上传冲突结果携带的删除标记同样适用。重复接收删除应无害，后续旧上传响应不能重建已删除记录。

这不是永久禁止恢复：服务端仍可接收比删除标记时间更新的非删除记录。同一 ID 是否提供显式恢复操作留给后续产品决策；按当前 LWW 规则，更新的离线副本可能重新建立记录，不能宣称删除全局永久胜出。

## 不变量

1. 同一记录的普通冲突仅由 `updatedAt` 的严格大小决定，相等保留接收方已有业务值。
2. 本地业务修改与待同步状态一起持久化，上传确认只清除所发送的本地修改代次。
3. 服务端有效变更与 `serverVersion` 原子提交，发布更高版本后不会再发布更低的新版本。
4. 拉取游标只覆盖已在本地持久化处理的增量，记录处理与派生任务不会因崩溃被游标跳过。
5. 客户端收到删除标记直接删除本地记录，服务端保留删除传播依据。
6. 第一阶段客户端的本地索引、缓存与存储管理不修改生产者的知识记录。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 本次取舍 |
| --- | --- | --- |
| 服务端接收时间 LWW | 不依赖设备时钟 | 离线旧操作晚到会胜出；本项目选择前端修改时间表达版本先后 |
| 字段级合并或 CRDT | 可保留更多并发编辑 | 需要逐字段定义合并语义及元数据；第一版明确接受整条覆盖的损失 |
| 相同时间戳按设备 ID 决胜 | 可提供确定性平局收敛 | 改变“相同时间戳保留各自已有值”的项目规则 |
| 按 `updatedAt` 拉取 | 少维护一个版本字段 | 回拨或落后设备的新上传可能小于游标而漏拉，必须独立记录服务端发布顺序 |
| 无发布互斥的 PG sequence | 写入并行度更高 | 取号与提交错序会漏拉，无法满足游标不漏记录的承诺 |
| 每轮全量复制 | 不需要增量游标 | 重复扫描和传输随知识库规模增长；全量重建只用于重新建立同步状态 |
| 客户端保留墓碑并按时间比较删除 | 可保护较新的本地编辑 | 改变客户端收到删除直接执行的既定语义 |

## 风险与为什么不能直接改写

设备时钟领先可能压制其他设备很长时间，时钟回拨可能让新编辑输给旧版本；同毫秒不同内容可能永久分歧。本地修改代次只防误确认，不能修复这些业务冲突。当前接受这些限制，不把该协议描述为无损合并或无条件最终一致。

全局写锁限制发布吞吐，服务端删除标记长期占用存储。锁等待或事务失败应返回可重试失败，不能旁路锁继续发布。客户端删除可丢弃本地未上传编辑；恢复与结构性删除需要额外生命周期规则。

投入使用后，不能直接重置 sequence、清空删除标记、改变时间单位或替换 ID，否则既有游标和身份会失效。需要此类改动时先记录后续 ADR，明确协议或同步范围的新版本；保全生产者待同步数据，再使受影响客户端重建快照和游标。备份恢复导致版本历史倒退时也必须使旧游标失效，不能把旧游标继续用于已回退的数据。

## 本决策未解决的问题

- Conversation、Message 与导入路径的原子同步和删除顺序：涉及跨记录语义，不能直接推定整条覆盖已满足需求。
- 共享知识库、成员权限与设备撤销：Owner 根决策只覆盖单一 Owner Scope，协作授权另行决定。
- 附件和其他二进制内容的传输、存储与回收：第一版对话导入只保存 Markdown 字符串。
- 时钟异常提示、冲突展示与显式恢复：当前记录其影响，后续决定用户如何观察和处理。
- 同步协议升级及快照重建协议：当前确立需要重建的边界，具体协商机制另行设计。

## 落地顺序

1. 实现记录同步闭环：覆盖本地待同步、逐条上传结果、并发确认、PG 发布顺序、分页与删除。完成条件为对应核心义务有直接验证证据。
2. 补充对话树多记录协议：明确父子记录创建、路径导入和级联删除的事务与拉取顺序，再开放 Conversation/Message 完整同步。
3. 按验证结果同步文档并转为 `implemented`：完成条件为记录闭环已验证，明确剩余边界，删除不再成立的实现推测。
