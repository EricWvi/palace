# 回响页是加宽的札记瀑布流，左列顶部叠放当天固定的回顾卡片，新建与搜索只有快捷键，数据来自专用的实时读取接口

「回响」导航变为可点击，进入札记（Jotting）的浏览页。页面比 Palace 其他页面宽，约 1200px，页头随之伸展。左列从上到下是 5 张当天固定的回顾卡片、札记统计与 12 周热力图、常用标签；右侧是札记的多列瀑布流，按 `created` 从新到旧排列，长札记在卡片内原地折叠和展开，不设详情页。点击卡片组会把卡片向右平铺，盖在变暗的瀑布流上；平铺后点击某张卡片，它会原地放大显示全文，关闭后这张卡片在本次页面会话中不再出现。`n` 新建札记，`/` 搜索，两者都没有可见入口。新建时正文里的 `#标签` 会提取为标签。页面的数据来自服务端新增的札记读取接口，每次按需查询，不复用移动端的增量同步接口。

当前为 `approved`，核心测试用例见[札记读取接口](../../../test-cases/web/echo/jotting-reading.md)和[回响页](../../../test-cases/web/echo/echo-page.md)。视觉与交互参照 `design/4.1-echo.html` 的变体 B「热力图与统计」（示例数据在 `design/4-echo-data.js`）。本文件是 `web/echo` 的根决策，没有前序 ADR。它修改 [Web 导航根决策](../navigation/0-text-nav-day-routes-and-moment-opening.md) D1 中“回响不可点击”的约定，并承接[札记根决策](../../server/jotting/0-jottings-indexed-from-git-commits.md)“本决策未解决的问题”中的“Web 回响页”：读取接口由本决策定义（D8），札记根决策的同步与上传接口保持不变。回顾卡片的已读状态只存在前端内存中，卡片组也不在服务端持久保存；正式的选取规则和跨设备已读留给后续决策。

## 问题与约束

- 札记是标题可选的短文，大多只有几行，少数有十几段。用时间线式的单列阅读，一屏只能看到几张；用摘星那样的目录式列表，又看不到正文，而短札记的价值恰恰在正文。
- 回响的意思是让旧札记重新出现。只按时间倒序浏览时，旧札记会沉到底部，再也看不到，所以页面需要一个主动把旧札记推到眼前的位置。
- 札记由本地 Agent 整理：移动端或 Web 上传的札记先进入 `inbox/`，Agent 稍后移动、改写并 commit（札记根决策 D4）。用户需要看出哪些札记还没整理，但这只是一个暂时状态，不应该占据卡片的主要空间。
- 标签会越积越多，侧栏必须在标签数量增长后仍然放得进一屏。
- Web 是在线、实时的：它不保存札记的本地副本，每次打开或筛选都直接查询服务端。札记根决策的 `changes` 接口是为离线移动端设计的增量同步协议，不包含路径，也不提供搜索与统计。
- Palace 只有一个用户，而且这个用户熟悉快捷键。美观简洁优先于可发现性，这与 Web 导航根决策的约束相同。
- 页宽变化发生在 SPA 内部导航时，可以做成动画；原型运行在 `file://` 下，无法跨页面播放动画，因此在页内用「时刻 / 回响」原地演示。

## D1：回响页加宽，页头随之伸展

- 回响页的页面容器最大宽度约为 1200px，Palace 其他页面是 760px。页头在页面容器内部，随页面一起伸展，读起来像同一张纸改变了尺寸，而不是换了一个页面。
- 在「时刻」和「回响」之间切换时：旧内容先淡出（约 150ms），页宽变化（约 400ms，比其他页面常用的 300ms 慢，因为移动的距离更长），新内容再淡入。系统开启“减少动态效果”时，所有过渡都是瞬时的。
- 地址是 `/jottings`。摘星的各类内容用内容类型作为路径（`/notes`、`/conversations`），这里保持一致。

**为什么加宽**：瀑布流至少要放下三列卡片，左列还要放下回顾卡片组；760px 只够放一列半。只让回响页加宽，其他页面保持适合阅读长文的宽度。

## D2：左列加瀑布流的两栏布局

- 左列宽约 180px，滚动时固定在页面顶部（`sticky`），从上到下依次是回顾卡片组（D3）、统计与热力图（D5）、标签（D5）。
- 右侧瀑布流的卡片最小宽约 260px，列数随宽度变化。每张卡片按 `created` 从新到旧依次放进当前最短的一列，因此从左到右、从上到下大致是从新到旧。滚动到底部时按 D8 的游标加载下一页，新的一页继续放进最短的列，已经放好的卡片不移动。
- 卡片正文超过 8 行时折叠，截断处做渐隐，下面显示“展开”；展开和收起都在原地带高度动画完成。**没有札记详情页**：札记很短，跳转到详情再返回的成本比阅读本身还高。
- 视口宽度 ≤ 720px 时变成单列：左列移到上方，瀑布流只有一列。

## D3：今日回响——5 张当天固定的卡片

- 左列顶部叠放 D8 回顾接口返回的卡片（最多 5 张），最上面一张几乎是正的，下面几张有轻微的错位和旋转，看起来像从抽屉里随手摸出的一叠旧卡片。卡片尺寸统一，正文截断并渐隐，卡片上的标签不能点击。
- **点击卡片组**：卡片依次向右平铺，浮在瀑布流第一排上方，瀑布流变暗。卡片组保持展开，直到点击卡片以外的任何地方。这次点击会被拦截，不会同时触发下面瀑布流里的标签或“展开”。
- **平铺后点击一张卡片**：卡片从原来的位置放大到屏幕中央，显示全文。点击背景或按 Escape 关闭。关闭时，内容缩回卡片原来的位置并淡出，这张卡片离开卡片组，后面的卡片左移补位。**关闭即算读过**。
- 全部读完后，卡片组换成一行“今天的回响都已看过”。
- **已读状态只存在前端内存中**：刷新或重新进入回响页后，卡片组恢复完整。卡片组本身由服务端按日期确定（D8），所以刷新后看到的仍是同一组卡片。
- 有标签筛选或搜索时，卡片组收起；筛选清除后，卡片组再展开。
- 手机上没有悬停，也放不下错位叠放，卡片组改为一行可以横向滑动的卡片，点击直接放大阅读。

**为什么当天固定**：每次打开都重新抽卡，用户会忍不住一直刷新，卡片就变成了老虎机，而不是回顾。固定一组、读完即止，让回顾成为一件每天可以做完的小事。

**为什么已读暂时只放在内存中**：持久化已读需要决定存在哪里、按天如何过期、多设备之间是否共享，而这些都依赖正式的选取规则，见“本决策未解决的问题”。在那之前，“刷新后卡片组恢复”的代价只是重新看到几张已经读过的卡片，不影响任何数据。

**为什么关闭就算读过**：没有“标记已读”按钮。用户已经点开了全文，再要求一次确认就是多余的操作。

**为什么筛选时收起**：用户在找某样东西时，不是偶遇旧札记的时候。收起卡片组也让筛选结果从页面顶部开始。

## D4：卡片的内容与状态

- 卡片依次显示标题（有标题时）、正文 Markdown（段落、引用、列表、行内代码、粗体、斜体）和页脚。页脚是时间加标签，标签可以换行。
- **时间**：7 天以内显示相对时间（刚刚、N 分钟前、N 小时前、N 天前），悬停时浮出完整时间；超过 7 天直接显示 `YYYY-MM-DD HH:mm`。提示浮在锚点上方，不会让卡片重新排版。回顾卡片太窄，超过 7 天只显示日期，相对时间不带提示，因为点开就能看到全文。
- **待整理**：D8 返回的 `pending` 为 `true` 时，卡片右上角显示一个小圆点，悬停时显示“待整理”。不在页脚里写文字。
- 页脚里的标签可以点击，点击后按该标签筛选（D5）。

**为什么待整理是圆点**：待整理是卡片的一个暂时状态，不是札记本身的属性。如果写进页脚，它会占用标签的位置，还可能在换行后单独落到一行；放在角落的内边距里，它不占任何排版空间。

**待整理的判定依据是路径，而不是 commit 状态**：Agent 有可能把上传的札记原样 commit，但还没有移出 `inbox/`，这时它仍然没有整理。所以 `pending` 表示札记文件位于札记目录的 `inbox/` 下，由服务端根据索引中记录的路径计算（D8）。

## D5：左列——统计、热力图和前 8 个标签

- **统计**：三个数字并排，依次是札记总数、标签总数、有札记的天数。
- **热力图**：最近 12 周，每列一周，周一在上，当前这一周在最右侧。每格按当天的札记数分为 0、1、2、3 及以上四档颜色；今天之后的格子留空。悬停时显示 `YYYY-MM-DD · N 张`。热力图只用来看，不能点击。
- **标签**：按札记数量降序列出前 8 个标签，数量相同的按名称排序，每个标签后面显示数量。当前筛选的标签不在前 8 个时，额外追加一行，保证筛选状态始终可见。
- 标签末尾是“全部标签 N”。点击后，右侧的瀑布流换成全部标签视图：标签以 `#标签 (数量)` 的形式像段落一样连续排列。在这个视图中，搜索输入会实时过滤标签。
- 在任何位置（侧栏、卡片页脚、全部标签视图）点击一个标签，都会回到瀑布流并按该标签筛选；再次点击当前筛选的标签则清除筛选。
- 左列不提供“待整理”筛选：待整理靠卡片上的圆点辨认，整理是 Agent 的工作，Web 上没有需要逐张处理待整理札记的场景。

**为什么是统计与热力图**：原型比较过“待整理入口 + 标签”和“统计 + 热力图 + 标签”两个变体。热力图让人一眼看到最近写得多还是少，与“回响”的回顾意图一致；待整理入口服务的是整理工作，而整理不在 Web 上进行。

**为什么只列 8 个标签**：常用标签数量增长得很慢，长尾标签却越来越多。如果全部放进侧栏，侧栏迟早会超过一屏，常用标签也会被淹没。长尾标签只在偶尔查找时用到，放进一个宽视图里横向排列，比一个很长的竖列更容易扫读。

## D6：`n` 新建札记，`#标签` 写在正文里

- 按 `n` 会在瀑布流上方滑出输入框并获得焦点。Ctrl/Cmd + Enter 提交。输入框为空时，按 Escape 或失去焦点会收起；已有内容时两者都不收起，草稿保留。
- 正文中以空白或行首开头的 `#词`（`#` 后面连续的非空白、非 `#` 字符）会提取为标签，并从正文中移除，标签按出现顺序去重。`# 标题`（`#` 后面跟空格）、`C#`、`a.html#x` 都不会被识别为标签。提取后只清理标签留下的空白，其余正文原样上传。
- 光标前正在输入 `#片段` 时，下方列出包含该片段的已有标签（最多 6 个），可以用 ↑↓ 选择，Enter 或 Tab 确认，Escape 关闭列表。候选来自 D8 的标签统计。
- 提交时调用 `POST /api/jottings`：`id` 是客户端生成的 UUIDv7，`created_at` 是提交时刻，没有 `title`。新札记写入 `inbox/`，所以带有待整理圆点，并以高度动画出现在第一列顶部；统计、热力图和标签数量随之刷新。如果当前有筛选或搜索，先清除它们，保证新卡片一定能被看到。

**为什么用 `#标签`**：单独的标签输入框需要在两个输入框之间切换焦点，打断连续书写。行内 `#标签` 是 flomo 的习惯写法，写的时候顺手，也不需要任何可见控件。

## D7：`/` 搜索，没有可见入口

- 按 `/` 会滑出搜索框并获得焦点；如果新建的输入框是空的，就先把它收起。
- **只有按 Enter 才会执行搜索**，输入过程（包括输入法组字）不会改变瀑布流。搜索由 D8 的列表接口在服务端完成；命中的文字在渲染后用 `<mark>` 高亮，因此不会拆开 Markdown 结构。
- 搜索可以和标签筛选叠加，两者取交集。瀑布流上方的筛选行显示当前条件（`#标签 · “关键词”`）、命中数量和“清除”。
- 在搜索框中按 Escape：有内容时先清空，再按一次收起。在页面上按 Escape（焦点不在输入框中）会依次退出：放大的卡片 → 平铺的卡片组 → 全部标签视图 → 标签筛选。
- 焦点在输入框中，或者按下了修饰键时，`n` 和 `/` 都不会触发。

**为什么没有可见入口**：同摘星入口页，Palace 只有一个熟悉快捷键的用户，界面上每多一个按钮，都是在替用户做一次“你可能需要它”的假设。

**为什么按 Enter 才搜索**：瀑布流在每次输入时重新排版，会产生剧烈的跳动；中文输入法组字时，中间状态也不是有意义的查询，还会产生无意义的请求。全部标签视图是例外：标签统计已经在前端，标签数量少，列表只是在原地变短，所以实时过滤。

## D8：服务端为 Web 提供实时读取接口

新增三个只读接口，读取札记索引的当前状态，不读 Git 和工作区，不包含 tombstone。访问范围同札记根决策 D7。札记在响应中统一为：

```json
{ "id": "…", "created_at": 1760841000000, "title": null, "tags": ["阅读"], "body": "…", "pending": false }
```

`created_at` 是 epoch 毫秒，`pending` 见 D4。

**列表与搜索** `GET /api/jottings?tag=<标签>&q=<关键词>&cursor=<游标>&limit=<n>`

- 按 `created_at` 降序、`id` 降序返回札记；`id` 用来打破同一毫秒的并列，保证分页顺序稳定。
- `tag` 只返回带该标签的札记，精确匹配。`q` 在标题、正文和标签中做忽略大小写的子串匹配；不做分词，因为中文短文用子串匹配已经足够，且结果可以预测。两者同时出现时取交集。
- 响应为 `{ jottings, total, next_cursor }`。`total` 是满足条件的札记总数，供筛选行显示；`next_cursor` 为 `null` 表示没有下一页。游标对客户端不透明，编码最后一张札记的 `(created_at, id)`。
- `limit` 默认 60，上限 200。

**概览** `GET /api/jottings/overview?from=YYYY-MM-DD`

- 响应为 `{ total, days, tags, daily }`：`total` 是札记总数；`days` 是有札记的天数；`tags` 是全部标签及其札记数 `[{ name, count }]`，按数量降序、名称升序；`daily` 是从 `from` 到今天每一天的札记数 `[{ date, count }]`，没有札记的日期也列出。
- 日期按 `PALACE_TIMEZONE` 的本地日期计算。热力图的起点（12 周前的周一）由前端计算后作为 `from` 传入，服务端不关心周的划分。
- 侧栏的前 8 个标签、全部标签视图和新建时的标签补全都来自同一份 `tags`，前端不再单独请求。

**今日回响** `GET /api/jottings/recall`

- 响应为 `{ date, jottings }`：`date` 是 `PALACE_TIMEZONE` 下的今天，`jottings` 是最多 5 张札记。
- **候选**是 `created_at` 早于今天零点的全部札记。今天新建的札记不参与，否则当天的每一次新建都可能改变卡片组；它们本来也不是“回响”。
- **选取**：对每个候选计算 `SHA-256(date ‖ id)`，按摘要升序取前 5 张，返回顺序即摘要顺序。只要候选集合不变，同一天的任何请求都得到同一组、同一顺序的卡片；不同日期的结果彼此无关。候选不足 5 张时全部返回。
- 结果不持久保存，每次请求时计算。札记被 Agent 修改时返回最新内容；被删除或当天有旧日期的札记进入索引（例如移动端补传离线时写的札记）时，卡片组可能随之变化，这在没有持久化的前提下可以接受。

**为什么不复用 `changes` 接口**：`changes` 服务于离线客户端，语义是“自游标以来的变化”，前端要先拉取全部札记再在浏览器中排序、筛选、统计，首屏成本随札记总数增长。它的响应也有意不包含路径，无法判断待整理。Web 始终在线，直接按页面需要查询，让排序、搜索和统计都留在 PostgreSQL 中，同步协议也不必为 Web 的需求改动。

**为什么用摘要排序而不是带种子的随机数**：按 `(date, id)` 的摘要排序不需要服务端保存任何状态，也不依赖数据库返回的行序或随机数生成器的实现；同一组输入总是得到同一组输出，测试可以直接断言结果。

## 不变量

1. 同一天之内，只要候选札记没有变化，回顾接口每次返回同一组札记，顺序相同。
2. 今天新建的札记不会出现在今天的回顾卡片组中。
3. 在一次页面会话中，读过的回顾卡片不会再次出现；刷新页面后卡片组恢复完整。
4. 瀑布流中的札记总是按 `created_at` 降序、`id` 降序排列，分页加载不会重复或遗漏札记。
5. 待整理圆点出现，当且仅当札记文件位于札记目录的 `inbox/` 下。
6. 列表接口在同时给出 `tag` 和 `q` 时，返回的札记同时满足两者，`total` 与可翻页得到的札记数一致。
7. 筛选状态始终可见：当前筛选的标签一定出现在侧栏中，并且筛选行显示当前条件。
8. 收起平铺卡片组的那次点击，不会同时触发瀑布流中的其他操作。
9. 新建提交后，新札记一定出现在可见的瀑布流中。
10. 新建时提取出的标签不会留在正文中；不以空白或行首开头的 `#`，以及后面跟空格的 `#`，都不会被提取；正文的其余部分原样上传。
11. 有内容的草稿不会因为 Escape 或失去焦点而丢失。
12. Web 读取接口不改变 `changes` 接口的行为和响应。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| 回响页沿用 760px 单列，像时刻一样阅读 | 与其他页面宽度一致，切换导航时不需要动画 | 一屏只能看到几张短卡片，回顾卡片组也没有位置；短札记适合并排扫读 |
| 目录式列表（同摘星），点开读全文 | 与摘星的样式统一 | 很多札记没有标题，目录里只能显示截断的正文；札记的价值在正文，多一次点击就少一半的偶遇 |
| 札记详情页 | 长札记有完整的阅读空间 | 绝大多数札记不足 8 行；原地展开已经能覆盖长札记，而且不会丢失滚动位置 |
| Web 用 `changes` 拉取全部札记，在浏览器中计算 | 不需要新接口，原型就是这样做的 | 首屏随札记总数增长；同步响应不含路径，要支持待整理就得改动移动端协议；Web 不需要离线副本 |
| 每次打开都随机抽卡 | 回顾的内容更多 | 会诱导用户反复刷新，回顾就没有“做完”的时候，见 D3 |
| 服务端持久保存每天的卡片组 | 卡片组在新增、删除札记后也不变 | 需要新表和过期规则，而选取规则本身还会改；摘要排序已经满足“同一天同一组”的主要场景 |
| 已读状态存到服务端或 `localStorage` | 刷新后不重置；存服务端还能跨设备 | 需要先确定选取规则和过期方式；在规则确定前持久化，只会留下需要迁移的数据 |
| 左列放“待整理”筛选入口（原型变体 A） | 能集中查看未整理的札记 | 整理由 Agent 完成，Web 上没有逐张处理的场景；圆点已经足够辨认 |
| 回顾卡片组始终显示，不随筛选收起 | 位置稳定 | 查找时会占据注意力，筛选结果也被往下推 |
| 显式的“已读”按钮 | 关闭和已读互不影响 | 打开全文本身已经是读过的意思，多一个按钮违背界面简洁的约束 |
| 待整理写在页脚里，或作为一个标签 | 不需要悬停就能看懂 | 会和标签争抢空间，换行后可能单独落到一行；作为标签还会混进标签统计和筛选 |
| 侧栏列出全部标签 | 不需要额外的视图 | 标签增多后会超过一屏，常用标签被淹没 |
| 单独的标签输入框 | 结构清晰，不需要解析正文 | 打断连续书写，而且需要一个可见控件 |
| 搜索随输入实时执行 | 反馈更快 | 瀑布流每次输入都重新排版，输入法组字的中间状态也会触发请求 |
| 右下角的“+”按钮和放大镜图标 | 新用户可以发现 | Palace 只有一个熟悉快捷键的用户；同摘星入口页的取舍 |

## 风险

- **输入框所在抽屉的裁剪方式**：抽屉的展开动画需要裁剪内容。如果用 `overflow: hidden`，它会成为滚动容器；在 Chromium 中，当文本输入到一个滚动容器仍在长高的 textarea 时，光标位置会错乱，按 `n` 后立即输入的中文会变成倒序。原型改用 `overflow: clip`（并加上 `min-width: 0`）。实现时必须保留这个做法，并用真实 Chromium 覆盖“按 `n` 后立即连续输入”的场景。
- **原型的正文规范化会破坏 Markdown**：原型提取标签后，会把每一行的连续空白压缩成一个空格，并去掉行首和行尾的空白，这会破坏列表缩进和代码块。实现不能照搬，D6 只清理标签留下的空白，与札记根决策 D4 “正文原样保存”一致。
- **瀑布流的重新排版**：按最短列放置依赖卡片的实际高度，折叠又依赖渲染后的高度。字体加载、窗口缩放、展开或收起卡片后，各列高度都会变化。只在列数变化时重新排版，展开卡片后列高可能变得不均匀；这一点可以接受，但新建卡片插入第一列顶部、加载下一页时，已有卡片不能跳到别的列。
- **子串搜索的成本**：`q` 的子串匹配会扫描全部札记的正文。千级札记时可以接受；札记增长到明显变慢时，再为它加 trigram 索引，接口不变。
- **回顾卡片组在当天变化**：D8 的卡片组只在候选集合不变时稳定。Agent 删除一张今天卡片组中的札记，或者补传旧日期的札记，都会让刷新后的卡片组变化。这是不持久化的代价，见“本决策未解决的问题”。

## 本决策未解决的问题

- **回顾卡片的正式选取规则**：例如偏向一年前的同一天、偏向很久没出现过的札记。D8 的摘要排序只是保证“当日确定”的占位算法，接口形状预期不变。
- **已读状态与卡片组的持久化**：已读是否跨刷新、跨设备保留，卡片组是否在当天内对删除和补传保持不变。这需要在正式选取规则确定后一起决定。
- **札记的编辑与删除**：札记根决策只允许客户端新建。回响页第一版沿用这个边界，只读加新建。
- **附件与札记之间的引用**：同札记根决策，卡片暂时不渲染图片和引用。

## 落地顺序

1. **服务端读取接口**：实现 D8 的三个接口，纳入 OpenAPI 合同；用真实 PostgreSQL 测试排序与分页、`tag` 与 `q` 的交集、`pending` 的判定、按 `PALACE_TIMEZONE` 的日期分桶，以及回顾结果的确定性与今天新建札记的排除。完成条件：不变量 1、2、4、5、6、12 有直接证据。这一步与界面无关，可以独立评审。
2. **回响页骨架**：导航中的回响可以点击，`/jottings` 路由、页面加宽和切换动画、两栏布局、瀑布流与分页、卡片折叠、时间与待整理圆点。完成条件：回响页能浏览全部札记。
3. **左列与搜索**：统计、热力图、前 8 个标签、全部标签视图、`/` 搜索、筛选行与 Escape 退出链。
4. **新建**：`n`、`#标签` 提取与补全、上传，并在真实 Chromium 中验证输入法场景。
5. **今日回响**：卡片组的叠放、平铺、放大和内存中的已读。

从第 2 步开始，导航中的回响可以点击；时刻、摘星以及札记的同步与上传行为不变。
