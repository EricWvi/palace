# 放大卡片里原地编辑和删除札记；标签写回正文末尾编辑，删除用两步确认的题签

放大卡片右侧的题签新增「修订」和「削简」。瀑布流的放大卡片依次是「修订」「束阁 / 启封」「削简」，回顾卡片的放大卡片依次是「温故」「束阁」「修订」「削简」。点「修订」后，放大卡片原地变成编辑器：标题变成单行输入框，正文变成文本框，标签以 `#词` 写回正文末尾，保存时按新建札记的规则重新提取。编辑时右侧题签换成「保存」「取消」，Ctrl/Cmd+Enter 保存。点「削简」后，这枚题签变成朱红色的「确认」，题签长度不变；再点一次才删除，第一次点击后 3 秒内没有再点就变回「削简」，移开鼠标不影响计时。删除后放大卡片缩回空位，卡片离开墙或卡片组。网页改过、尚未 commit 的札记带待整理圆点。

当前为 `implemented`，核心测试用例见[回响页](../../../test-cases/web/echo/echo-page.md)。本决策基于[回顾按完成次数最少者优先抽取](20261101-recall-least-completed-first-from-a-stored-daily-pile.md)和[瀑布流的札记点时间放大](20261101-zoom-wall-jottings-by-their-time-and-load-palace-media.md)，修改前者 D6 的题签列表。写入规则和接口见[Web 编辑和删除札记](../../server/jotting/20261101-edit-and-delete-jottings-from-the-web-in-the-work-tree-until-committed.md)。只涉及 `apps/palace-web` 的回响页。

## 继承与修改

| 前序约定 | 本决定 |
| --- | --- |
| 放大决策 D1：回顾与瀑布流共用放大卡片，编辑只做在这里 | 继承；编辑和删除只在放大卡片中，见 D1 |
| 回顾决策 D6：瀑布流题签是「束阁」或「启封」；回顾卡片是「温故」「束阁」 | 修改：两处都加上「修订」「削简」，见 D1 |
| 回顾决策 D5：完成后放大卡片缩回空位，卡片离开卡片组 | 继承；删除时同样缩回空位，见 D4 |
| 根决策 D7：Escape 依次退出放大的卡片 → 平铺的卡片组 → … | 修改：编辑中且有改动时，Escape 不退出，见 D2 |
| 新建札记：`#词` 提取为标签，Ctrl/Cmd+Enter 保存，有内容的草稿不会因 Escape 丢失 | 继承到编辑：同一套标签提取和快捷键，见 D2、D3；标签补全没有继承，见 D2 |
| 根决策：`pending` 的札记带待整理圆点 | 继承；`pending` 的含义按服务端决策 D5 扩大到网页改过、尚未 commit 的札记 |

## D1：题签的排列

| 放大卡片 | 阅读时的题签（自上而下） | 编辑时 |
| --- | --- | --- |
| 瀑布流 | 编辑 / 束阁（或启封） / 删除 | 保存 / 取消 |
| 回顾卡片组 | 温故 / 束阁 / 修订 / 删除 | 保存 / 取消 |

- 题签文字取书简的说法：「温故」读过一遍，「束阁」收起不再抽出，「启封」重新抽出，「修订」改写，「削简」删去。
- 每枚题签的内宽约三个字，两个字的题签不显得局促；竖排时整列同宽。
- 删除总在最后，离常用的题签最远。
- 窄屏下题签排成卡片下方的一行（回顾决策 D6），顺序相同。

**为什么回顾里也能删除**：回顾时最容易发现一张札记没有保留的必要，这时还要去墙上找它就太绕了。

## D2：原地编辑

- 点「修订」后，放大卡片的内容区原地变成编辑器，卡片位置不变，题签换成「保存」「取消」：
  - 标题变成单行输入框，字体和位置与标题相同；没有标题时显示浅色的“标题”占位，留空即无标题。
  - 正文变成文本框，随内容长高，超过放大卡片的最大高度时在卡片内滚动。光标放在正文末尾、标签之前。
  - 标签写回正文末尾，与正文隔一个空行，例如 `#阅读 #rust`；没有标签时不写。
- 保存：
  - Ctrl/Cmd+Enter 或「保存」：标题去掉首尾空白，正文按新建札记的规则提取 `#词` 为标签并从正文移除，然后保存。保存期间题签不可点。
  - 成功后回到阅读状态，显示保存后的内容；墙上和卡片组的这张卡片同步更新，带上待整理圆点。
  - 内容没有改动时，「保存」直接回到阅读状态，不发请求。
- 退出：
  - 「取消」：放弃改动，回到阅读状态。
  - 没有改动时，Escape 回到阅读状态，再按一次 Escape 关闭放大卡片；点背景同样只回到阅读状态。
  - 有改动时，Escape 和点背景都不起作用，只能保存或取消。这与新建札记“有内容的草稿不会因 Escape 丢失”一致。
- 编辑中正文是原始 Markdown，图片只是一行地址；回到阅读状态后照常加载。
- 编辑器没有新建札记那样的已有标签补全。评审稿写的是继承补全，实现时没有做：补全需要全部标签，而放大卡片目前不读概况数据；编辑多是改几个字，标签很少在这里新增。需要时再把补全提出来共用。

**为什么标签写回正文**：新建札记就是这样写标签的，编辑时用同一种写法，就不需要再学一套标签输入框，界面也只有标题和正文两块。代价是标签的顺序在保存时按正文中出现的顺序重排，与新建相同。

**为什么标题单独一个输入框**：新建札记没有标题，但已有的札记很多有标题。把标题也写进正文（例如首行 `# 标题`）会和正文本身以标题开头的札记混淆。标题在阅读时本来就单独显示在卡片顶部，编辑时原地变成输入框最直接。

## D3：保存失败

- `409 jotting_changed`（札记在打开后被一次 commit 改过）或 `409 jotting_moved`（文件正被移动）：编辑器和草稿都保留，题签上方显示一行说明“札记已在别处改过，复制修改后取消再修订”，「保存」不可点。重新打开时读到的是最新内容。
- 其他错误：保留草稿，显示“保存失败”，「保存」可以重试。

**为什么冲突时不自动合并**：冲突来自 Agent 刚 commit 的修改，实际很少发生；网页上没有能看清两边差异的地方，自动合并或覆盖都可能悄悄丢掉一边。保留草稿让用户自己决定。

## D4：两步确认的删除

- 点「削简」：这枚题签变成「确认」，文字和两道边线变成朱红色 `--color-destructive`，题签大小不变。
- 再点「确认」：删除。第一次点击后 3 秒内没有再点，变回「削简」；鼠标移开这枚题签不作废，也不重新计时，只有这一个 3 秒。失去焦点即变回。

**为什么移开鼠标不作废**：指针从一枚窄题签上滑出一点是常事，立即作废会让「确认」一闪就没了，还得重点一次。只用第一次点击起的一个计时，规则最简单，误删仍然要两次点在同一枚题签上。
- 删除成功后，放大卡片按“完成”的方式缩回空位并淡出：
  - 回顾卡片组：卡片离开卡片组，与「温故」相同。
  - 瀑布流：卡片从所在列移除，同一列下面的卡片用 200ms 从原位滑上来补位，不是一帧跳上去；其他列不动。墙上其他卡片已排定的列不变（根决策“风险”）。
- 删除失败（包括两种 `409`）：放大卡片保持打开，题签上方显示说明，与 D3 相同。

**为什么是两步确认而不是对话框或撤销提示**：对话框打断阅读，而且要在放大卡片上再叠一层。撤销提示需要先把删除延迟发出，或者服务端支持撤销，网页上从未 commit 的内容也无法真正撤销。题签原地变成「确认」不增加任何元素，第二次点击在同一个位置，误删需要连续两次点错。

**为什么用「确认」两个字**：与「削简」同样两个字，题签长度不变，旁边的题签不会跳动。

**为什么用朱红**：`--color-destructive` 在设计令牌中映射为 `--accent` 朱红，像题签上的朱印，与宋体题签的风格一致，又足够醒目。

## 不变量

1. 编辑和删除只能从放大卡片发起，墙上和卡片组的缩略卡片没有这两个入口。
2. 有改动的草稿只会因为「取消」而丢弃；Escape、点背景和保存失败都不会丢掉它。
3. 删除要在同一枚题签上点两次；第一次点击后超过 3 秒，或者失去焦点，第一次点击作废；鼠标离开不影响。
4. 保存或删除失败时，放大卡片保持打开，墙和卡片组不变。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| 单独一行标签输入框 | 标签与正文分开，顺序可以保留 | 多一块界面；与新建札记的写法不一致 |
| 打开编辑页或侧栏编辑 | 编辑空间更大 | 离开了放大卡片，回顾和墙要各自处理返回；小改动用不到更大的空间 |
| 编辑中 Escape 直接放弃改动 | 与阅读时一致 | 一个误按就丢掉改动，违反新建札记已经确立的规则 |
| 删除弹确认对话框 | 常见做法 | 打断阅读，放大卡片上再叠一层；见 D4 |
| 「削简」变「确认删除」 | 更明确 | 题签变长，旁边的题签跟着移动 |
