# 回顾按完成次数最少者优先抽取，当天的卡片组存进数据库；只有「回顾完成」计数，札记可以不再参与回顾

今日回响的选取规则从“按日期摘要排序”改为“完成次数最少的先抽，同一层内按日期摘要随机”。每张札记有一个回顾完成次数；只有在回顾卡片的放大界面点「回顾完成」或「不再回顾」，次数才加 1，卡片才离开卡片组，直接关闭只是缩回原位。上一次卡片组里没完成的札记不参与紧接着的下一次抽取，所以忙时没看完的卡片不会第二天又出现。当天的卡片组在第一次请求时抽出并写入数据库，此后一整天不变，完成状态也保存在服务端，刷新后不再恢复。每天的张数由环境变量 `PALACE_JOTTING_RECALL_SIZE` 设定，默认 5，取值 1–18，只在抽卡时读取。札记可以设为不再参与回顾，恢复时次数重设为当前最小值；新札记与删除后复活的札记同样从最小值开始。数据库只保留最近两组卡片组。放大卡片右侧新增竖排的文字操作：回顾卡片是「回顾完成」「不再回顾」，瀑布流卡片是「不再回顾」或「恢复回顾」。卡片组平铺时每行 6 张、最多 3 行。

当前为 `approved`，核心测试用例见[札记读取接口](../../../test-cases/web/echo/jotting-reading.md)和[回响页](../../../test-cases/web/echo/echo-page.md)。本决策基于[回响页根决策](0-jotting-wall-with-daily-recall-pile.md)和[瀑布流的札记点时间放大](20261101-zoom-wall-jottings-by-their-time-and-load-palace-media.md)，回答根决策“本决策未解决的问题”中的“回顾卡片的正式选取规则”与“已读状态与卡片组的持久化”。涉及 `palace-db`（新表与查询）、`palace-jottings`（抽卡与完成）、`palace-backend`（接口与配置）、`docs/server/环境变量.md` 和 `apps/palace-web` 的回响页。札记文件、Git 索引规则与移动端同步协议不变：回顾状态不写进札记文件，也不进入 `changes` 接口。没有已有数据需要迁移：上线后第一次抽卡时，所有札记的次数都视为 0。

## D1：完成次数最少的先抽，跳过上一次没完成的

抽卡时，候选是同时满足下列条件的札记：

- 未删除，并且参与回顾（D2）；
- `created_at` 早于今天零点（根决策 D8，不变）；
- 不是**上一次卡片组**里未完成的札记。上一次卡片组指日期早于今天的、最近的一组。哪天没有打开回响页，那天就没有卡片组，所以它不一定是昨天的。

候选按 `(完成次数 升序, SHA-256(date ‖ id) 升序)` 排序，取前 `N` 张（D4），返回顺序就是这个顺序。候选不足 `N` 张时全部取出。

**完成次数最少的先抽**：同一时刻候选的完成次数只会集中在相邻的几个值上。次数最少的那一层抽完、并且都被完成之前，次数更多的札记只在这一层不够 `N` 张时才会被补进来。效果相当于一只洗牌袋：每张札记都被回顾过一次，才会开始第二轮。

**同一层内用日期摘要排序**：同一层的札记每天按一个新的伪随机顺序排列，没有完成的札记每天都重新参加洗牌，不会因为“次数最少”就天天排在最前面。摘要不依赖随机数发生器，测试可以固定日期、直接断言抽出的札记。

**跳过上一次没完成的**：只靠洗牌时，一轮快结束、最少的那一层只剩几张，如果恰好都没完成，它们会每天被抽出来，直到完成为止。忙时没看完卡片很正常，所以上一次没完成的札记跳过紧接着的这一次。它们的次数没有变，仍在最少的那一层，下下次照常参与抽取，不会被遗漏。读过的札记不设冷却：一轮的末尾和下一轮的开头可能抽到同一张，札记多到几千张时一轮要几百天，可以忽略。

**代价**：次数只在完成时增加，是否完成由用户决定，所以“任意两张札记的次数相差不超过 1”不是硬性保证。最少的那一层不足 `N` 张时，次数多一次的札记会被补进来；它们如果被完成，次数差就会到 2。这只发生在一轮的边界，而且长期来看“最少者优先”会不断把次数拉平，满足“所有札记被回顾的次数差不多”的要求。

**为什么不用纯随机或按次数加权的随机**：2000 张札记、每天 5 张，一年约 1825 次抽取，平均每张约 0.9 次；纯随机下大约 40% 的札记一年都没出现过，同时有札记出现了 4、5 次。按次数加权能减小这种偏差，但消除不了，而且结果不能直接断言。

## D2：回顾状态单独存一张表；新札记、复活和恢复都从当前最小值开始

回顾状态存放在新表 `jotting_recall` 中，以札记 `id` 为主键。每一行有两种状态：

| 状态 | 含义 |
| --- | --- |
| 计数 | 参与回顾，带完成次数 |
| 不再回顾 | 不参与抽卡；不保存次数 |

没有行的札记参与回顾，它的完成次数视为**当前最小值**：所有未删除、处于“计数”状态的行中最小的次数，没有这样的行时为 0。下面三种情况都把札记变成“没有行”，从而落在最少的那一层：

- Agent 新建、或从移动端上传的札记：对账和上传都不写这张表。
- 删除后复活的札记：对账把札记写成 tombstone 时，在同一事务中删除它的回顾状态，复活时自然没有行。复活的札记当作新札记，“不再回顾”也随之清除。
- 恢复回顾：删除这一行。

完成一张没有行的札记时，写入“计数”状态，次数为“当前最小值 + 1”。

**为什么没有行就等于最小值，而不是插入时写下当时的最小值**：两者在排序上没有区别，都让札记落在最少的那一层（插入时的最小值只会小于或等于之后的最小值）。“没有行”的写法让对账和上传完全不碰这张表，也不需要在两条写入路径上维护“插入时求最小值”。

**为什么恢复时要重设**：被排除期间，它的次数停在排除前的值；如果其他札记的次数在这期间涨了，恢复后它会连续很多天被抽中，直到追平。

**为什么不放在 `jotting` 表上**：`jotting` 是 Git 索引，每一列都来自札记文件或同步协议，它的触发器在每次更新时都要取发布锁。回顾状态是 Palace 自己的数据，不来自文件，也不同步给移动端，分开存放后，完成一张卡片不会和对账争同一把锁。

**为什么不写进札记文件**（例如 frontmatter 中的 `recall: false`）：那样服务端就要修改 Agent 维护的已提交文件，属于编辑的范围，留给后续决策。代价是回顾状态不在 Git 中，数据库丢失时会一起丢失；丢失的结果只是所有札记重新开始一轮，而且所有札记都恢复参与回顾。

## D3：当天的卡片组在第一次请求时抽出并存储

- 新表 `jotting_recall_pile` 每天一行，记录日期和抽卡时间；`jotting_recall_card` 记录这一天卡片组中每张札记的位置，以及完成时间（未完成为空）。
- `GET /api/jottings/recall` 先查今天的卡片组，有就直接返回。没有时，在一把事务级 advisory lock 内再查一次，仍然没有就按 D1 抽卡，写入卡片组，然后返回。候选不足、一张也没抽到时同样写入一行空的卡片组，这一天不再重抽。
- 当天的卡片组只读不改：Agent 修改了其中的札记时返回最新内容；删除了其中的札记时不显示它，也不补抽；当天新建、修改、复活的札记都不会进入今天的卡片组。

**为什么必须存储**：完成次数会在一天之中改变，而 D1 的排序依赖次数，每次请求都重新计算的话，完成一张就会让卡片组重新洗一遍。存储还解决了根决策“风险”中记录的问题：Agent 当天删除或补传札记时，卡片组不再随之变化。

**为什么在第一次请求时抽卡，而不是定时抽卡**：没有打开回响页的日子不产生卡片组，也就不会把没看过的札记记作“上一次没完成”而跳过。

**为什么加锁**：同一时刻的两个首次请求（例如两个标签页）只能抽出一组。锁内只读写数据库，不做网络请求。

## D4：张数由 `PALACE_JOTTING_RECALL_SIZE` 设定，只在抽卡时生效

- 可选环境变量，取值 1–18 的整数，默认 5。超出范围或不是整数时启动失败，错误信息列出变量名和取值范围。
- 只在抽卡时读取当前配置。今天的卡片组一旦抽出，它有几张就是几张；修改这个值并重启服务，不影响今天，下一次抽卡才按新值。
- 上限 18 来自平铺布局：每行 6 张、最多 3 行（D6）。

## D5：「回顾完成」才计数，直接关闭只是缩回

**完成** `POST /api/jottings/recall/{date}/{id}/done`，请求体 `{ next }`，`next` 为 `"keep"` 或 `"retire"`：

- 在一个事务中，把该卡片的完成时间从空设为现在，并且只在这一步确实发生时把次数加 1（D2）。`next` 为 `"retire"` 时，同时把回顾状态设为“不再回顾”。
- 同一张卡片完成两次：第二次不再计数，返回成功；`"retire"` 仍会设为不再回顾。刷新、重试和两个标签页同时点击都不会重复计数。
- 卡片不在这一天的卡片组里，或者这一天的卡片组已经被清理（D8），返回 `404`。只要卡片组还在，就可以完成，不限于今天：页面跨过零点后，完成昨天的卡片仍然有效。
- 响应是这张卡片新的回顾状态。

**参与回顾** `PUT /api/jottings/{id}/recall`，请求体 `{ recall }`，`recall` 为 `"included"` 或 `"excluded"`：

- `"excluded"` 写入“不再回顾”；`"included"` 删除这一行，次数从当前最小值开始（D2）。两者都不计数，也不影响已经存在的卡片组：今天卡片组中的札记在瀑布流里被设为不再回顾后，今天仍然留在卡片组中，下一次抽卡起不再出现。
- 札记不存在或已删除时返回 `404`。

前端行为：

- 回顾卡片放大后，点「回顾完成」或「不再回顾」：先请求，成功后卡片缩回原位并淡出，离开卡片组。请求失败时卡片不收起，按钮恢复可点。
- 点背景或按 Escape：卡片缩回原位，原卡片在下面显现，按瀑布流“落在原卡片上”的方式收尾（放大决策 D1），卡片仍留在卡片组中。
- 瀑布流卡片放大后只有「不再回顾」或「恢复回顾」，点击后文字原地切换，卡片保持放大。
- 是否参与回顾没有快捷键：这是低频操作。

**为什么只有完成才计数**：次数是“被回顾过”的记录。直接关闭可能只是瞄了一眼，也可能是被打断；如果关闭就计数，次数就混进了没真正回顾过的札记，D1 拉平次数的依据也就失真了。

**为什么「不再回顾」也计数并离开卡片组**：它表示“看过了，而且以后不用再看”，与完成是同一次回顾的两种结论。它的次数没有用处（恢复时会重设），计数只是让两个按钮走同一条完成路径。

**为什么用 `next` 而不是布尔值**：`{ retire: true }` 在调用处看不出 `false` 是什么意思；两个具名取值把“完成后接着做什么”写在请求里。

## D6：右侧竖排的文字操作；卡片组平铺为每行 6 张、最多 3 行

**放大卡片右侧的操作**

- 位于卡片外、贴着卡片右边缘，间隔约 12px，顶端与卡片顶端对齐，随卡片保持垂直居中。纯文字竖排（`writing-mode: vertical-rl`），`--font-ui`、小字号、`--text-3`，悬停变为 `--text-2`；多个操作上下排列。
- 放大动画结束后淡入；关闭一开始就淡出，不随卡片缩回，避免再次出现“字在飞”。
- 视口放不下卡片右侧的操作时（窄屏），改为卡片下方的一行横排文字。

**为什么竖排**：Web 端以文字为主、不用图标；竖排的短句贴在卡片旁，像书页边上的批注，与页面书卷的气质一致，也不占卡片自己的版面。

**多行平铺**

- 卡片尺寸不变。每行最多 6 张，视口放不下 6 张时按能放下的列数换行；最多 3 行，正好容纳 18 张。
- 叠放时只有前 5 张能看到错位和旋转，再往下的卡片与第 5 张重合，所以叠放的外观不随张数变化。
- **展开**：每张卡片从叠放处沿对角线移到自己的格子，延迟按 `(行 + 列) × 40ms` 计算，卡片像一道波从叠放处向右下方铺开。18 张时最后一张的延迟为 280ms，加上 300ms 的移动，整组在 0.6 秒内铺完。按序号逐张延迟需要 0.7 秒才开始动最后一张，太拖沓。
- **收起**：按相反的顺序，离叠放处最远的卡片先动，整组从右下角向叠放处收拢，延迟同样按 `(行 + 列)` 的倒序计算。
- **补位**：一张卡片完成后离开，后面的卡片前移一格。同一行内的前移是一次水平平移；需要换到上一行末尾的卡片不做跨行的斜向长距离移动，而是在原位淡出、在新的格子淡入，像文字换行。
- 平铺的卡片仍然盖在瀑布流上方，瀑布流变暗；点击卡片以外的任何地方收起，这次点击不会穿透到瀑布流（根决策不变量 8）。
- 窄屏上卡片组仍是一行可以横向滑动的卡片（根决策 D3），不受行数限制。

## D7：接口响应中的回顾状态

- 札记在列表、回顾接口中增加 `recall` 字段：`"included"` 或 `"excluded"`。瀑布流放大卡片据此显示「不再回顾」或「恢复回顾」。
- 回顾接口的每张卡片另带 `done`：这张卡片今天是否已经完成。前端只显示未完成的卡片；全部完成时显示“今天的回响都已看过”；卡片组为空时什么也不显示。
- 回顾接口的 `date` 保持为今天；它也是完成接口路径中的 `{date}`。
- 完成次数不出现在任何响应中：它只决定抽卡顺序，显示出来会让回顾变成刷数字。

## D8：数据库只保留最近两组卡片组

每次抽出新的卡片组时，在同一事务中删除除了“新的一组”和“上一组”以外的全部卡片组。表中因此最多只有两组，一年也不会超过两组的数据量。

- 上一组要留着：D1 的“跳过上一次没完成的”和 D5 跨零点的完成都需要它。
- 清理和抽卡在同一事务中完成，不需要定时任务。没有打开回响页的日子不抽卡也不清理，这时表里本来就没有新增数据。

**为什么不保留历史**：每张札记被回顾的情况已经汇总在完成次数里；逐日的卡片组只在当天和下一次抽卡时有用。以后如果要做“回顾记录”一类的功能，再为它单独设计存储。

## 不变量

1. 同一天内，回顾接口每次返回同一组札记、同一顺序；修改张数配置、重启服务、Agent 修改或新建札记都不改变它。被删除的札记不再显示，也不会被替补。
2. 同一天无论有多少并发请求，只抽出一组卡片组。
3. 抽卡时，候选中完成次数更少的札记总是排在次数更多的之前。
4. 上一次卡片组中未完成的札记不出现在紧接着的下一组中。
5. 今天新建的札记、不再回顾的札记、已删除的札记不出现在今天的抽卡结果中。
6. 一张卡片只有在第一次被标记完成时，次数加 1；重复完成不再计数。直接关闭放大卡片不改变任何服务端状态。
7. 新札记、删除后复活的札记、恢复回顾的札记，在下一次抽卡时都处于完成次数最少的那一层。
8. 卡片组的张数等于抽卡那一刻的 `PALACE_JOTTING_RECALL_SIZE` 与候选数中较小的一个，取值 1–18。
9. 数据库中最多保存两组卡片组。
10. 回顾状态的任何变化都不改变札记的 `server_version`，也不出现在 `changes` 接口中。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| 纯随机或按次数加权的随机 | 实现最简单；每天的结果更难预料 | 次数分布有方差，大量札记长期不出现，见 D1 |
| 严格的最少者优先，不跳过上一次没完成的 | 次数最均匀 | 一轮末尾没完成的那几张会天天出现，忙时尤其明显 |
| 关闭即算完成（沿用根决策） | 少一个按钮 | 瞄一眼、被打断也会计数，次数不再代表真正回顾过 |
| 出现在卡片组里就计数 | 不需要完成接口 | 没看的札记也被算作回顾过，次数失真；不完成的札记就失去了被再次抽到的优先级 |
| 每次请求都重新计算卡片组 | 不需要新表 | 完成会改变次数，卡片组在一天中不断变化，见 D3 |
| 定时任务在零点抽卡 | 打开页面时不需要抽卡 | 没打开页面的日子也会产生卡片组，没看过的札记被当作“上一次没完成”而跳过 |
| 插入时写下当时的最小值 | 每张札记都有显式的次数 | 对账和上传两条写入路径都要维护这张表；排序上与“没有行即最小值”等价，见 D2 |
| 回顾状态放在 `jotting` 表或札记 frontmatter | 和札记放在一起 | 前者让完成和对账争发布锁、混入 Git 索引；后者需要服务端改写已提交的文件，见 D2 |
| 保留全部卡片组历史，定期清理旧数据 | 以后可以回看 | 当前没有使用者；需要一个定时任务和保留期限配置，见 D8 |
| 完成接口带 `{ retire: boolean }` | 字段少 | 调用处的 `false` 不自明，见 D5 |

## 风险

- **回顾状态不在 Git 中**：数据库丢失或重建时，次数和“不再回顾”都会丢失，见 D2。
- **上一组被跳过的札记较多时**：张数很大（例如 18）而很少完成时，每次都有大量札记被跳过一次；在札记总数远大于张数的前提下，这对候选数量的影响可以忽略。札记总数接近张数时，候选可能不足，卡片组会少于设定的张数。
- **平铺时的视口高度**：3 行卡片的总高度约 600px，盖住瀑布流的大部分首屏。这是 18 张时的预期效果；视口矮于这个高度时，平铺的卡片组会超出视口底部，可以滚动页面查看。

## 本决策未解决的问题

- **札记的编辑**：放大卡片右侧的操作列以后会加入「编辑」，规则由编辑的决策定义。
- **回顾记录**：逐日回顾过哪些札记的历史，见 D8。

## 落地与验收

1. **服务端**：迁移新增 `jotting_recall`、`jotting_recall_pile`、`jotting_recall_card` 三张表；对账写入 tombstone 时删除回顾状态。`palace-db` 实现在锁内抽卡、存储与清理，以及完成与设置回顾状态的查询；`palace-jottings` 用 `PALACE_TIMEZONE` 确定日期，读取张数配置；`palace-backend` 增加完成与设置回顾状态两个接口，扩展响应，纳入 OpenAPI 合同；`docs/server/环境变量.md` 增加 `PALACE_JOTTING_RECALL_SIZE`。验收：真实 PostgreSQL 测试覆盖不变量 1–10，其中并发抽卡与并发完成用 barrier 驱动；真实 Router 测试覆盖 `404` 与配置错误。
2. **Web**：放大卡片右侧的操作列，回顾卡片的完成与直接关闭的两种收尾，瀑布流的不再回顾与恢复回顾，多行平铺与补位动画。验收：页面测试覆盖按钮与收尾行为，真实 Chromium 覆盖多行平铺的位置和补位。

第 1 步完成后，现有前端仍可工作：直接关闭不调用完成接口，卡片组在刷新后照常显示全部未完成的卡片。札记文件、Git 对账、上传与 `changes` 接口的行为不变。
