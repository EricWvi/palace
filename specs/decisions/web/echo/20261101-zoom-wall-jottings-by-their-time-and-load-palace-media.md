# 瀑布流的札记点时间放大，放大卡片加载 Palace 媒体图片；缩略卡片仍只显示占位

瀑布流里的札记卡片也能像回顾卡片一样放大到屏幕中央阅读全文。入口是页脚的时间：点击时间就放大。原地展开保留，但正文超过 40 行的札记点「展开」直接放大。回顾和瀑布流用同一个放大卡片，以后的编辑和归档也只做在这里。放大卡片里加载正文中写成 `/api/media/<id>` 的图片，最大高 360px；缩略卡片（瀑布流与回顾卡片组）仍然只显示占位文字。时间的悬停提示去掉：瀑布流照旧显示相对时间或完整时间，放大卡片一律显示完整时间。

当前为 `approved`，核心测试用例见[回响页](../../../test-cases/web/echo/echo-page.md)。本决策基于[回响页根决策](0-jotting-wall-with-daily-recall-pile.md)，修改其 D3 的放大卡片归属、D4 的图片与时间规则，并回答其“本决策未解决的问题”中“附件与札记之间的引用”的读取部分。媒体的正文写法与读取沿用[媒体读取决策](../../server/media/20261020-read-media-by-redirect-to-presigned-url.md)。只涉及 `apps/palace-web`，服务端接口与札记文件格式不变。札记的编辑、归档和图片上传留给后续决策。

## 继承与修改

| 前序约定 | 本决定 |
| --- | --- |

| 根决策：长札记在卡片内原地折叠和展开，不设详情页 | 继承原地展开；新增放大阅读，仍不设详情页、不改地址，见 D2、D3 |
| 根决策 D4：图片在附件可以读取之前只显示占位文字 | 修改：缩略卡片仍显示占位；放大卡片加载 `/api/media/<id>`，其余地址仍显示占位，见 D4 |
| 根决策 D4：7 天以内显示相对时间，悬停浮出完整时间 | 修改：瀑布流不再有悬停提示；放大卡片一律显示完整时间，见 D5 |
| 根决策 D7：Escape 依次退出放大的卡片 → 平铺的卡片组 → 全部标签视图 → 标签筛选 | 继承；瀑布流的放大卡片同样排在第一位 |

| 媒体读取决策 D1：正文中的媒体引用写成 `/api/media/<id>` | 继承；札记按同一写法识别媒体 |
| 媒体读取决策 D4：被业务记录引用的媒体不能单独删除 | 不适用于札记：札记以文本引用媒体，没有外键，见“风险” |

## D1：回顾与瀑布流共用一个放大卡片

- 放大卡片从卡片原来的位置长到屏幕中央，宽 560px（窄屏为视口宽减 32px）；背景变暗，点击背景或按 Escape 关闭。这些与根决策 D3 相同。
- 两个入口只在关闭后的处理上不同：
  - 回顾：缩回卡片组中的位置并淡出，这张卡片算读过，离开卡片组（根决策 D3，不变）。
  - 瀑布流：文字在缩回的前 60% 淡出，剩下一张空白的卡片（纸色、边框与墙上卡片相同，阴影随之消失）飞回原位，到达后淡出，下面的原卡片随之显现；卡片仍留在墙上，展开或折叠的状态不变。
- 关闭时放大卡片先回到顶部，再开始缩回。
- 放大期间原卡片隐藏，关闭时重新测量它的位置，所以放大期间页面滚动过也能缩回正确的地方。

**为什么共用**：编辑和归档都会放在放大卡片里。两个入口如果各有一份放大实现，后续功能就要做两遍，两处的行为也会慢慢分叉。

**为什么瀑布流在缩回途中就淡出**：放大卡片显示的是全文和图片，原卡片是折叠的、只有占位，差别集中在底部：全文在卡片高度处被硬裁、没有页脚，原卡片则有渐隐、「展开」和页脚。评审稿沿用回顾的做法，先缩到原位、再用最后 120ms 淡出，长札记在这一刻明显地从“裁断的全文”跳成“折叠的卡片”。试过让整张卡片在缩小途中淡出：纸色和边框对比度低，先于深色文字看不见，看起来像一些字在飞。所以文字先淡出，飞回去的是一张空白卡片，到原位后它和原卡片的纸色、边框一致，淡出时只有原卡片的文字浮现出来。回顾卡片关闭后离开卡片组，原位是空的，仍然先缩回再淡出。

## D2：点击时间放大

- 瀑布流卡片页脚的时间是一个按钮：点击放大，悬停时文字颜色加深、光标变成手形，可以用 Tab 聚焦、按 Enter 放大。没有其他可见的放大入口。
- 卡片的其余部分（空白、正文、内边距）点击都不放大。标签、链接、「展开」照常执行各自的操作。
- 回顾卡片的入口不变：点击卡片组平铺，再点击整张卡片放大。

**为什么是时间**：时间是一张札记的“地址”，点时间进入单条内容是常见做法。它位置固定、目标明确，不会和选字、点标签、点链接冲突，也不增加任何可见元素。

**为什么不是点空白处**：正文的段落是块级元素，宽度占满卡片，一行短字右侧看着是空白，点击的目标其实是段落。要按眼睛看到的空白判断，就得用 `caretPositionFromPoint` 比对字形矩形，还要处理图片占位、代码块、公式和表格；即使做到了，同一行左半边点不开、右半边能点开，也没有任何视觉提示。只把卡片内边距和页脚空白当作入口又太窄，像点不中。

**为什么不是整卡点击**：选字时容易误开，正文里的链接和标签周围也容易误触。

## D3：原地展开保留，超过 40 行的札记展开即放大

- 正文能放进 8 行时没有折叠，也没有「展开」（根决策 D4，不变）。
- 正文全部展开后不超过 40 行：「展开」在卡片内原地展开，「收起」折回，动画不变。
- 正文全部展开后超过 40 行：「展开」直接放大，卡片在墙上保持折叠。按钮文字仍是「展开」，不区分两种说法。
- 行数按正文完整高度除以正文行高计算，在卡片排版后测量，与判断是否需要折叠的时机相同。

**为什么留着原地展开**：中等长度的札记在墙上展开就能读完，不用离开瀑布流的上下文。

**为什么超长就放大**：超过 40 行的札记在墙上展开后会占好几屏，所在的列被拉得很长，瀑布流各列失衡，收起后还得找回原来的位置。放大卡片有自己的滚动区域，关闭后墙不会变。

## D4：只有放大卡片加载图片，且只加载 Palace 媒体

- 放大卡片中，正文里地址完全匹配 `/api/media/<uuid>`（小写连字符形式）的图片按 `<img>` 加载，懒加载、不带 referrer，与文章相同。其余地址（外站图片、相对路径）显示占位文字 `[图片：alt]`，不发出任何请求。
- 图片 `max-height: 360px`，宽度按比例缩放，不超过卡片宽度，居中显示。
- 瀑布流卡片和回顾卡片组仍然一律显示占位文字。
- 第一版全部按图片渲染。札记的列表接口不带媒体类型，正文里如果引用了视频，会显示成一张加载失败的图片。

**为什么缩略卡片不显示图片**：瀑布流按卡片高度排列，图片晚到会让卡片长高，而已经放好的卡片不会重排（根决策“风险”），各列会更加不齐。回顾卡片尺寸固定、很窄，图片放不下。

**为什么限高 360px**：手机截图大多是竖长的，按 560px 宽显示会高过一屏，一张图就把文字推出视口。限高 360px 时，竖图约占放大卡片的一半高，横图基本是满宽显示。

**为什么只加载 `/api/media/<uuid>`**：Palace 媒体由 Owner 自己上传，读取时 302 到对象存储，不会碰到第三方站点。札记以后可能从 flomo 导入外站图片地址，打开一张旧札记不应该让浏览器去请求外部站点。

**为什么暂不支持视频**：要按类型渲染，服务端就得在札记响应中附带被引用媒体的 `content_type`，也就要解析正文里的引用。目前札记里只有图片，等真有视频时再做。

## D5：放大卡片的高度随内容变化；时间不再有悬停提示

- 放大动画按打开那一刻测得的高度进行；动画结束后，卡片改为高度随内容变化，最高为视口的 80%，并保持垂直居中，超出部分在卡片内滚动。图片加载出来后，卡片上下对称地长高。关闭时按当时的实际尺寸缩回原位。
- 瀑布流卡片的时间去掉悬停提示：7 天以内显示相对时间，超过 7 天显示 `YYYY-MM-DD HH:mm`，与之前相同。回顾卡片组的紧凑写法不变。
- 放大卡片的时间一律显示 `YYYY-MM-DD HH:mm`，不是按钮，也没有提示。

**为什么不等图片加载完再放大**：图片要经过一次 302 跳转，再从对象存储取字节，点开后会有明显延迟。先放大、再随图片长高，阅读文字不用等。

**为什么去掉悬停提示**：时间成了放大入口之后，悬停提示和点击是同一处的两种行为。想知道一张近期札记的确切时间，点开就能看到；去掉提示后，时间上就只剩一种行为。

## 不变量

1. 瀑布流卡片只在点击时间、或点击超长札记的「展开」时放大；点击正文、空白、标签或链接都不会放大。
2. 正文全部展开后超过 40 行的札记，在墙上不会原地展开。
3. 关闭瀑布流的放大卡片后，原卡片仍在墙上，展开或折叠状态与放大前相同；关闭回顾的放大卡片后，这张卡片离开卡片组。
4. 缩略卡片（瀑布流与回顾卡片组）从不请求图片。
5. 放大卡片只请求地址完全匹配 `/api/media/<uuid>` 的图片；其他地址显示占位，不发出请求。
6. 放大卡片中图片的显示高度不超过 360px，卡片高度不超过视口的 80%。
7. 瀑布流与放大卡片中的时间都没有悬停提示；放大卡片的时间总是完整时间。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| 整张卡片点击放大（选中文字时不放大） | 目标最大，与回顾卡片一致 | 点链接、点标签周围容易误开；选字和点击靠选区是否为空来区分，行为不稳定 |
| 点击卡片空白处放大，按字形矩形判断空白 | 不占用任何元素 | 需要逐字测量；块级元素、代码块和公式都要特殊处理；能点的区域没有视觉提示，体验发飘，见 D2 |
| 只点卡片内边距和页脚空白放大 | 实现简单 | 内边距只有十几像素，像点不中 |
| 悬停时右上角浮出放大图标 | 入口明确 | 右上角已有待整理圆点；图标违背“以文字为主” |
| 去掉原地展开，统一放大 | 只有一种阅读方式，删掉高度动画 | 中等长度的札记要离开墙才能读完；Eric 选择保留 |
| 缩略卡片也显示图片 | 瀑布流适合图文混排 | 图片晚到会打乱瀑布流各列高度；回顾卡片放不下 |
| 图片 decode 完再开始放大 | 动画一步到位，高度准确 | 点开后有明显延迟 |
| 服务端附带媒体类型，支持视频 | 视频能直接播放 | 需要解析正文引用并改接口；目前没有视频札记 |

## 风险

- **札记中的媒体没有删除保护**：媒体读取决策 D4 靠外键阻止删除被引用的媒体，札记是文本引用，`DELETE /api/media/<id>` 不会拦住它。目前没有任何界面或流程会删除媒体，影响有限；札记编辑引入图片上传时，与引用关系一起决定。
- **视频显示为加载失败的图片**：见 D4，接受到真有视频札记为止。

## 本决策未解决的问题

- **札记的编辑与归档**：入口和操作都放在 D1 的放大卡片里，规则由后续决策定义；它们涉及服务端写入 Agent 维护的札记文件，超出本决策“只改 Web 读取”的范围。
- **图片上传与札记对媒体的引用关系**：由编辑的决策一起定义，包括上面的删除保护。
- **点击图片查看原图**：放大卡片中的图片受限高约束；是否支持点击后查看原尺寸，等实际使用后再定。

## 落地与验收

- 把 `ZoomedCard` 及其动画从 `recall-pile.tsx` 移到 `components/echo/` 下的独立模块，关闭后的处理由调用方决定；回顾卡片组改用它，行为不变。
- `JottingCard` 的时间改为按钮并接入放大；「展开」按 40 行分流；`JottingTime` 去掉提示，增加放大卡片使用的完整时间写法。
- 放大卡片使用只放行 `/api/media/<uuid>` 的图片规则，`echo.css` 增加图片限高和放大后高度随内容变化的样式。
- 页面测试覆盖不变量 1–5、7；不变量 6 与图片加载后的居中长高由真实 Chromium 验证。ADR 批准后补充核心测试用例。

服务端接口、札记文件格式、回顾卡片的选取与已读规则，以及新建与搜索行为不变。
