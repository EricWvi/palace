# 睡眠从时刻页菜单开始，计时与结束后的这一晚都以表盘置顶当天，历史页把每晚画在同一条夜轴上

时刻页新增睡眠 Moment。晚上 18:00 到次日 05:00，日期旁 `···` 菜单里有「开始睡眠」；开始后当天顶部出现计时表盘，表盘自带一个停止按钮，06:00 前点它先确认一次。结束后这一晚归入醒来那天，以表盘置顶那一天：时长、入睡与醒来时间，以及截至这一晚的 7 晚柱。05:00 到 15:00 之间，如果这一晚没有开始过，菜单换成「记录睡眠」，填入睡和醒来时间补记。到 15:00 仍在计时的视为忘了结束，计时消失，下次开始睡眠时删除。点表盘进入睡眠历史页 `/sleep`，每晚一行画在 20:00 到次日 10:00 的夜轴上，点一行修改或删除，点空行补记。交互定稿见原型 [`design/2.2-moment-sleep.html`](../../../../design/2.2-moment-sleep.html)。

当前为 `implemented`，核心测试用例见[睡眠](../../../test-cases/web/sleep/sleep.md)，接口与用法见[睡眠功能文档](../../../../docs/features/sleep/README.md)。本文件是 `web/sleep` 的根决策，没有前序 ADR。它在 [Moment 根决策](../../server/moment/0-moment-supertype-and-typed-details.md)上新增 `sleep` 类型，并修改其不变量 3 中“详情表不保存另一份时间”的约定，见 D3；它修改 [Web 导航根决策](../navigation/0-text-nav-day-routes-and-moment-opening.md) D4 中睡眠“在时间线上原地展开”的预设，见 D5。涉及 `palace-db` 的新表与迁移、`palace-domain` 的时间段校验、`palace-backend` 的睡眠接口与 OpenAPI、`apps/palace-web` 的时刻页与睡眠历史页。只有入睡和醒来两个时间：不导入手环数据，没有睡眠分期、评分、心率，也没有午睡。

## 问题与约束

- 用户每晚在时刻页手动记录：睡前点开始，醒来点结束。忘记点开始或忘记点结束都很常见，规则要让两种遗漏都能补救，且不会留下错误的一晚。
- 睡眠是有时长的 Moment，跨越午夜；“这一晚算哪天”必须唯一，时间线、表盘和历史页才不会互相矛盾。
- 时刻按浏览器所在时区归日（Moment 根决策 D4），服务端不保存本地日期。18:00、05:00、15:00、06:00 这些规则说的都是用户所在地的钟点。
- 手机上误触停止按钮的代价是整晚记录被截断，而停止按钮是计时中最显眼的东西。
- Palace 只有一个用户，界面少文字、无入口按钮：开始与补记收进日期旁的 `···` 菜单，表盘本身就是进入历史的入口。

## 继承与修改

| 前序约定 | 本决定 |
| --- | --- |
| `moment` 只持有身份、类型与 `occurred_at`；详情表以 `(owner_id, id, kind)` 复合外键锁定类型，提交时检查每个 Moment 有对应详情（Moment 根决策 D1、D2） | 继承；新增 `kind = 'sleep'` 与详情表 `sleep`，见 D3 |
| 详情表不再保存另一份 `occurred_at`（Moment 根决策不变量 3） | 修改：`sleep` 保存完整的时间段，其终点必须等于 `moment.occurred_at`，由提交时检查保证，见 D3 |
| 时间线按调用方的本地日区间查询，服务端不保存本地日期（Moment 根决策 D4） | 继承：一晚的 `occurred_at` 是醒来时间，按浏览器时区归入醒来那天；钟点规则只在浏览器里判断，见 D2 |
| 只属于当天的 Moment 在时间线上原地展开（Web 导航根决策 D4） | 修改：睡眠不进入时间线列表，而是在日期下置顶表盘，点击进入自己的历史页，见 D5 |
| 低频操作收进区域旁的 `···` 菜单（Web 导航根决策 D5） | 继承：开始睡眠、记录睡眠放在日期旁的菜单最前面；结束睡眠例外，在表盘上，见 D1 |

## D1：一晚的生命周期

| 状态 | 怎么进入 | 页面 |
| --- | --- | --- |
| 没有在计时 | 初始；结束、作废之后 | 18:00–05:00 菜单有「开始睡眠」；05:00–15:00 且这一晚没开始过时有「记录睡眠」；15:00–18:00 菜单里没有睡眠项 |
| 计时中 | 「开始睡眠」 | 今天的页面顶部是计时表盘，以秒计时，右侧是停止按钮；菜单里没有睡眠项 |
| 已结束的一晚 | 停止按钮、记录睡眠、历史页补记 | 醒来那天顶部是这一晚的表盘 |
| 作废的开始 | 计时到开始那晚之后的 15:00 仍未结束 | 计时表盘消失，像没有开始过；记录留在服务端，下次「开始睡眠」时被替换 |

- 结束只在表盘上：计时中最常做的事就是结束，而菜单需要先悬停找到 `···`，在手机上还要两次点按。停止按钮是图形（圆环里的方块），不写字，环缓慢呼吸，表明计时还在走。
- 06:00 前（含开始那晚 18:00 之后）点停止，先弹出「现在就结束睡眠？」并写明现在几点、睡了多久；默认按钮是「继续睡」，Esc 和点遮罩也是继续睡。06:00 之后直接结束。夜里醒来摸手机时最容易误触，而真在 06:00 前起床的早晨很少，多一次确认的代价小。
- 「这一晚没开始过」指：没有计时中的开始，并且今天还没有归入的一晚。忘了开始的早上，用「记录睡眠」补；一晚已经记下就不再提供补记，修改去历史页。
- 作废点选在开始那晚之后的 15:00，与「记录睡眠」的截止时间一致：过了这个时间，这一晚已经不可能还在睡。作废的开始不需要单独的清理任务，因为同一时刻最多只有一个开始（D4），下一次开始就会替换它。

## D2：钟点规则只在浏览器里判断

18:00、05:00、15:00、06:00 都按浏览器的本地时间判断，由前端纯函数实现；服务端只保证结构上的约束（D3、D4），不知道也不判断钟点。服务端部署时区不一定是用户所在时区，与时间线按浏览器时区归日的理由相同。

记录或修改一晚时，用户只填两个钟点，日期由这一晚归入的那天决定：入睡钟点在 12:00 及以后的算前一天晚上，之前的算当天凌晨；醒来钟点就在那一天。醒来必须晚于入睡、不晚于现在，全程不超过 16 小时，否则对话框给出原因并禁用保存。对话框默认填近几晚的平均入睡与醒来时间（时刻页取表盘的 7 晚，历史页取近 30 晚），大多数补记只需要微调。

## D3：已结束的一晚是 `sleep` Moment

- `moment.kind` 新增 `sleep`；`moment.occurred_at` 是醒来时间，所以一晚按浏览器时区落在醒来那天，时间线、表盘和历史页用同一个归日。
- 详情表 `sleep(id, owner_id, kind, span tstzrange)`：`span` 是 `[入睡, 醒来)`，两端都是毫秒精度，有限，长度大于零且不超过 24 小时。
- `upper(span)` 必须等于对应 `moment.occurred_at`，由提交时运行的约束触发器检查（与“每个 Moment 有详情”的检查同一个函数）。这是对 Moment 根决策不变量 3 的修改：一晚的终点在两处出现，但数据库保证两处相等。
- 同一 Owner 的两晚不能重叠：`EXCLUDE USING gist (owner_id WITH =, span WITH &&)`（`btree_gist` 扩展）。半开区间让一晚的醒来与下一晚的入睡可以相接。重叠的写入整体回滚，接口返回 409。
- 时间线照常返回睡眠 Moment，卡片字段是入睡时间 `started_at`；`occurred_at` 是醒来时间。时刻页把它从列表里拿出来放进表盘（D5），其他客户端仍能按时间线顺序显示它。

把终点放进详情表，是为了用一张表上的排他约束拒绝重叠。替代做法是在写入事务里加按 Owner 的 advisory lock 再查重叠，正确性依赖每个写入方都记得加锁，而排他约束对任何写入方都成立。

## D4：计时中的开始是每个 Owner 至多一行，不是 Moment

- `sleep_start(owner_id primary key, started_at)`：计时还不是一晚，不进入时间线，也不是 Moment。
- 「开始睡眠」写入服务端当前时间；已经有一行时直接替换。这同时实现了“下次开始时删除作废的开始”，也让重复提交只是把开始时间推后几毫秒。
- 「结束」携带浏览器看到的 `started_at`，在一个事务里删除这一行、以服务端当前时间为醒来时间插入 Moment 与 `sleep` 详情。
  - `started_at` 与当前的开始不一致（例如另一台设备已经重新开始）时返回 404，不结束别人眼中的那一晚。
  - 没有开始、但已有一晚恰好以这个 `started_at` 入睡时，返回那一晚：结束请求的重试是幂等的。
  - 新的一晚超过 24 小时或与已有一晚重叠时整体回滚，开始保留。
- 开始和结束都用服务端时钟，浏览器时钟偏差不会写出未来的时间；06:00 确认用浏览器时钟，只决定是否多问一次。

## D5：时刻页的表盘与历史页

- 时间线列表和骨架都不显示睡眠项；日期标题下的置顶位按优先级显示：今天的计时表盘 > 这一天归入的一晚 > 无。一天有多晚时显示最晚醒来的那一晚。轮廓里有睡眠项而这一晚的数据还没到时，置顶位先显示同样高度的空表盘，不让下面的卡片在数据到达时跳动。
- 计时表盘每秒只更新数字；表盘本身只在计时开始、结束或作废时重建，停止按钮的呼吸动画不随数字重启。
- 7 晚柱是截至这一晚的 7 个本地日，每天取归入那天的一晚，高度按 7 晚中最长的一晚折算，没有记录的一天画成贴底的短横。
- 以前的日子只显示那天的一晚，菜单里没有睡眠项：开始、结束、补记只针对今天，修改去历史页。
- 菜单的睡眠项在每次接近 `···` 时（指针进入、获得焦点或按键）按当时的钟点重新判断，页面从下午开到晚上也会出现「开始睡眠」。
- 点表盘进入 `/sleep`，带上来源日期，返回链接回到那一天。历史页取最近 365 个本地日的夜晚，从其中最早的一晚开始列，新的历史不会先列出一年空行：顶部是近 30 晚的平均时长、平均入睡与平均醒来时间，下面每天一行，最新在上，按周用细线分隔，每行在 20:00 到次日 10:00 的夜轴上画出这一晚。点有记录的一行打开修改对话框（可删除，删除需再点一次「确认删除」），点没有记录的一行打开补记对话框。

## 接口

| 方法与路径 | 作用 |
| --- | --- |
| `GET /api/sleep/running` | 当前的开始 `{ started_at }`，没有时 `started_at` 为 `null` |
| `PUT /api/sleep/running` | 开始睡眠，返回新的开始 |
| `POST /api/sleep/running/end` | 以 `{ started_at }` 结束，返回新的一晚 |
| `GET /api/sleep/nights?start=&end=` | 醒来时间在 `[start, end)` 内的夜晚，按醒来时间排序；区间不超过 400 天 |
| `POST /api/sleep/nights` | 以 `{ started_at, ended_at }` 补记一晚 |
| `PUT /api/sleep/nights/{id}` | 修改一晚的时间段，Moment 随醒来时间移到新的日子，身份不变 |
| `DELETE /api/sleep/nights/{id}` | 删除一晚及其 Moment |

时间都是 epoch 毫秒。夜晚列表的上限 400 天覆盖历史页的一年加上跨时区与夏令时的余量，又不会一次读出全部历史。

## 不变量

1. 一晚恰好是一个 `kind = 'sleep'` 的 Moment 加一条 `sleep` 详情，二者 `id` 相同，`upper(span)` 等于 `moment.occurred_at`。
2. 一晚的时间段非空、有限、毫秒精度，长度不超过 24 小时。
3. 同一 Owner 的任意两晚不重叠。
4. 每个 Owner 至多有一个计时中的开始；开始总是替换旧的开始。
5. 结束只消耗与请求 `started_at` 相同的开始，并且与插入这一晚在同一事务中；失败时开始保留。
6. 对同一个开始重复结束，得到同一晚，不产生第二晚。
7. 修改一晚不改变它的 Moment 身份；删除一晚不留下没有详情的 Moment。
8. 一晚、开始与它们的读写都限定在 Owner Scope 内；跨 Owner 的读写都是未找到。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| 一晚归入入睡那天 | 与“晚上的事”一致 | 凌晨入睡会落到另一天；早上打开今天的页面看不到昨晚，置顶的意义就没了 |
| 计时中的开始也是 Moment（`ended_at` 为空） | 只有一张表 | 计时不是时间线上的一条记录；还要用可选字段区分两种状态，正是领域模型禁止的形状 |
| 服务端按部署时区判断 18:00、15:00 | 规则集中在一处 | 部署时区不是用户所在时区；与时间线按浏览器时区归日冲突 |
| 后台任务清理作废的开始 | 服务端状态更“干净” | 需要服务端知道用户钟点；每个 Owner 至多一个开始，下一次开始替换它就够了 |
| 结束放在菜单里 | 菜单项统一 | 结束是计时中最常做的事，藏在悬停菜单后面多一步；在手机上更难点 |
| 写入事务内用 advisory lock 防重叠 | 详情表不重复保存终点 | 依赖每个写入方都加锁；排他约束对任何写入方都成立 |
| 历史页用月历 | 一眼看出哪天没记录 | 看不出入睡和醒来的早晚，夜轴叠起来能看出作息的漂移（原型变体对比后选定） |

## 风险与为什么不能直接改写

一晚的 Moment `id` 一旦出现在时间线和历史页里就不能替换，修改只改时间段。`span` 与 `moment.occurred_at` 的相等关系若被单独改写其中一处，提交时检查会拒绝整个事务；任何迁移都必须在同一事务里同时改两处。

## 本决策未解决的问题

- **一年以前的历史**：历史页只读最近 365 天；更早的夜晚仍在库里，翻页留给真有需要时再定。
- **午睡与一天多晚**：数据允许同一天归入多晚（不重叠即可），时刻页只置顶最晚的一晚；是否单独呈现午睡，等有需求再定。
- **设备数据导入**：手环或手机健康数据的导入、分期与评分不在本决策范围。

## 落地与验收

迁移 `0021_sleep.sql` 启用 `btree_gist`，扩展 `moment.kind`，新建 `sleep` 与 `sleep_start`，更新提交时详情检查。`palace-domain` 校验时间段；`palace-db` 提供开始、结束、补记、修改、删除与按区间读取，时间线返回睡眠卡片；`palace-backend` 暴露上表的接口并进入 OpenAPI；`apps/palace-web` 在时刻页实现表盘、菜单项、记录对话框与 06:00 确认，新增 `/sleep` 历史页。

真实 PostgreSQL 测试覆盖不变量 1–8；HTTP 契约测试覆盖接口的响应结构；前端测试覆盖钟点规则、表盘与菜单的状态、确认对话框与历史页的修改和删除。
