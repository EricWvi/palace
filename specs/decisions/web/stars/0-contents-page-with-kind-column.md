# 摘星入口是目录式列表：左侧一列内容类型，右侧按年分组、一行一条，第一版只开放对话

「摘星」导航变为可点击，进入摘星的入口页。页面像一本书的目录：左侧一列内容类型「笔记 / 文章 / 对话」，右侧是当前类型的条目，按年分组，每条一行，标题后以点线连到日期。第一版只有「对话」可以打开，笔记和文章照常显示但不可点击。对话列表一行代表一条 Path，显示该 Path 的标题，与时间线上的对话 Moment 一一对应；同一 Conversation 的多条 Path 各占一行。服务端新增分页的对话列表接口，支持按 Path 标题和 Path 上的消息内容搜索；按 `/` 打开搜索，回车执行。

当前为 `approved`，核心测试用例见[摘星入口页](../../../test-cases/web/stars/contents-page.md)。这是 `web/stars` 的根决策，没有前序 ADR；它修改[Web 导航根决策](../navigation/0-text-nav-day-routes-and-moment-opening.md)的 D1（摘星不可点击）与 D3（没有来源日期时的落点），解决了该决策“本决策未解决的问题”中的“摘星入口页”。视觉参照为 `design/3.1-stars.html`；笔记详情页的参照 `design/3.2-stars-note.html` 不在本决策范围内。

## 问题与约束

- 摘星收录三类内容：对话、笔记、文章，用来“留下值得再次使用的内容”。「时刻」已经按日期浏览一切，摘星不应再做一份按时间排列的混合流。
- 回到摘星的人通常已经知道要找哪一类东西，所以第一层按类型分。三类内容都是“标题 + 一篇正文”，列表可以共用同一种样式。
- 目前只有对话已经实现；笔记与文章的数据和详情页尚未落地。原对话列表接口已按[Moment 根决策](../../server/moment/0-moment-supertype-and-typed-details.md)移除，服务端现在只能按天列举对话 Moment，没有跨日期的列表接口。
- 标题属于 Path（[标题归属](../../server/conversation/20261005-title-belongs-to-path.md)），时间线上一张对话卡片也对应一条 Path。
- Palace 主要由 Eric 自用，美观简洁优先于可发现性；Web 端以文字为主，少放按钮、图标和说明文案（同 Web 导航根决策的约束）。

## D1：地址与导航

| 地址 | 含义 |
| --- | --- |
| `/conversations` | 摘星入口页，显示对话列表 |
| `/conversations?q=<关键词>` | 同上，显示搜索结果 |
| `/conversations/:id` | 对话阅读页，规则不变 |

- 顶部导航的「摘星」链接指向 `/conversations`。在 `/conversations` 和 `/conversations/:id` 上，摘星都带 `aria-current="page"`。
- 每种类型的列表用自己的路径（以后是 `/notes`、`/articles`），与详情页的路径 `/<类型>/:id` 成对，不用 `?kind=` 参数。原型用 `?kind=` 只是因为它是一个静态文件。
- 摘星链接暂时固定指向对话列表。以后有了多种类型，“回到上次停留的类型”由引入笔记的决策决定。

## D2：左侧的类型列

左侧一列自上而下是「笔记」「文章」「对话」，每项右侧用小字写条数。顺序把自己写的内容放在最前，这是预期最常用的一类。

| 状态 | 表现 |
| --- | --- |
| 当前类型 | 正文色，带 `aria-current="page"` |
| 可打开的其他类型 | 浅色文字，悬停加深；是指向该类型列表的链接 |
| 尚未开放（第一版的笔记、文章） | 浅色文字，不是链接，不进入 Tab 顺序，没有悬停效果，不显示条数 |

- 类型列与右侧列表的顶端对齐，即与时刻页的日期标题处在同一高度；页面滚动时，类型列停留在视口上方。
- 尚未开放的类型照常显示，与导航根决策 D1 的理由相同：这一列的形状在功能陆续上线时保持不变，三个词本身也说明了摘星装的是什么。
- 条数是该类型的全部条目数，不随搜索变化。
- 窄屏下类型列改为列表上方的一行，只保证不破版，不代表移动端设计。

## D3：对话列表的一行

一行代表一条 Path，与时间线上的对话 Moment 一一对应。同一 Conversation 有几条 Path，列表中就有几行。

```
2026
改去 Point Reyes  ChatGPT ······························ 10.07
PostgreSQL advisory lock 的用法  Gemini ················ 10.05
计划周末出行  ChatGPT ································· 09.30
```

| 部分 | 内容 |
| --- | --- |
| 标题 | 该 Path 的标题，用展示字体（`--font-display`，18px）；过长时以省略号截断 |
| 来源 | Conversation 的来源名称，小字浅色，紧跟标题 |
| 点线 | 从来源延伸到日期，填满中间的空白 |
| 日期 | 该 Path 的 `updated_at`，按浏览器本地时区显示为 `MM.DD` |
| 年份标题 | 同一年的条目归到一个年份标题下，年份也按本地时区计算 |

- 列表按 Path 的 `updated_at DESC`、Path ID 降序排列，与阅读页选择默认 Path 的顺序相同。
- 点击一行进入 `/conversations/:conversation_id?path=<Path ID>`，不带 `date`。
- 同一 Conversation 的几条 Path 不合并，也不排在一起，各自按更新时间落在自己的位置。分支往往讨论不同的事，标题也不同；把它们当作各自独立的条目，与时间线上各自出现在不同日期的做法一致。
- 同名的分支（新建分支默认沿用原标题）会出现几行标题相同的条目，靠日期区分，不加 Session ID 一类的后缀。它们点开后在同一个阅读页中，分叉处的文字已经负责区分（对话阅读页 D2）；目录里多一个后缀，只会让所有行都更嘈杂。
- 不显示消息数和摘录。目录只回答“是哪一篇、什么时候”；摘录常常是寒暄，读起来很吵（与对话阅读页 D2 不用消息开头给分支命名同理），消息数进入阅读页就能看到。

**为什么一行是 Path 而不是 Conversation**：标题属于 Path，一个 Conversation 没有自己的标题。以 Conversation 为一行时必须挑一条 Path 代表它：挑默认 Path，行的名字会在其他分支更新后改变；挑最早的 Path，点开后看到的标题可能与行上不同。两种做法还都让其他分支在目录中消失，只能进入阅读页从分叉处找到。以 Path 为一行时，行的标题、日期和点开后的页首完全一致，也与时间线的粒度相同。

## D4：搜索

- 列表上方平时没有搜索框。在页面上（焦点不在输入框里时）按 `/`，类型列右侧、列表上方出现一条只有下划线的输入框并获得焦点。
- 在输入框里按回车才执行一次搜索；输入过程中不发请求，列表保持不变。关键词去除首尾空白后，不区分大小写，按子串匹配该 Path 的标题，或该 Path 从根到末端任一条消息的正文。
- 执行搜索时，关键词以替换历史记录的方式写入 `?q=`，从阅读页后退时回到同一组结果。关键词为空时按回车，等同于清除搜索：移除 `q`，回到完整列表。
- 标题中的匹配部分用 `--accent-soft` 底色标出。匹配只发生在正文时，这一行照常显示，不标注匹配位置。
- 分支共享从根开始的前缀，匹配落在共享消息上时，共享这些消息的每条 Path 都会出现在结果中。这与“一行是一条 Path”一致：每一行点开后都能读到那条消息。
- 在输入框里按 Esc：有内容时清空输入框，并清除已执行的搜索（移除 `q`，回到完整列表）；内容为空时收起输入框。
- 没有结果时显示一行浅色小字“没有找到。”。

回车才搜索，是因为搜索要扫描消息正文，逐字触发会在输入中文时为每个拼音中间态发一次请求；结果列表也不会在输入时来回跳动。代价是要多按一次回车，对一个已经知道要找什么的读者可以接受。

搜索放在服务端，是因为消息正文只在服务端，单条可达 1 MiB，不能为了搜索把它们下发到浏览器。子串匹配而不是全文检索，是因为 PostgreSQL 内置的分词不切中文。

子串匹配用 `ILIKE` 实现，并在这一版就为消息正文建 trigram 索引：

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX message_content_trgm ON message USING gin (content gin_trgm_ops);
```

- 索引建在 `message.content` 上，即原始 Markdown，不新增去掉标记的纯文本列。子串搜索几乎不受 `**`、反引号一类标记影响；代价是链接地址等不可见文字也能被搜到，换来的是不需要在导入时多写一列、也不需要回填现有消息。
- 不扫描全部消息正文，是因为它们是库里最大的数据。标题表小，只用 `ILIKE` 扫描，不建索引。
- 关键词中的 `%`、`_` 与 `\` 按字面量转义后再拼成 `%关键词%`，用户输入不会成为通配符。
- 索引只影响速度，不影响结果：少于 3 个字符的关键词（如两个汉字）提取不出 trigram，PostgreSQL 退回全索引扫描，结果仍由 `ILIKE` 复核。中文字符要计入 trigram，数据库的 `LC_CTYPE` 不能是 `C`；当前 `postgres:17-alpine` 默认的 `en_US.utf8` 满足这一点。
- `pg_trgm` 自 PostgreSQL 13 起是 trusted 扩展，数据库 owner 即可在迁移中创建，不需要超级用户。

## D5：对话列表接口

新增 `GET /api/conversations`，按 Path 列出当前 owner 的对话：

| 参数 | 含义 |
| --- | --- |
| `q` | 可选，搜索关键词，语义见 D4；去除首尾空白后为空，视同未提供 |
| `cursor` | 可选，上一页返回的 `next_cursor` |

响应：

```json
{
  "items": [
    {
      "id": "<Path ID>",
      "conversation_id": "<Conversation ID>",
      "title": "改去 Point Reyes",
      "source": "chatgpt",
      "updated_at": "2026-10-07T21:14:03+08:00"
    }
  ],
  "next_cursor": "…",
  "total": 9
}
```

- `id` 是 Path ID，也是对应对话 Moment 的 ID；字段命名与时间线的对话卡片一致（对话 Moment 卡片字段 D1）。`title` 与 `updated_at` 来自 Path，`source` 来自 Conversation，查询时派生，不另外保存。
- 每页 50 条，按 D3 的顺序以 keyset 分页：游标编码最后一行 Path 的 `(updated_at, id)`，没有下一页时 `next_cursor` 为 `null`。用 keyset 而不用偏移量，是因为浏览时可能有新导入，偏移量会让条目在两页之间重复或丢失。
- `total` 是该 owner 的 Path 总数，不受 `q` 影响，供类型列显示条数；它与列表不加搜索时的行数相同。
- 前端滚动到列表末尾时加载下一页。

## D6：从阅读页回到摘星

- 没有 `date` 的对话阅读页（从摘星或直接链接进入），删除整个对话后进入 `/conversations`，替换当前历史记录，后退不会回到已删除的对话。
- 从摘星进入阅读页后按浏览器后退，回到原来的列表：`q` 由地址恢复，已加载的页面和滚动位置由前端缓存恢复。
- 在阅读页删除单条 Path、删除整个对话，或编辑标题与来源后，列表缓存随之失效；回到列表时不出现已删除的行，也不显示旧标题。
- 从摘星进入的阅读页不显示返回链接，与导航根决策 D3 一致：返回链接只说明“回到哪一天”，摘星没有日期可写，浏览器后退已经足够。

## 不变量

1. 在 `/conversations` 与 `/conversations/:id` 上，导航中摘星是唯一带 `aria-current="page"` 的项。
2. 尚未开放的类型不是链接，也不进入 Tab 顺序。
3. 列表中的每一行恰好对应一条 Path，点开后阅读页展示的就是这条 Path，页首标题等于行上的标题。
4. 不加搜索时，当前 owner 的每条 Path 在列表中恰好出现一次。
5. 列表顺序与 Path 的 `updated_at DESC, id DESC` 一致，分页之间不重复、不遗漏。
6. 列表接口只返回当前 owner 的 Path，搜索也不会匹配到其他 owner 的标题或消息。
7. 搜索结果中的每一行，其 Path 的标题或该 Path 上至少一条消息包含关键词。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| 类型作为页面标题（「对话 笔记 文章」三个大字）+ 两行条目按月分组（原型变体 A） | 层级清楚，可以放来源和摘要 | 一屏条目少，找东西要多滚动；Eric 在原型评审中选了目录式 |
| 搜索优先，三类混合列表加 `[ 类型 ]` 前缀（原型变体 C） | 一个入口找所有内容 | 与时刻的时间线重复；按更新时间混排时，改得最勤的笔记会把对话和文章挤到后面 |
| 一行代表一个 Conversation，显示默认 Path 的标题 | 同名分支不会重复出现，行数更少 | 其他分支在目录中消失；分支更新后行的名字随之改变 |
| 一行代表一个 Conversation，显示最早 Path 的标题（沿用标题归属决策） | 名字稳定 | 点开的默认 Path 标题可能不同，违反不变量 3；其他分支同样消失 |
| 同一 Conversation 的 Path 排在一起，缩进显示分支 | 看得出哪些是同一棵树的分支 | 目录里出现树形结构，违背一行一条的目录样式；排序不再只按时间，较旧的分支会被拉到新条目旁边 |
| 前端拉取全部对话后本地过滤 | 实现简单，搜索零延迟 | 搜索正文需要下发全部消息；分页后本地过滤也只能覆盖已加载的部分 |
| 用 PostgreSQL 全文检索（tsvector） | 有排序和词形处理 | 内置配置不切中文，需要额外的分词扩展；单用户数据量下子串匹配已经够用 |
| 先不建索引，等变慢再加 | 少一个迁移和扩展依赖 | 每次搜索都扫描全部消息正文；正文是库里最大的数据，变慢时已经影响日常使用，不如一开始就建 |
| 输入时实时搜索 | 不用按回车，结果即时出现 | 输入中文时每个拼音中间态都触发一次正文扫描，列表随输入来回跳动 |
| 新增去掉 Markdown 标记的 `raw_text` 列并在其上建索引 | 只匹配可见文字 | 每条消息多存一份正文，导入时要多写一列，现有消息需要回填；子串搜索对标记几乎不敏感，收益很小 |
| `?kind=` 选择类型 | 一个路由承载三类 | 与 `/conversations/:id` 等详情路径不成对；每类的列表将来可能需要各自的参数 |

## 本决策未解决的问题

- **笔记与文章**：数据模型、列表字段、详情页（参照 `design/3.2-stars-note.html`）与导入接口由各自的决策决定。开放时在类型列中改为可点击，列表样式沿用 D3。
- **`n` 新建笔记**：原型中的快捷键随笔记一起引入。
- **摘星链接的落点**：有多种类型以后，是否回到上次停留的类型。
- **跨类型搜索**：第一版只搜当前类型。

## 落地顺序

1. **列表接口**：实现 D5，包括按 Path 的 keyset 分页、`total` 与 `q` 搜索，以及启用 `pg_trgm` 并创建 `message_content_trgm` 索引的迁移。完成条件是真实 PostgreSQL 测试覆盖不变量 4–7：每条 Path 恰好出现一次、排序与分页的不重不漏、owner 隔离和搜索匹配范围。这一步不改变任何界面。
2. **入口页**：实现 D1–D3 与 D6，导航中摘星变为可点击，类型列中只有对话可以打开。完成条件是组件测试覆盖不变量 1–3，Chromium 测试覆盖后退时恢复滚动位置、删除后的落点。
3. **搜索**：实现 D4 的 `/` 输入框、回车执行与 `?q=`。单独成一步，使入口页可以先上线，搜索的交互细节可以单独评审。

从第 2 步起，「摘星」从不可点击变为可点击，没有 `date` 的对话阅读页删除后落到 `/conversations` 而不是 `/`；时刻页、对话阅读页的其他行为不变。
