# 笔记来自挂载的 Markdown 文件夹：脚本生成 frontmatter cache，服务端监听 cache 提供列表，rg 搜索正文，Palace 只读

> 历史决策：D3 中“将来的文章也对所有已登录用户只读、不属于 Owner”已被[文章决策](20261020-articles-imported-with-media.md) D1 取代，文章是 Owner 数据；D7 的笔记页版式现在与文章页共用。D4 中“每篇笔记的 frontmatter 必须包含”所针对的文件范围已被[跳过没有 frontmatter 或草稿的决策](20261022-notes-skip-files-without-frontmatter-or-drafts.md)修改：没有 frontmatter 或 `draft: true` 的 Markdown 不是笔记，脚本跳过并列出。

摘星开放「笔记」。笔记不存数据库，而是一个由 Eric 在 Palace 之外维护的 Markdown 文件夹，挂载进容器。Palace 提供一个 TypeScript 脚本，把每篇笔记 frontmatter 中的 `title`、`date` 收集成一个 cache 文件，放在笔记文件夹根目录；服务端只监听这一个文件，变动时整体替换内存中的笔记索引。笔记列表由内存索引提供，按 `date` 倒序；搜索由容器内的 ripgrep 扫描笔记文件夹完成；笔记页的样式沿用对话阅读页，读取的是 Markdown 文件本身。Palace 不新建、不编辑、不删除笔记。摘星导航改为指向 `/notes`。

当前为 `implemented`，核心测试用例见[摘星笔记](../../../test-cases/web/stars/notes.md)。本决策基于[摘星入口页根决策](0-contents-page-with-kind-column.md)，开放其中预留的笔记类型；涉及 `apps/palace-web` 的摘星与笔记页、`palace-backend` 的笔记接口、`palace-server` 的配置与运行时、`Dockerfile`，以及新增的 cache 生成脚本。笔记的 tag 与层级、文章类型、旧数据库中 Quick Note 等内容的迁移不在本决策范围内。

## 问题与约束

- 笔记合并了原来的笔记、Quick Note、cheatsheet 和自己写的 Blog 文章（见导航设计记忆）。这些内容 Eric 习惯在编辑器里以 Markdown 文件维护，并会不时修改；在 Palace 里再做一个编辑器，既重复又会和文件形成两份真相。
- 笔记不在时刻里出现，所以不需要成为 `moment`，也不需要进入数据库参与时间线查询。
- 笔记文件会不时更新。若服务端直接监听整个文件夹，需要递归监听、在每次保存时重新解析 frontmatter；挂载盘为 NFS/SMB 时 inotify 不可靠，只能周期性全量扫描。把“文件夹 → 索引”这一步放到容器外的脚本中，服务端只关心一个文件，监听和失败处理都简单得多。
- 图片都是 S3 链接，笔记文件夹里没有需要 Palace 提供的本地资源，服务端只读取 `.md` 文件。
- Palace 主要由 Eric 自用；美观简洁优先，笔记页与对话阅读页共享 Markdown 渲染与版式，跳过原型设计。

## D1：地址与导航

| 地址 | 含义 |
| --- | --- |
| `/notes` | 摘星入口页，显示笔记列表 |
| `/notes?q=<关键词>` | 同上，显示搜索结果 |
| `/notes/<id>` | 笔记页；`<id>` 可以包含 `/`，见 D4 |

- 顶部导航的「摘星」链接改为指向 `/notes`。在 `/notes`、`/notes/<id>`、`/conversations`、`/conversations/:id` 上，摘星都带 `aria-current="page"`。
- 指向 `/notes` 而不是“上次停留的类型”：笔记是预期最常用的一类（根决策 D2 把它排在第一位），固定落点不需要额外记住状态。代价是常看对话时要多点一次类型列。
- 对话阅读页删除整个对话后的落点仍是 `/conversations`：删除前读者在对话里，回到对话列表才连贯。

## D2：Palace 对笔记只读

- Palace 不提供新建、编辑、删除、重命名笔记的界面或接口。笔记页没有 `···` 菜单。
- 笔记的唯一真相是文件夹中的 Markdown 文件；增删改都在 Palace 之外完成，再由 cache 脚本反映到 Palace。

**为什么**：笔记在编辑器中维护，有版本管理和顺手的编辑体验；Palace 若也能写，就要处理两边同时修改、写回挂载卷的权限和格式保真，而得到的只是一个更弱的编辑器。只读让 Palace 与文件之间只有单向数据流。

## D3：访问范围

- 挂载进摘星的只读内容（本决策的笔记，以及将来的文章）对所有已登录用户可读，不属于任何 Owner，不带 `owner_id`。
- 未登录请求与其他接口一样被拒绝；单用户测试入口下由固定测试用户访问。

**为什么**：挂载卷是部署级资源，不存在“谁的”这一问。给它绑定一个 Owner（例如通过环境变量指定 email）只会让配置多一项，而单用户部署下没有任何隔离收益。Owner 根决策约束的是数据库里的 Owner 数据，这里没有对应的表。

## D4：笔记的身份与 frontmatter

- 笔记 ID 是 Markdown 文件相对笔记文件夹根目录的路径去掉 `.md` 后缀，分隔符统一为 `/`，例如 `rust/advisory-lock`。前端地址 `/notes/<id>` 中每一段分别做 URL 编码；接口 `/api/notes/{id}` 中整个 ID 是一个路径段，`/` 编码为 `%2F`。
- 服务端加载 cache 时检查每个 ID：空段、`.`、`..`、反斜杠或会构成绝对路径的 ID 使整份 cache 被拒绝，因此索引中的 ID 只能指向文件夹内的文件。
- 改名或移动文件会改变 ID，旧链接随之失效。笔记以文件为主，文件路径就是作者心目中的名字；为了链接稳定而要求每篇笔记手写一个 `id`，代价大于收益。
- 每篇笔记的 frontmatter 必须包含：

  | 字段 | 规则 |
  | --- | --- |
  | `title` | 非空字符串，列表与笔记页的标题 |
  | `date` | `YYYY-MM-DD`，或带时区偏移的 RFC 3339 时间 |

  其他字段（包括 `tag`）原样保留在文件中，cache 不收集，Palace 暂不使用。
- 只有日期的 `date` 按 `PALACE_TIMEZONE` 的当天 00:00 解释为时间点。`PALACE_TIMEZONE` 因此从“日志时区”扩展为“部署的本地时区”，文档同步更新。
- 列表日期就是 `date`，不用文件的修改时间，也不收集 `updated`：笔记会被反复修改，按修改时间排列会让最近碰过的笔记不断跑到前面，目录日期也随之漂移。与根决策 D3 不用 Path `updated_at` 的理由相同。

## D5：cache 文件与内存索引

### 生成脚本

- 脚本是 `scripts/notes-cache.ts`，用 Node 24 直接运行，参数是笔记文件夹路径；在容器外由 Eric 的工作流触发（手动、git hook 或定时任务均可，不属于 Palace 的职责）。
- 脚本用 `rg --no-config --files --no-require-git --type-add 'note:*.md' --type note` 枚举笔记文件，而不是自己遍历目录。这样列表与搜索（D6）看到的是同一组文件，`.gitignore`、`.ignore` 和隐藏文件的规则只有 ripgrep 一种解释。`*.md` 用文件类型选择而不是 `--glob`：`--glob` 的规则优先于 ignore 文件，会把 `.ignore` 排除的笔记重新选回来（评审时写的是 `-g '*.md'`，实现时发现并改正）。
- frontmatter 按 YAML core schema 解析，`date: 2026-10-05` 保持为字符串，不会被解析成 UTC 零点而换了日期。
- 脚本解析每个文件的 frontmatter，按 D4 校验；任何一篇不合格时报告所有问题并以非零状态退出，不写 cache。Palace 只信任 cache，不重复校验。
- cache 写在笔记文件夹根目录的 `.palace-cache.json`，先写临时文件再 rename 原子替换。它以点开头且不是 `.md`，ripgrep 既不枚举也不搜索它，不需要写进 `.ignore`（评审稿曾要求写入，实现时去掉）。
- cache 是 `{ version: 1, notes: [{ id, title, date }] }`，`date` 保持 frontmatter 中的原文，由服务端按 D4 换算。

### 服务端

- 新增可选环境变量 `PALACE_NOTES_DIR`，指向容器内的笔记文件夹。未配置时，笔记列表为空，类型列照常显示条数 0。
- 服务端非递归地监听 `PALACE_NOTES_DIR` 目录，只处理文件名为 `.palace-cache.json` 的事件；另外每分钟比较一次 cache 的修改时间、大小与 inode 作为兜底，覆盖 inotify 不触发的挂载盘。编辑笔记本身不会唤醒服务端。
- 变化时完整读取并解析 cache，按 `date DESC, id DESC` 排好，整体替换内存索引。任何一项不合格（ID 越界、标题为空、日期无法解析、ID 重复）都拒绝整份 cache。请求读取的总是某一份完整索引，不会看到解析到一半的状态。
- 解析失败（文件缺失、JSON 损坏、版本不认识）时保留上一份索引并记录错误日志；启动时没有可用的 cache，则以空索引启动，不阻止服务启动。

**为什么挂载目录而不是单个 cache 文件**：单文件 bind mount 绑定的是 inode；脚本原子替换 cache 后，容器里看到的仍是旧 inode，变化永远不会被发现。cache 放在笔记文件夹内，整个文件夹只挂载一次，rename 在容器内可见。

## D6：笔记列表接口与搜索

`GET /api/notes`，参数与语义同根决策 D5 的对话列表：

| 参数 | 含义 |
| --- | --- |
| `q` | 可选，搜索关键词；去除首尾空白后为空，视同未提供 |
| `cursor` | 可选，上一页返回的 `next_cursor` |

响应为 `{ items, next_cursor, total }`，`items` 的每一项是 `{ id, title, occurred_at }`，`occurred_at` 是 `date` 换算出的 epoch 毫秒。每页 50 条，按 `occurred_at DESC, id DESC` 以 keyset 分页，游标编码最后一行的 `(occurred_at, id)`；无法解析的游标返回 400。`total` 是当前索引的笔记总数，不受 `q` 影响。用 keyset 的理由与对话相同：浏览时 cache 可能被替换，偏移量会让条目重复或丢失。

搜索：

- 标题匹配在内存中完成：不区分大小写的子串匹配。
- 正文匹配调用 `rg --no-config --files-with-matches --null --fixed-strings --ignore-case --no-require-git --type-add 'note:*.md' --type note -e <关键词> .`，以笔记文件夹为工作目录，参数直接传给进程而不经过 shell。`--fixed-strings` 让关键词按字面量匹配，与对话搜索转义 `%`、`_` 的语义一致；`-e` 让以 `-` 开头的关键词不被当成选项；`--no-config` 让运行环境里的 ripgrep 配置不能改变哪些文件参与搜索。
- 命中的文件映射回 ID，只保留当前索引中存在的笔记；与标题命中的结果合并，按列表顺序分页。cache 尚未刷新时新文件搜不到、已删除的文件不出现，结果始终是索引的子集。
- frontmatter 是文件的一部分，因此 `tag` 等字段里的文字也能被搜到；这对“找一篇笔记”是有益的，不做剔除。
- rg 每次搜索限时 10 秒；超时、不可执行，或退出码既不是 0（有匹配）也不是 1（无匹配）时，接口返回 503 `search_unavailable`，前端显示错误状态，不把部分结果当作完整结果。
- 每次翻页都重新执行一次 rg。单用户、笔记数量在千级时，一次扫描的成本可以接受，不缓存搜索结果，也就不需要处理缓存与 cache 刷新之间的一致性。

`rg` 不需要容器里有 git：它自己解析 `.gitignore`，但默认只在 git 仓库内才应用，所以必须带 `--no-require-git`（挂载的通常不是仓库根目录）。运行镜像通过 `apk add ripgrep` 安装。

## D7：笔记页

`GET /api/notes/{id}` 返回 `{ id, title, occurred_at, content }`，`content` 是去掉 frontmatter 后的 Markdown 正文。

- 服务端只读取当前索引中存在的 ID 对应的文件；不在索引中的 ID 返回 404。路径因此只来自脚本生成的 cache，而不是请求，请求中的 `..` 或绝对路径无法读到笔记文件夹之外的文件。
- 文件在索引中但已被删除或无法读取时返回 404，并记录日志。
- 每次请求都从文件读取正文，不缓存。正文修改后无需重新生成 cache 即可看到；标题和日期以 cache 为准，直到下一次生成。
- 页面沿用对话阅读页的版式：页首是标题与 `YYYY.MM.DD` 日期；正文第一行若是一级标题，由它代替 frontmatter `title` 作页首标题并从正文中移除，避免同一标题出现两次，日期挂在它下面。正文用共享的 Markdown 组件渲染（含代码高亮），图片按原地址加载（都是 S3 链接）。不存在的笔记显示“找不到这篇笔记。”。没有 `···` 菜单，也没有任何修改笔记的操作。
- 笔记目录复用对话阅读目录的外观与交互，按实际渲染的 H1–H6 顺序列出，页首标题计作 H1。H1 横线最长，层级越深越短，展开后按层级缩进；同名标题使用独立锚点，代码块不作为标题。点击后跳转并固定当前标记，读者自行滚动后解除。悬停 350ms 展开，提前离开或移出浏览器取消；键盘进入立即展开。标题不足两条或窗口宽度不足 900px 时隐藏。
- 从摘星进入的笔记页不显示返回链接，与根决策 D6 一致。

## 不变量

1. 在 `/notes`、`/notes/<id>`、`/conversations`、`/conversations/:id` 上，摘星是导航中唯一带 `aria-current="page"` 的项，链接目标是 `/notes`。
2. Palace 不提供任何改变笔记文件的接口；笔记文件夹以只读方式挂载时，所有功能照常工作。
3. 笔记接口对任一已登录用户返回相同结果，未登录请求被拒绝。
4. 不加搜索时，当前索引中的每篇笔记在列表中恰好出现一次；顺序是 `occurred_at DESC, id DESC`，分页之间不重复、不遗漏。
5. 每一行的日期等于该笔记 frontmatter 的 `date`，与文件修改时间无关。
6. 搜索结果是当前索引的子集，每一行的标题或文件内容包含关键词（不区分大小写的字面量匹配）。
7. 被 `.gitignore`、`.ignore` 排除的文件既不出现在列表中，也不出现在搜索结果中，无论笔记文件夹是否位于 git 仓库内。
8. 笔记页只能读取当前索引中列出的文件；任何请求都读不到笔记文件夹之外的文件。
9. cache 解析失败不会清空或部分替换已有索引。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| 服务端直接递归监听笔记文件夹，自行解析 frontmatter | 不需要脚本，不会忘记重新生成 | 每次保存都要触发重新解析，挂载盘上 inotify 不可靠时只能频繁全量扫描；ignore 规则也要在 Rust 中再实现一遍 |
| 笔记存入数据库，在 Palace 中编辑（3.2 原型） | 与对话一样带 Owner、可在 Web 端随手写 | 与编辑器中维护的文件形成两份真相，需要双向同步或放弃编辑器；违背只读的单向数据流 |
| 单独 bind mount cache 文件 | 挂载最小 | 原子替换后容器看到旧 inode，变化检测失效 |
| 用 frontmatter 中手写的 `id` 作为笔记身份 | 改名不影响链接 | 每篇笔记多一个必填字段且必须手工保证唯一；Eric 自用，失效的旧链接很少 |
| 按 `updated` 或文件 mtime 排序 | 最近改过的笔记在前 | 目录日期随修改漂移；`git checkout` 等操作会改写 mtime，顺序不可预期 |
| 启动时把全部正文读入内存，在内存中搜索 | 搜索不依赖外部程序 | 正文常驻内存，且每次正文修改都要重新加载，又回到监听整个文件夹的问题 |
| 用 SQLite/PostgreSQL 全文索引正文 | 搜索更快，可排序 | 需要把正文同步进数据库，同样要监听文件夹；中文分词问题与对话搜索相同 |
| 笔记绑定到配置的 Owner | 与 Owner 隔离模型形式一致 | 部署级资源没有归属问题，多一项配置而没有隔离收益 |
| 摘星记住上次停留的类型 | 常看对话的人少点一次 | 需要持久化前端状态；笔记是预期最常用的类型，固定落点足够 |

## 本决策未解决的问题

- **tag 与层级**：笔记的层级关系以后用 frontmatter 的 tag 表示；cache 何时收集 tag、列表如何按 tag 浏览，由后续决策决定。
- **文章**：文章同样对所有已登录用户只读（D3），但来源与列表字段由文章自己的决策决定。
- **跨类型搜索**：仍只搜当前类型。
- **cache 过期提示**：Palace 不判断 cache 是否落后于文件夹，忘记运行脚本时只表现为新笔记不出现。

## 落地与验收

- `scripts/notes-cache.ts` 生成 cache，`task test:scripts` 用真实 ripgrep 覆盖枚举、校验与原子写入。
- `palace-notes` crate 拥有 cache 解析、内存索引、目录监听与轮询、ripgrep 搜索和正文读取；它不依赖数据库，也不接受 Owner。`palace-backend` 新增 `GET /api/notes` 与 `GET /api/notes/{id}`，`palace-server` 的两个入口从 `PALACE_NOTES_DIR` 构造 `NoteLibrary` 并保持监听。运行镜像安装 `ripgrep`。
- `apps/palace-web` 的 `StarsPage` 按类型显示笔记或对话列表，两个列表都加载第一页以便类型列显示两种条数；新增 `NotePage` 承担 `/notes/*`；摘星链接改为 `/notes`。
- 真实文件系统与真实 ripgrep 的测试覆盖不变量 4–9，真实 PostgreSQL 与真实 Router 的 HTTP 测试覆盖不变量 3 与接口层的不变量 6、8，组件测试覆盖不变量 1、2 与笔记页。证据见核心测试用例。

对话列表、对话阅读页、搜索交互与时间线的行为保持不变；摘星的落点从对话列表变为笔记列表。
