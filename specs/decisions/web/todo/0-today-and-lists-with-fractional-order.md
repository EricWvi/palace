# 行事页是「今日」加集合的目录式页面，任务按 fractional-indexing 键排序，今日已做与完成分开，搁置是独立的排期状态

> 历史决策：D1 中「集合按创建顺序排列，不能拖动」、D5 中集合接口只带 `{ name }`，以及「本决策未解决的问题」中的「集合的排序」，已由[集合按拖动的顺序排列](20261031-lists-in-dragged-order.md)修改。

「行事」导航变为可点击，进入任务（Todo）的管理页。页面宽约 920px，比默认的 760px 宽、比回响的 1200px 窄。左列是「今日」、收件箱和各个集合，右侧显示选中的那一个。今日按集合分组列出排在当天的任务，任务前的圆圈表示「今日已做」，累计做过的天数加一，任务本身仍然开着；「完成」才把任务归入集合底部的「已完成」。「安排」或 `p` 在原地列出收件箱以外、没有搁置的任务，勾选后排入今日。集合内拖动排序，顺序由前端用 `fractional-indexing` 生成的字符串键决定，拖动只写被拖动的那一条。搁置是排期的第三种状态，不再用旧版 2096 年的哨兵日期。交互定稿见原型 [`design/5.1-todo.html`](../../../../design/5.1-todo.html)。

当前为 `implemented`，核心测试用例见[行事](../../../test-cases/web/todo/todos.md)，接口与用法见[行事功能文档](../../../../docs/features/todos/README.md)。本文件是 `web/todo` 的根决策，没有前序 ADR。它修改 [Web 导航根决策](../navigation/0-text-nav-day-routes-and-moment-opening.md) D1 中「行事不可点击」的约定。涉及 `palace-db` 的新表与迁移、`palace-domain` 的任务校验、`palace-backend` 的任务接口与 OpenAPI、`apps/palace-web` 的行事页。旧 Dashboard 的数据迁移、看板、难易程度、Journey 自动添加任务、TimeTagger 计时都不在范围内。旧版的行为整理见 [Todo 旧版文档](../../../../docs/legacy/dashboard/todo/README.md)。

## 问题与约束

- 任务是长期存在、可以反复安排到某一天的事项。「读完一本书」可以周一做一点、周二再做一点，读完才算完成。所以「今天做过了」和「这件事完成了」必须是两种操作，前者还要累计做过的天数。
- 每天开始时要从所有集合里挑出今天做的事。候选很多，挑选时既要看到全貌，又不能误挑已经排到别的日子的任务。
- 有些任务暂时不想被安排，但仍要留在集合里。旧版用 2096-10-02 这个日期表示，凡是读日期的地方都会把它当成真实计划去比较和排序。
- 新想到的事经常还不知道该放进哪个集合，需要一个先收下、稍后整理的缓冲区。
- 集合里的顺序由用户拖动决定。旧版用整数 `d_order`，插到两条之间需要改写其他行；置顶取最大值加一，最终会和别的行撞号。
- 「今天」是用户所在地的日期。服务端部署时区不一定等于浏览器所在时区，旧版正是因为同时用了浏览器日期、`time.Now()` 和数据库 `CURRENT_DATE` 而难以核对。
- Palace 只有一个用户，界面遵循「少 UI、以文字为主」：操作收在右键和 `···` 菜单里，新建和安排有快捷键。

## D1：页面与地址

- 地址：`/todos` 是今日，`/todos/inbox` 是收件箱，`/todos/lists/{id}` 是一个集合。视图写在地址里，后退回到上一个视图。
- 页面宽 920px，左列 120px，与右侧相隔 104px。左列依次是「今日」（旁边是「已做 / 总数」）、一段空隙、收件箱、各集合（旁边是未完成任务数），末尾一个「＋」新建集合。集合按创建顺序排列，不能拖动。
- 右键左列的集合名，可以改名或删除集合；收件箱没有这个菜单。删除集合会连同其中的全部任务一起删除，先弹窗确认。

**为什么页宽在 760 和 1200 之间**：任务一行一条，用不着回响那样的多列；但左列和任务之间需要拉开距离，760px 放不下 120px 的左列、足够的间隔和较长的任务标题。

## D2：任务的组成与排期状态

| 部分 | 规则 |
| --- | --- |
| 标题 | 去除首尾空白后非空，UTF-8 不超过 1 KiB |
| 位置 | 收件箱，或一个集合 |
| 排序键 | D4 的 fractional-indexing 键 |
| 链接 | 可选，`http`/`https` 的绝对地址，不超过 2 KiB；有链接时标题可点击，在新标签页打开 |
| 正文 | 可选，Markdown 纯文本，UTF-8 不超过 256 KiB；在侧栏的文本框里编辑 |
| 排期 | 未排期、搁置、某一天；排在某一天时还有「今日已做」 |
| 做过的天数 | 非负整数 |
| 完成时间 | 未完成为空 |

排期状态在领域层是一个枚举：`Open`（未排期）、`Shelved`（搁置）、`Day { day, done }`。收件箱里的任务只能是 `Open`，所以位置和排期合起来是 `Inbox`、`List { list, plan }` 两种。

- 排到的日子早于今天时，页面把它看作未排期：不在今日出现，安排时可以再选。这样跨过午夜不需要服务端改写任何行。
- 任何改变排期的操作都把「今日已做」清掉，做过的天数不变。
- 收件箱的任务不能排期、不能完成：它只是缓冲区，要先移到集合里。移入收件箱时排期一并清除。旧版的收件箱同样不提供排期和归档。
- 搁置的任务留在集合里，标题颜色淡一档，旁边写「搁置」，安排今日时不列出。搁置一个排在今日的任务，它就离开今日。

**为什么搁置是独立状态而不是远期日期**：哨兵日期在每个读日期的地方都要被特判，漏掉一处就会把它当成 2096 年的真实计划去排序、显示或比较。独立状态让「未排期 / 搁置 / 某天」三者在数据库和类型上都不会混淆。

## D3：今日已做、完成与恢复

- **今日已做**：只能作用于排在今天的任务。勾上时做过的天数加一，取消时减一；重复设置同一个值不改变天数。请求带上页面认为的「今天」，服务端只在任务确实排在这一天时接受，否则返回 409，这样跨过午夜后旧页面上的点击不会记到昨天的任务上。
- **完成**：任务离开集合，进入集合底部折叠的「已完成 N」，同时清除排期和今日已做，做过的天数保留。完成后几秒内可以撤销，撤销把任务放回原来的位置；原来的键已被别的任务占用时放到顶部。
- **恢复**：回到原集合的顶部，排期为未排期。
- **已完成**列表按完成时间从新到旧，显示做过的天数和完成时间，可以恢复、删除（立即生效），「清空」删除这个集合的全部已完成任务，先在原处问一句「清空 N 个？」。

**为什么今日已做不是完成**：长期事项每天推进一点。把两者合并，要么每天都得重建任务，要么失去「做过多少天」这个信息。

## D4：排序键由前端用 fractional-indexing 生成，服务端校验格式并保证不重复

- 键的格式与 [`fractional-indexing`](https://github.com/rocicorp/fractional-indexing)（rocicorp）一致：一个字母开头的整数部分，字母决定整数部分的长度，后面是 base62 小数部分，小数部分不以 `0` 结尾。集合内按键的字节序升序排列，键小的在上。
- 前端是唯一生成键的一方，用该库的 `generateKeyBetween`：新建、恢复、移到别的集合时取当前第一条之前；置顶、置底取两端之外；拖动取新邻居之间。每次只写被移动的那一条。
- 服务端用同样的规则校验格式，拒绝不合法或超过 1 KiB 的键；数据库列使用 `COLLATE "C"`，排序与 JavaScript 的字符串比较一致。
- 同一位置（收件箱或一个集合）里未完成的任务键不重复，由部分唯一索引保证；两个标签页恰好生成了同一个键时，后写的一方得到 409，页面刷新后重试。已完成的任务不参与，因为恢复时会拿到新键。

**为什么由前端生成**：拖动发生在前端，邻居就在前端手里；服务端再生成一次只是把同一个计算搬过去，还得为 Rust 维护一份与 npm 库逐字节一致的实现。服务端只需要知道键是合法的、彼此不重复，这两点用格式校验和唯一索引就能保证。

**为什么要求唯一**：`generateKeyBetween(a, b)` 要求 `a < b`。两个相同的键之间无法插入，页面会在下一次拖到它们之间时失败。

## D5：存储与接口

新表 `todo_list`（`id`、`owner_id`、`name`、时间戳）与 `todo`（`id`、`owner_id`、`list_id`、`title`、`position`、`link`、`body`、`planned_on`、`shelved`、`done`、`done_days`、`completed_at`、时间戳）。

- `list_id` 为空表示收件箱；`(owner_id, list_id)` 复合外键引用集合，`ON DELETE CASCADE`。
- 检查约束：收件箱的任务没有排期、没有完成时间；`shelved` 与 `planned_on` 不同时出现；`done` 只在有 `planned_on` 时为真；已完成的任务没有排期；`done_days >= 0`。
- 任务和集合不进入同步域，不分配 `serverVersion`，与文章、标注相同。

| 方法与路径 | 作用 |
| --- | --- |
| `GET /api/todos` | 全部集合与全部未完成任务 |
| `POST /api/todos` | 新建任务，`{ list_id, title, position }`，`list_id` 为 `null` 表示收件箱 |
| `PUT /api/todos/{id}` | 整体替换 `list_id`、`title`、`link`、`position`、`plan` |
| `DELETE /api/todos/{id}` | 删除任务 |
| `GET`/`PUT /api/todos/{id}/body` | 读取或替换正文 |
| `PUT /api/todos/{id}/done` | `{ day, done }`，设置今日已做 |
| `POST /api/todos/{id}/complete` | 完成 |
| `POST /api/todos/{id}/restore` | `{ position }`，恢复 |
| `POST /api/todos/plan` | `{ day, ids }`，把未排期的任务排到这一天 |
| `POST /api/todo-lists`、`PUT`/`DELETE /api/todo-lists/{id}` | 新建、改名、删除集合 |
| `GET`/`DELETE /api/todo-lists/{id}/completed` | 已完成列表、清空 |

- `plan` 在接口上是带 `kind` 的联合：`{ kind: "open" }`、`{ kind: "shelved" }`、`{ kind: "day", day, done }`；写入时 `day` 变体不带 `done`。
- 列表不分页：未完成任务是用户亲手维护的，数量有限，今日、安排和计数都需要全部任务。正文较长，只返回 `has_body`，打开侧栏时再取。
- 跨 Owner 与不存在都返回 404；对已完成任务做编辑或今日已做、完成收件箱任务、今日已做的日子与排期不符、排序键冲突都返回 409；格式不合格、给收件箱任务排期返回 400 并指出字段；一次安排超过 1000 个 id 返回 413。

## D6：安排今日

- 点「安排」或按 `p`，今日的位置换成候选列表：收件箱以外、未完成、没有搁置的任务，按集合分组，组内沿用集合自己的顺序。
- 已经排在今天或以后某天的任务也列出来，标出日期，但不能勾选；要改它们的日子，用任务自己的菜单。
- 勾选若干条后「排入今日」，一次请求写入，只改变未排期（含排到过去日子）的任务；取消或 `Esc` 不改变任何东西。

**为什么不按做过的天数排序**：旧版按天数降序排列候选。常做的事排在前面，新任务却永远沉在底部；按集合自己的顺序，用户拖到上面的就是想先做的。

## D7：任务行与菜单

- 今日的行以圆圈开头，点它切换今日已做；集合里的行以一个淡点开头，右侧写排期（今日、明日、一周内写星期几、更远写月日、搁置）。悬停时行尾出现 `···`。
- 右键或 `···` 打开同一个菜单：今日已做（仅排在今天时）、完成、排期（今日、明日、选日期、搁置或取消搁置、清除排期）、改名、链接、正文、置顶、置底、移到、删除。收件箱的任务没有完成和排期。
- 改名与链接在行内原地编辑，`Enter` 或离开输入框保存，`Esc` 取消；双击标题也能改名。「选日期…」打开日历对话框。正文在右侧滑出的侧栏中编辑，「关闭」或 `Esc` 时保存，清空即删除正文。
- 完成和删除之后底部出现一行提示和「撤销」。删除在提示消失后才真正发出请求，撤销时什么也不发。
- 集合内用 `@dnd-kit/core` 与 `@dnd-kit/sortable` 拖动排序：指针移动 4px 后才开始拖动，单击、双击和选择文字不受影响；落点取离指针最近的行，所以越过首行之上或末行之下时落在相应的一端；也支持键盘拖动（`Space` 拿起，方向键移动，`Space` 放下）。今日视图不能拖动，它的顺序来自各集合。
- 快捷键：`n` 在当前集合新建任务（在今日时转到收件箱新建），`p` 安排今日（在集合里时先回到今日），`Esc` 依次关闭侧栏、安排和新建输入框；新建输入框为空时回车也会关闭它。所有修改先写进页面上的看板再发请求；请求失败时重新读取看板，并在底部提示原因。

## 不变量

1. 任务与集合只在所属 Owner 的认证上下文中可见、可改；跨 Owner 与不存在都返回 404。
2. 收件箱的任务没有排期、不能完成；已完成的任务没有排期。
3. 排期只有未排期、搁置、某一天三种状态；今日已做只存在于排在某一天的任务上。
4. 做过的天数只在今日已做从假变真时加一、从真变假时减一，从不为负。
5. 同一位置的未完成任务排序键格式合法且互不相同；移动一条任务只改写这一条的键。
6. 删除集合在同一事务中删除它的全部任务。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| 整数排序值 | 简单 | 插到中间要改写其他行，置顶取最大值加一会随时间溢出或撞号 |
| 服务端根据「放在谁之前」生成键 | 客户端不需要算法 | 需要 Rust 版的同格式实现，且与前端库逐字节一致；拖动的邻居本来就在前端 |
| 远期哨兵日期表示搁置 | 不增加列 | 每个读日期的地方都要特判，见 D2 |
| 收件箱作为一行普通集合 | 外键简单 | 每个 Owner 都要预建一行并禁止删除和改名；`list_id` 为空直接表达「还没有集合」 |
| 服务端按部署时区判断今天 | 服务端可以自己算今日 | 用户与部署可能不在同一时区；页面带上自己的日期更直接 |
| 安排时按做过的天数排序 | 常做的事在前 | 新任务沉底，见 D6 |
| 删除时弹窗确认 | 不会误删 | 多一次点击；延迟发送的撤销同样安全 |

## 风险与为什么不能直接改写

- **排序键的格式**：已有的键都是按 rocicorp 格式生成的。换库或换格式之前，必须先按新格式重写全部键，否则新旧键混排时顺序错乱，`generateKeyBetween` 也会因为看不懂旧键而失败。
- **键的增长**：在同一个缝隙里反复插入，键会每次变长一点。1 KiB 的上限足够日常使用；真到上限时，需要一次按当前顺序重排整个集合的操作，目前没有提供。
- **跨午夜的页面**：页面在午夜之后仍显示昨天的今日。重新聚焦页面时会按新的日期重新计算；今日已做的请求带日期校验，不会记错日子。

## 本决策未解决的问题

- **旧 Dashboard 的数据迁移**：需要先决定正文与看板这些材料的去留。
- **看板**：已经放弃，不再实现。
- **重复规则、提醒、执行日期历史**：目前只累计天数，不记录每一次发生在哪天。
- **任务出现在时刻的时间线上**：涉及 Moment 的类型与卡片设计，另行决定。
- **集合的排序**：目前按创建顺序。

## 落地与验收

- 迁移 `0020_todos.sql` 新建 `todo_list` 与 `todo`，包括复合外键、检查约束和部分唯一索引 `todo_open_position`（`NULLS NOT DISTINCT`，让收件箱也参与唯一性）。

- `apps/palace-web`：`lib/todo.ts` 是按今日读取看板、分组与生成键的纯函数，`components/todo/use-todo-actions.ts` 负责全部修改，`components/todo/` 下是左列、今日、集合、任务行、菜单、正文侧栏与撤销提示，样式在 `todo.css`；依赖 `fractional-indexing` 4.x 与 `@dnd-kit/core`、`@dnd-kit/sortable`、`@dnd-kit/utilities`。
