# 集合按拖动的顺序排列，排序键与任务相同，收件箱固定在最上方

左列的集合不再按创建顺序排列，而是像集合里的任务一样可以拖动排序。集合多了一个 `position`，格式、生成方与唯一性规则都沿用任务的 fractional-indexing 键：页面生成键，服务端校验格式，同一 Owner 的集合键不重复。收件箱不是集合，始终在今日之后、所有集合之前，不能拖动。今日分组与安排候选的集合顺序随之改变。

当前为 `implemented`，核心测试用例见[行事](../../../test-cases/web/todo/todos.md)，接口与用法见[行事功能文档](../../../../docs/features/todos/README.md)。本文件修改[行事根决策](0-today-and-lists-with-fractional-order.md)的 D1 与 D5，并解决其「本决策未解决的问题」中的「集合的排序」。涉及迁移 `0022_todo_list_position.sql`、`palace-db` 的集合读写、`palace-backend` 的集合接口与 OpenAPI，以及 `apps/palace-web` 的左列。已有集合在迁移中按原来的创建顺序取得键，顺序不变。

## 问题与约束

- 集合是长期存在的分类，常用的应当靠前；创建顺序只反映「哪个先想到」，用户无法调整。
- 今日和安排都按集合顺序分组。按创建顺序时，最重要的集合可能永远排在最后。
- 任务已经有一套成熟的排序方案（根决策 D4）。集合再造一套规则，就要多维护一份格式校验、一份冲突处理和一份前端算法。

## 继承与修改

| 前序约定 | 本决定 |
| --- | --- |
| 根决策 D1：集合按创建顺序排列，不能拖动 | 修改：集合按 `position` 的字节序排列，左列中可以拖动，见 D2 |
| 根决策 D1：左列依次是今日、空隙、收件箱、各集合、「＋」 | 继承，不变；收件箱与今日不参与拖动，「＋」新建的集合排在末尾 |
| 根决策 D4：键由前端用 `fractional-indexing` 生成，服务端校验格式，同一位置不重复，冲突返回 409 | 继承；集合的键遵守同一规则，唯一范围是同一 Owner 的全部集合，见 D1 |
| 根决策 D5：`todo_list` 只有 `id`、`owner_id`、`name` 与时间戳；`POST`/`PUT /api/todo-lists` 只带 `{ name }` | 修改：`todo_list` 增加 `position`；新建与修改都带 `{ name, position }`，`PUT` 整体替换两者，见 D1 |
| 根决策 D6：安排时按集合分组，组内沿用集合自己的顺序 | 继承；组的先后随集合的新顺序 |
| 根决策 D7：集合内拖动的手感（4px 起拖、越界落在两端、键盘拖动） | 继承，左列采用同样的手感；键盘只用 `Space` 拿起，见 D2 |

## D1：集合的排序键与接口

- `todo_list.position` 与 `todo.position` 同格式：`COLLATE "C"`，非空，不超过 1 KiB；唯一性由普通唯一索引 `todo_list_position(owner_id, position)` 保证；任务用的是只约束未完成任务的部分索引，集合没有「已完成」状态，不需要条件。
- `GET /api/todos` 的 `lists` 按 `position, id` 排列，每个集合带上 `position`。
- `POST /api/todo-lists` 与 `PUT /api/todo-lists/{id}` 的请求体都是 `{ name, position }`。改名时页面带回原来的键，移动时带回原来的名字；与任务的 `PUT` 一样整体替换，服务端不需要区分「改名」和「移动」两种请求。键格式不合法返回 400 并指出 `position`，键被同一 Owner 的另一个集合占用返回 409。
- 页面新建集合时取当前最后一个集合之后的键，拖动时取新邻居之间的键；每次只写被移动的那一个集合。

**为什么沿用任务的键**：集合与任务的排序问题完全相同，复用同一个 `TodoPosition` 校验、同一个冲突映射和同一组前端函数（`topKey`、`bottomKey`、`keyAt` 改为接受任何带 `id` 与 `position` 的项）。

**为什么已有集合在迁移中取得整数键**：迁移按每个 Owner 的创建顺序依次写入 `a0`…`az`、`b00`…`bzz`。它们都是库能识别的整数键，前后都留有插入空间，可以容纳 3906 个集合，远超一个人会维护的数量。

## D2：左列的拖动

- 集合的链接本身就是拖动手柄，没有额外的把手。指针移动 4px 后才开始拖动，所以单击仍然打开集合；拖动中的集合淡一档。
- 键盘：在集合链接上按 `Space` 拿起，方向键移动，`Space` 或 `Enter` 放下，`Esc` 取消。`Enter` 不拿起，因为它在链接上的含义是打开集合。
- 松开被拖动的链接时，浏览器仍会对它发出一次点击。dnd-kit 只阻止这次点击的冒泡，`<a>` 的默认跳转仍会整页刷新；页面在 dnd-kit 阻止冒泡的同一时间窗（拖动开始到结束后 50ms）内一并取消默认行为，所以放下不会打开集合。
- 右键菜单（改名、删除集合）不变，挂在同一个链接上。

## 不变量

1. 同一 Owner 的集合排序键格式合法且互不相同；不同 Owner 的键互不影响。
2. 移动或改名一个集合只改写这一个集合。
3. 收件箱始终排在所有集合之前，不参与集合的排序。
4. 已有集合在迁移后的顺序与迁移前的创建顺序一致。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 取舍 |
| --- | --- | --- |
| 整数排序值 | 简单 | 与根决策 D4 否决任务整数排序的理由相同：插入要改写其他行 |
| 单独的「移动集合」接口，只带 `position` | 改名请求不必带键 | 多一个接口和一套 OpenAPI 定义；整体替换与任务的 `PUT` 一致，页面手里本来就有完整的集合 |
| 收件箱作为可拖动的一项 | 用户可以把收件箱放到别处 | 收件箱不是集合（根决策替代方案表），没有自己的行可存键；它是缓冲区，固定在最上方最容易找到 |
| 集合加一个拖动把手 | 不会和单击混淆 | 左列是纯文字，多一个把手破坏版式；4px 起拖已经区分了单击与拖动 |

## 风险与为什么不能直接改写

- **迁移的回填**：迁移在同一事务中添加列、回填、加上非空约束和唯一索引。超过 3906 个集合的 Owner 会因重复键而迁移失败，而不会得到错误的顺序；这个数量在单用户场景下不会出现。
- **键的格式**：与根决策相同，换库或换格式前必须先按新格式重写所有任务与集合的键。

## 落地与验收

- 迁移 `0022_todo_list_position.sql` 添加、回填并约束 `todo_list.position`，建立 `todo_list_position`。
- `palace-db`：`TodoList` 带 `position`，看板按键排序，`insert_todo_list` 与 `update_todo_list` 写入键并把唯一冲突映射为 409；`palace-backend`：`create_todo_list` 与 `update_todo_list` 接受 `{ name, position }`，OpenAPI 声明 409。
- `apps/palace-web`：`components/todo/todo-side.tsx` 用 `@dnd-kit/sortable` 排列集合，`use-todo-actions.ts` 的 `createList` 与 `updateList` 负责写入。

证据见核心测试用例「List order must come from unique well-formed keys」：真实 PostgreSQL 覆盖键唯一、字节序与只改写一行；真实 Router 覆盖接口形状、400 与 409；组件测试覆盖新建与改名带上的键；真实 Chromium 覆盖指针与键盘拖动、收件箱固定以及放下不打开集合。迁移回填的顺序在本地 PostgreSQL 上手工核对过（64 个集合越过 `az` 到 `b00`），没有自动化证据。

任务的排序、今日已做、完成与安排的规则都不变；从本决策起，集合的先后由用户决定。
